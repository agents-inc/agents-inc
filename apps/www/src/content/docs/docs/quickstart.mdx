Setting up is two moves: choose your skills at
[agentsinc.sh/editor](/editor), then run the command it hands you. The
editor is where you choose; the CLI is what writes to disk. Nothing reaches
your filesystem until that command runs, so the browser half is safe to poke
at. This page walks the run and names every file it leaves behind. Read it end
to end the first time; after that the only command you need daily is
`compile`.

:::tip[There may be a shorter route than this one]
This page walks the default: open the editor, click a stack, run the command.
Two situations have a better answer. **Adding this to a codebase that already
exists?** The [stack-detection
skill](/docs/guides/adding-to-an-existing-project) reads your dependencies
instead of asking you to retype them. **Starting from nothing?**
[The composer](/docs/editor/composer) takes a sentence describing the project.
Both end at the same command this page explains, so nothing below is wasted
either way — [Three ways in](/docs/ways-in) compares all three.
:::

## Before you start

You need [Claude Code](https://docs.anthropic.com/en/docs/claude-code)
installed. Codex is not in a release yet, and this page does not walk it —
[Claude or Codex](/docs/configuration/providers) covers what differs.

Nothing needs to be installed globally. `npx` fetches the CLI for you.

## Quick start

1. Open [agentsinc.sh/editor](/editor) and click a stack.
2. Press **Install** at the foot of the right-hand column, and copy the
   command out of the dialog.
3. Run it. This is the CLI, and it is the part that writes to disk.

`npx agents-inc init --ui` opens the same page from your shell if you would
rather not leave it. It prints the address before it tries a browser, so it
also works over SSH and on a machine with no desktop session — but it opens on
the bare catalogue and carries nothing with it, so it is a link rather than a
different route.

```bash
npx agents-inc init --from Ab3xY9_Q
```

Run it from your project root — the folder holding `package.json`. Anything
you set to project scope is written relative to it; anything global lands under
your home directory, in `~/.claude` and `~/.agents-inc/claude/`, wherever you
run from. Global is the recommended starting point —
see [Global-first setup](/docs/guides/global-first-setup).

## What exists afterwards

Take the wording of the summary the CLI prints seriously — it names the exact
directories it wrote to, and where those are depends on the scope you chose.

**Your configuration**, in `.agents-inc/claude/`:

| File              | What it is                                                                                                       |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| `config.ts`       | Plain TypeScript, meant to be hand-edited. Your skills, your sub-agents, and the skill-to-agent `stack` mapping. |
| `config-types.ts` | Generated. Type unions narrowed to what you actually installed, so a mistyped skill id is a type error.          |

At global scope these live at `~/.agents-inc/claude/`.

**Your compiled sub-agents**, in `.claude/agents/`, or `~/.claude/agents/` at
global scope — one markdown file per sub-agent. These are build outputs.
Editing them directly works until the next compile overwrites them; to change a
sub-agent for real, see
[Customizing subagents](/docs/guides/customizing-subagents).

**Your skills**, in one of two places depending on install mode:

- **Plugin** (the default) — registered as Claude Code plugins, under
  `~/.claude/plugins/` at global scope and `.claude/plugins/` at project scope.
  Nothing is copied into your project source.
- **Eject** — copied into `.claude/skills/`, or `~/.claude/skills/` at global
  scope. Yours to modify.

Mode is chosen per skill, so a real installation is often mixed. See
[Install modes](/docs/concepts/install-modes).

:::note[Seeing this before you run anything]
**Preview**, beside Share above the editor's Install button, draws the same
file tree with each file's contents beside it. It is rendered by the same
package the CLI compiles with, so the paths are the ones you will get rather
than an illustration of them.
:::

## The next command

Open `.agents-inc/claude/config.ts`, change something, and run:

```bash
npx agents-inc compile
```

`compile` is the command you will run most. It rebuilds every sub-agent from
the current config and is non-interactive, so it is safe in scripts and CI.
[Editing your config](/docs/guides/editing-config) covers what is worth
changing in there — mainly the `stack` mapping, which decides which skills each
sub-agent receives, and whether each one is preloaded or loaded on demand. Every
field the file accepts is listed in the
[config reference](/docs/configuration/config-reference).

## When something looks wrong

```bash
npx agents-inc doctor
```

Health checks over the installation: config parses, skills resolve, sub-agents
compiled, no orphans, marketplace reachable. It exits non-zero if any check
fails.

`npx agents-inc list` shows what is installed. The full set is in the
[commands reference](/docs/reference/commands), and
[Troubleshooting](/docs/troubleshooting) covers what each refusal means.

## Changing your mind

The editor cannot read what is on your disk, so going back to it is a round
trip through two commands:

```bash
npx agents-inc edit --ui          # publishes this installation and opens it
npx agents-inc edit --from <id>   # applies what you changed there
```

The second command is the one to get right. The install dialog hands out
`init --from`, and that one refuses a directory that already has an
installation — `An installation already exists at …`. `edit --from` is the one
that accepts a setup already in place. It states a whole roster, so whatever it
leaves out is removed, and every removal is named before anything is written.

`npx agents-inc update` refreshes the listing of every marketplace your config
names through Claude Code's own plugin commands, and that is all it does — the
plugins already installed keep their version, it asks nothing, and it recompiles
nothing, because a sub-agent references a plugin skill by pointer rather than by
copy. Ejected skills are copies you own, so it never touches them.
