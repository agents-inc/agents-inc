A **skill** is one atomic, reusable unit of expertise: one library or one practice, written once. React is a skill. Zod is a skill. Vitest is a skill.

Skills exist so that expertise is not copied into agent prompts by hand. You pick the skills that match the stack you actually use, and the CLI compiles them into [sub-agents](/docs/concepts/sub-agents). Change a skill and recompile, and every agent that uses it updates.

## Quick start

Open the [editor](https://agentsinc.sh) and type into the **search skills** field above the grid. It matches name, slug and description across the whole catalogue, and the domain chips beside it narrow to one domain at a time. Clicking a cell selects the skill there and then — [Selecting skills](/docs/editor/selecting-skills) covers the rest of the grid.

:::note[From the terminal]

```bash
npx agents-inc search zustand
```

`search` matches a query against every skill's id, display name, slug, description and category, and prints what hits. It reads the marketplace this installation points at plus the local skills already on disk, and it selects nothing — installing what you find is the wizard's Skills step, which [Quickstart](/docs/quickstart) walks.
:::

## What a skill is on disk

```
skills/{skill-name}/
  SKILL.md         # The skill content
  metadata.yaml    # Name, domain, category, relationships
```

Both files are required — the CLI's loader validates the pair, and `npx agents-inc doctor` reports any skill missing either one.

## How skills are organised

Each skill belongs to one of {DOMAIN_COUNT} **domains** — {DOMAIN_IDS} — and to a **category** within it (`web-framework`, `web-client-state`, `api-api`, and so on). A category can be marked exclusive: the editor heads it `one of` and a click swaps your pick rather than adding to it, and the wizard treats it as a radio group. Either way you get one framework, not three.

Skills also declare relationships to each other (`requires`, `conflictsWith`). Those relationships drive the compatibility filtering you see while selecting.

## Where skills come from

The official marketplace at [agents-inc/skills](https://github.com/agents-inc/skills) is the default source and currently ships {SKILL_COUNT} skills. You are not limited to it:

- **Add one straight from GitHub.** `＋ Add skill` on the editor's filter bar searches skills outside the catalogue and stages them into a category you choose. An added skill always installs by ejecting — a plugin serves somebody else's repository as-is, and the metadata a skill needs can't be written into it.
- [Write your own](/docs/guides/writing-custom-skills) for project-specific knowledge.
- [Run your own marketplace](/docs/guides/creating-a-marketplace) curated for your team's conventions.

## How a skill reaches an agent

Two separate decisions:

- **Install mode** — whether the skill's files live in a Claude Code plugin or are copied into your project. See [Install modes](/docs/concepts/install-modes).
- **Load behaviour** — whether the skill is named in the compiled agent's frontmatter `skills:` list, which is the key Claude Code loads from when the agent starts (`preloaded: true`), or left for the agent to pull in through Claude Code's Skill tool when the work calls for it. Dynamic is the default and keeps prompts lean. It's set per sub-agent rather than per skill, so one skill can be preloaded on one sub-agent and dynamic on another: in the editor it's the `pre` / `lazy` word on the skill's row under that sub-agent in the roster, and in your config it's the `preloaded` flag on that one assignment. See [Editing your config](/docs/guides/editing-config).

Both decisions show up in the compiled file itself, and [Anatomy of a sub-agent](/docs/reference/sub-agent-anatomy) reads one line by line.
