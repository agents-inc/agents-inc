# Release 0.142.2 (2026-07-18)

Two more dual-scope wizard bugs found in real usage right after 0.142.0 shipped, both now fixed and verified end-to-end.

## Fixed

### A dual-scope skill/agent collapsed via spacebar lost its active styling in the same session

`toggleTechnology`/`toggleAgent` correctly collapse a persisted `[P][G]` pair to a single active
inherited-global entry when spacebar drops the project half — the skill/agent genuinely stays
active via the global install. But the domain-selection array (`domainSelections`/
`selectedAgents`, which drives the build/agents grid's "selected" rendering) was computed
separately from the reconciled config, so it unconditionally dropped the id — the row rendered as
deselected, and an exclusive category's `(N of M)` counter dropped to 0, even though the `[G]`
badge still correctly showed it installed.

Fix: `toggleTechnology`/`toggleAgent` now compute the reconciled config first, then check whether
the skill/agent still has an active entry (project or global) before removing it from the
selection array — a genuine full removal still drops normally, but a dual-scope collapse keeps it
selected, matching what a save-and-reopen already re-derives.

### A second spacebar press on the collapsed row incorrectly removed the global install too

Once the row above stays selected after collapsing, pressing spacebar a *second* time re-ran the
same removal logic — and since there's no project entry or tombstone left to collapse, it fell
through to "convert a previously-installed global skill into an excluded tombstone," silently
suppressing the still-real global install from the project's perspective. This should have been
blocked, exactly like any skill that was global-only from the start of the session.

Root cause: several guards (the blanket "can't touch global from project scope" guard, and the
`s`-scope-toggle's tombstone-recreation and persisted-pair checks) only consulted the frozen
hydration snapshot, which can't tell "this pair is exactly as it was when the wizard opened" apart
from "you just rebuilt this pair yourself a moment ago" — both can look identical. Fixed by adding
explicit session-scoped tracking of which skills/agents had their `[P][G]` pair (re)established by
a store action this session, consulted alongside the snapshot:

- A second spacebar on the collapsed row is now correctly **blocked** with the existing toast.
- `s` on the collapsed row correctly **restores** a fresh `[P][G]` pair (recreating the tombstone).
- `s` again **freely toggles** the freshly-rebuilt pair `P↔G` within the same session — it's only a
  pair reopened untouched from a *previous* session that stays locked to spacebar-only.

Fixed symmetrically for both skills and agents.
