# Release 0.149.0 (2026-08-02)

`init --from <id>` installs a configuration shared from agentsinc.sh

The website has been handing people `npx agents-inc init --from <id>` as its install command. No published CLI had that flag, so every copy of it failed with `Nonexistent flag: --from`. This release is the other half of that command.

## Added

### `init --from <id>`

Someone builds a stack on the website and gets a short id back. `init --from <id>` fetches that configuration and installs it without the wizard — the whole point of the site being that the choosing happens where the catalogue can be seen.

The flag overrides an existing installation rather than diverting to the dashboard: an id is an explicit instruction to install _that_ configuration. Nothing on the path assumes a terminal is attached, so it runs headless and in CI.

**Version pinning is exact.** The payload schema is a vendored copy of the web app's, and a payload minted under any other version fails to decode rather than being guessed at. What installs is always what was shared.

**Unknown ids inside a payload are the opposite.** They are skipped and named, never fatal — ids are catalogue slugs, so a configuration shared before a skill was renamed should still install everything else, and failing the whole decode would make every rename retroactively break every shared id. Skipped skills and sub-agents are reported by name, because a count cannot be acted on and a list can.

**Mapping produces the same result the wizard produces**, so everything downstream — writing the config, installing skills, compiling agents — is the path that already existed rather than a second one free to drift from it. The one addition is a per-agent stack assignment: the payload says which sub-agents carry which skills, and without carrying that through, the install pipeline's ownership rules would broadcast every scope-compatible skill to every selected sub-agent, handing a bare sub-agent someone else's skills.

**Every failure is a message rather than a throw.** The fetch runs before anything has been written, so there is nothing to roll back and the only useful thing to do is explain: an unreachable store, a missing id, a payload that does not match the expected format.

## Note on shared ids minted before today

The payload version moved to 3 when the web app deployed. Ids minted under the older format no longer decode. Nothing installed from them — no published CLI could read an id at all until this release — so the only effect is that an old link now reports a format mismatch instead of silently installing something different.
