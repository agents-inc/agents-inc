# Release 0.141.0 (2026-04-21)

Config propagation + install-integrity + info-panel correctness bundle (D-228, D-229, D-230, D-231, D-232).

## Fixed

### D-228 — Project `config-types.ts` imports from global install

`writeScopedConfigs` and `propagateGlobalChangesToProjects` in `src/cli/lib/installation/local-installer.ts` called `writeStandaloneConfigTypes` on the PROJECT branch, bypassing the import-from-global code path in `regenerateConfigTypes` (`config-types-writer.ts`). Every project's `config-types.ts` duplicated the global unions inline instead of extending `GlobalSkillId` / `GlobalAgentName` / `GlobalDomain` / `GlobalCategory` via `import type`.

Both call sites now route through `regenerateConfigTypes(projectDir, data, extras)`. Two helpers kept orchestrator-local:

- `buildConfigTypesBackgroundData(matrix, agents)` — wraps the already-loaded matrix + agents into the `ConfigTypesBackgroundData` shape (no re-load).
- `buildProjectTypesExtras(finalConfig, matrix)` — derives project-only `extraSkillIds`, `extraAgentNames`, `extraCategories`, `extraDomains` from project-scoped entries; category/domain lookups go through the matrix so a project skill that introduces a new category or domain lands in the project's union extension.

Global-root and global-config write paths still call `writeStandaloneConfigTypes` — those are legitimately global types files that must inline their own unions.

Resolves both **D-216 Regression #1** (project-scope init/edit) and **D-228** (HOME-scope propagation re-writing every registered project).

### D-229 — Plugin install per-skill failures now hard-error

`ensureMarketplace` returns successfully, but `installPluginSkills` can still reject individual skills per-entry (per-skill `claude plugin install` rejection, e.g. skill not in marketplace). Both `init.tsx::installPluginsStep` and `edit.tsx::applyPluginChanges` emitted one `this.warn()` per failed skill and then silently continued. `writeConfigAndCompile` then wrote `config.ts` entries claiming `source: "<marketplace>"` for skills that had never actually been installed into `settings.json`. `detectInstallation` trusts `config.ts`, so the lie was self-perpetuating.

Both commands now hard-error after the per-skill warnings:

```ts
if (pluginResult.failed.length > 0) {
  this.error(
    `Failed to install ${pluginResult.failed.length} plugin skill(s). Plugin install intent could not be honored. Verify the skill id matches the marketplace, re-run with --refresh to update the marketplace, or switch affected skills to eject mode.`,
    { exit: EXIT_CODES.ERROR },
  );
}
```

This fires before `writeConfigAndCompile`, so no orphan config entries are written. Uninstall failures remain diagnostic-only.

Same anti-pattern class as the earlier `2026-04-16-silent-plugin-install-skip-on-missing-marketplace` and `2026-04-17-init-partial-state-on-plugin-hard-error` findings; all three now closed.

### D-230 / D-232 — Info-panel diff baseline treats tombstones as slot-occupants

`skill-agent-summary.tsx` pre-filtered tombstones out of the diff baseline (`installedSkillConfigs.filter((s) => !s.excluded)`). That shortcut produced two distinct user-facing bugs:

- **D-230**: G→P scope toggle on a pre-existing global install emits the dual-scope shape `[{id, project}, {id, global, excluded}]`. The renderer then saw the pre-existing global as active in baseline but nothing occupying the global slot in current (the tombstone was excluded by the `!c.excluded` clause inside the `removedSkills` match), flagging the global as removed and rendering a spurious `- React` in the Global section.
- **D-232**: On the next `cc edit`, the saved config carries the same dual-scope shape. The baseline post-filter stripped the `react:global` tombstone, so `prevSkillKeySet` lacked the `react:global` key. The tombstone in current then rendered via `uniqueExcludedGlobalSkills` with `isNew=true`, producing a spurious `+ React` on a long-installed global.

Pre-filter removed; tombstones are now first-class baseline entries that occupy `(id, scope)` slots. `removedSkills` / `removedAgents` now use slot-occupancy matching: a baseline entry is "removed" only if nothing — active or tombstone — occupies that slot in current. `prevSourceMap` and `inheritedGlobalSkills` still filter to active baseline entries (tombstones don't track a live install source / aren't themselves installs).

D-225 investigation 09 (`todo/D-225-investigations/09-tombstone-interaction.md`) explicitly analyzed this and concluded "do NOT pre-filter tombstones — it regresses Scenario B and Scenario D"; the superseding investigation's recommendation now lands in code. Existing E2E assertions for Scenarios A / C that encoded the INCORRECT `Global: +` behavior rewritten to assert `Global: •` (global install was always live behind the tombstone; stripping the tombstone restores, not re-adds).

### D-231 — Drop dead `version` field from `config.ts`

`ProjectConfig.version` (`"1"` literal) was emitted and accepted but no reader consumed it. Dropped from:

- `src/cli/types/config.ts` — type definition
- `src/cli/lib/schemas.ts::projectConfigLoaderSchema` — Zod schema
- `docs/guides/editing-config.md` — example in user docs
- Unit tests (`config-round-trip.test.ts`, `define-config.test.ts`, `config-generator.test.ts`, `project-config.test.ts`) — literal `version:` in assertions and fixtures

Loader is shape-tolerant; existing configs round-trip without the field on next `cc edit` save.

## Proposed standards

- `.ai-docs/reference/config/config-writer.md` + `.ai-docs/reference/features/configuration.md` — writer-selection rule: project `config-types.ts` always via `regenerateConfigTypes`; `writeStandaloneConfigTypes` only for global paths.
- CLAUDE.md Data Integrity — plugin install operations that report per-skill failures MUST hard-error before `writeConfigAndCompile` writes `config.ts`.
- `.ai-docs/standards/clean-code-standards.md` Investigation Referencing — when a task has multiple investigation documents that disagree, the implementation must cite the adopted investigation in a comment near the load-bearing line, or deprecate the superseded one.
- `.ai-docs/standards/e2e/assertions.md` Diff-Shape Assertions — never use `expect.arrayContaining([...])` for info-panel diff assertions without a matching `.not.toEqual(arrayContaining([bug prefix]))` negative check.
