# Release 0.143.0 (2026-07-20)

Data-integrity and correctness pass across the install, config-generation and wizard layers, on top of a behaviour-preserving expressive-TypeScript refactor (D-218, D-242, D-243, D-244, D-245, D-246, D-247, D-248, D-249, D-250, D-251, D-252)

Every fix in this release was found by driving the real CLI across 172 exploratory scenarios under an isolated `HOME`, then adversarially re-verifying each finding before acting on it.

## Fixed

### D-242 — `f` hotkey bypassed the global-skill lock and deleted a global skill

`toggleTechnology` (spacebar) guards globally-installed skills during a project-scope edit; `toggleFilterIncompatible` (the `f` hotkey) did not. Pressing `f` removed the skill with no toast, and the resulting removal deleted the skill directory from `$HOME/.claude/skills/` while the global config still declared it installed — leaving config and filesystem permanently diverged.

The delete itself was correct: `removeDeletedLocalSkills` deletes at the skill's recorded scope by design. The defect was that a global-scoped skill could reach `removedSkills` from a project context at all. The same lock now applies to both paths.

The inconsistency was recent — the lock landed on the spacebar path only in 0.142.2, which closed one hole and left the other open.

### D-243 — deselect and re-select in one session discarded scope and source

Re-selecting a skill rebuilt it from wizard defaults instead of the hydration snapshot, so a skill saved as `(scope: project, source: eject)` came back as `(global, plugin-intent)`, triggering a bogus scope/source migration and deleting its ejected directory. Exit code was 0 throughout. A re-select of a skill still present in the snapshot is now treated as a restore.

### D-244 — generated config types collapsed to `string`

Any install that placed skills at project scope left the global config empty, and `formatUnion` returned the literal `"string"` for an empty member list. The project's `config-types.ts` then extended those aliases, so `SkillId`, `AgentName`, `Domain` and `Category` all degraded to `string` — silently disabling every type check in the user's `config.ts`. A `tsc` probe assigning bogus literals to all four aliases exited clean; the mixed-scope control exited 2.

Empty unions now emit `never`, matching the behaviour `generateBlankGlobalConfigTypesSource` already had for the identical state.

### D-245 — wrong marketplace name recorded for local sources

`loadFromLocal` never read the source's `.claude-plugin/marketplace.json`, so `config.ts` recorded `source: "agents-inc"` for every skill while the install output, `installed_plugins.json` and `settings.json` all named the real marketplace. `loadFromRemote` already read it — that asymmetry was the defect, and it affected local-directory sources (`--source /path`).

Also in this area: a custom `--source` no longer produces two identically-named entries in the sources grid, and local skill discovery no longer lets one malformed `metadata.yaml` fail the whole command.

### D-246 — global uninstall silently orphaned every plugin

`mergeGlobalConfigs` dropped `marketplace` and `source` from the global config written during a project-scope init. `getCliInstalledPluginKeys` builds its registry key from `config.marketplace`, so with the field absent no key matched: `uninstall --yes --all` run **from the home root** exited 0, printed no `Plugins:` section, removed the compiled agents and `.claude-src/`, and left every plugin registered in `installed_plugins.json` and enabled in `settings.json` — with the only record of them now deleted.

Both fields now carry through the merge, fill-only, so an existing global value is never repointed from a project context.

### D-247 — sources grid showed the marketplace owner's name

The grid's inline label resolved to the manifest's `owner.name`, rendering a person's name where a source label belongs. The manifest has no honest source-label field — `name` is an identifier and `description` is prose — so the field was removed end-to-end rather than re-derived, and the grid now uses the source name.

### D-248 — project-context source switch was performed but never recorded

`executeMigration` resolves paths from each skill's own scope, so a project-context edit legitimately writes and deletes under `$HOME` and calls the user-scope plugin registry. But `writeConfigAndCompile` passed `authoritativeScope: "owned"`, and `mergeConfigs` preserves inherited global-active entries verbatim — so the new source was never written. Disk said eject, both configs said plugin, the registry was empty, and no later edit could reconcile it.

The switch is now recorded, scoped narrowly to the ids the migration actually acted on rather than by widening scope authority.

### D-249 — a cancelled `init` made the setup wizard unreachable

`ensureBlankGlobalConfig()` ran before the wizard rendered, and `detectInstallationInDir` returns an installation on the config file's existence alone without checking whether it declares anything. So a single Ctrl+C at the first step left a blank global config behind, and every subsequent `cc init` — in any project — showed the dashboard instead of stack selection, with no `--force` escape hatch. The artifact is no longer created before the wizard succeeds.

### D-250 — `cc init` in a project did not materialise the project

Because `init` routes through the dashboard to `Edit` once a global install exists, `cc init` in a project and a bare `cc edit` reached identical code. Project materialisation — writing `<project>/.claude-src/config.ts` and `config-types.ts`, and registering the path in the global `projects[]` — was riding on a spurious config/filesystem diff, and stopped happening once D-248 made the global config truthful.

Caller intent is now passed explicitly from the dashboard flow, so `cc init` always materialises and registers the project, while a no-op `cc edit` against the global fallback leaves it untouched.

### D-251 — install report described the wrong directories

The success report printed project paths for skills and agents actually written to the home directory — wrong on the default `init` path, where every skill is global-scoped — and printed skill display titles (`Reviewing/`) where the on-disk directories are ids (`meta-reviewing-reviewing/`). It now reports one block per non-empty scope, using names that match the filesystem.

### D-252 — per-skill plugin-install failure left orphan config entries

A failed plugin install during migration was collected as a warning and the run continued, writing `config.ts` entries recording a plugin source for skills that were never installed. It now hard-errors before config is written, matching the guard the newly-added-skill path already had. Extends D-218.

## Changed

- `executeMigration` checks the marketplace precondition **before** any destructive step. Previously the `toPlugin` branch deleted the ejected copies first, then discovered there was no marketplace and demoted it to a warning — destroying hand-edited skill content while exiting 0. (D-218)

## Internal

- Expressive-TypeScript refactor across the type, configuration, loading, installation and wizard layers: type consolidation, shared-value extraction, function dedup and dead-code removal. Behaviour-preserving.
- Removed a shared exported constant holding mutable arrays that were handed to callers by identity; see `.ai-docs/agent-findings/2026-07-20-shared-mutable-constants-and-false-dry.md` for why the fix was to revert the deduplication rather than add a factory.
