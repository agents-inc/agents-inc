# Release 0.165.0 (2026-10-01)

A new installation's source folder is `.agents-inc/<provider>/`, a configuration can be installed onto OpenAI Codex, and `edit --from` applies a sub-agent's model and effort (CLI-893, CLI-895, CLI-896, CLI-898, CLI-899)

**The provider is a fact about a folder, and nothing else records it.** One installation is exactly one provider, and the folder it lives in, `.agents-inc/claude/` or `.agents-inc/codex/`, is the whole record of which. `config.ts` has no field for it and a shared payload carries none, so a share id says nothing about the host it is installed onto. That is why the folder rename and the second provider ship together: the rename is what gave the provider somewhere to be written down.

## Added

### OpenAI Codex as a second provider

**The provider is chosen in the editor, not in the terminal.** A `provider` row in the roster footer picks it, and the command the Install dialog hands you becomes `npx agents-inc init --from <id> --provider codex`. The terminal wizard gains no step. `--provider` without `--from` exits `INVALID_ARGS` and names `--from` and the editor, because the flag only says which folder a run creates and there is nothing to create without a configuration. `--provider claude` installs byte-for-byte what no flag installs.

**Where one scope holds an installation of each provider, `--provider` is how you pick one.** `edit`, `uninstall`, `share`, `eject`, `compile` and `update` refuse rather than guess, naming both installations and the flag. `list --provider` picks one, and without the flag `list` says another installation is there. `doctor` reports the state rather than refusing, because it is the state you most need to look at. Each provider family inherits and propagates only within itself.

**Codex offers three of the four placements:** plugin + global, eject + global (`$CODEX_HOME/skills/<id>/`) and eject + project (`<repo>/.agents/skills/<id>/`). The last is a committed directory that reaches the model in that repository with no plugin, no marketplace and no trust entry. `plugin + project` has no Codex mechanism, so it is refused by name, naming the three cells that exist, before anything is written. It is never quietly ejected instead. The same refusal runs when a config is read: `compile`, `edit` and `update` refuse a configuration asking for a cell its host does not offer, so a `.agents-inc/claude/` copied to `.agents-inc/codex/` is caught rather than acted on.

**Sixteen of the eighteen sub-agents compile, as Codex agent role definitions in TOML.** Each role is written to `.codex/agents/<name>.toml` in a project, or `$CODEX_HOME/agents/` globally, and carries `name`, `description` and `developer_instructions`. `effort` travels as `model_reasoning_effort`, and a sub-agent granted no `Bash` gets `[features] shell_tool = false`, the one per-agent limit Codex can express. `agent-summoner` and `skill-summoner` are left out for v1 because their roster mechanics on Codex are not proven. Every shipped stack lists both, so every Codex install says so.

**A role file carries no `model` line.** Every model a sub-agent can name is a Claude selector. Codex registers a role naming `opus` and then refuses to spawn it on a ChatGPT account, so each sub-agent runs on your Codex session's model. Six settings have no Codex expression at all: Claude models, tool allowlists, `permissionMode`, `isolation`, `experimental` and preloaded skills. Codex drops a whole role file over one key it does not know, so the renderer omits them, and an omission nobody is told about is a setting that silently stopped applying. So each compile says it once, rather than once per sub-agent.

**What Codex cannot do:** install a plugin for one project; restrict a sub-agent's tools (`tools` is a configuration struct, not an allowlist, so the read-only sub-agents can still edit files); preload a named list of skills; or carry a sub-agent's `disallowedTools`, which is dropped without a mention (no shipped sub-agent declares one).

**The editor's output preview draws the Codex tree**: role TOML under `.codex/`, project skills at `.agents/skills/`, and no file for the two summoners. It uses the same renderer the CLI installs with, so the preview can be diffed against a real install. The docs site gains a `configuration/providers` page.

### CLI-893 — a Codex project install writes its own trust entry, and says what it wrote

Codex reads a project's role files only while the user's **global** `$CODEX_HOME/config.toml` holds `[projects."<exact absolute path>"]` with `trust_level = "trusted"`. Each of the four ways that fails is silent: no entry; `trust_level = "untrusted"`; a trailing slash on the path; or the entry written in the project's own `.codex/config.toml`, which Codex refuses as self-authorisation. An untrusted Codex project install is half live: its skills reach the model and its sub-agents do not.

So the install writes the entry and prints the project, the file and the line it added. This reverses the earlier design, in which the CLI only printed the line for you to add. It is the owner's ruling of 2026-09-26: _"it should be automated on install"_. Any `compile` that finds role files in the project's `.codex/agents/` does the same. The file is merged, never rewritten: an existing `[projects."<dir>"]` table gains the key rather than a duplicate table Codex would refuse to parse. A `trust_level` you already set for that path, `"untrusted"` included, is left as you set it and reported. A project already trusted is told nothing.

`trustCodexProject` in `src/cli/lib/hosts/codex-project-trust.ts`, held by `hosts/__tests__/the-codex-host-writes-project-trust.test.ts` and, against the pinned binary, `e2e/lifecycle/codex-agent-roles-are-read-by-codex.e2e.test.ts`.

### `doctor` gains a `Layout` row and a `Placements Offered` row

**`Layout`, one row per scope**, reports which folder the scope is on, whether both folders are on disk and which of the two is being read, and any compiled sub-agent whose own prompt names the folder this installation does not use. At `$HOME` it also lists the registered projects still on the old name, labelled as the registry rather than as an inventory of the machine. A scope on `.claude-src/` alone is a warning naming the move by hand, not a failure.

**`Placements Offered`** reports the two states other commands stop on: a configured skill asking for a placement its host does not offer, and a scope holding an installation of each provider. Until it existed, `doctor` pronounced a clean bill of health on a configuration no other command would touch. It reports and never refuses.

### On Claude Code, `init` and `compile` say when a project's completion gate cannot run

0.163.0 gave every writing sub-agent a `Stop` hook that runs the project's typecheck. Claude Code registers a **project** sub-agent's frontmatter hooks only in a folder whose trust dialog the user has accepted, which is `projects[<project>].hasTrustDialogAccepted` in `~/.claude.json`. Otherwise the sub-agent and its prompt load and the hook is dropped. Claude Code logs that only to its own diagnostics.

So `init` and `compile` print one line naming the folder when every one of these holds:

- the provider is Claude;
- the run is not from the home directory;
- a compiled sub-agent in `<project>/.claude/agents/` has a `hooks:` line with at least one hook under `Stop` or `SubagentStop`;
- `~/.claude.json` has no accepted trust dialog for that exact path.

That covers the writing sub-agents' typecheck gate and any sub-agent declaring a stop hook of its own. A run from the home directory says nothing, because Claude Code trusts `~/.claude/agents/` unconditionally. The CLI reads `~/.claude.json` and never writes it: accepting the dialog is yours. `claudeCompileNotices` in `src/cli/lib/hosts/claude-project-trust.ts`.

## Changed

### A new installation's source folder is `.agents-inc/<provider>/`

**New installs write `.agents-inc/claude/` instead of `.claude-src/`, at both scopes**: `<project>/.agents-inc/claude/` and `~/.agents-inc/claude/`. The folder is named for the product and grouped by provider, so a Codex installation is `.agents-inc/codex/` with the same shape.

**Nothing in the CLI moves an existing installation.** An installation on `.claude-src/` is read **and** written where it is, by every command, indefinitely. There is no dual-write, no copy on first run, and no deprecation warning that changes where bytes land. `sourceFolderInUse` prefers whichever folder holds a `config.ts`. Every message naming the config file names the folder the scope is actually on, rather than a constant.

**Moving a folder is a manual step and there is no command for it.** The procedure is in `.ai-docs/reference/concepts/source-folder-layout.md`, along with its two real gotchas. First, `config-types.ts`'s relative import gains a level, which `npx agents-inc compile` in the moved scope repairs. Second, a `.gitignore` with a bare `.agents-inc/` rule hides the moved config, so the next commit records only the deletion.

**`init`, `edit`, `compile`, `update` and `eject` refuse outright while a scope holds both folders.** The folder the resolver prefers can be the stale one, so writing into it would leave your own sub-agents in the other. The refusal names which folder is being read and asks you to merge by hand, because nothing merges them. `doctor` and `list` keep working in that state, because they are what you look at it with.

**Installed output keeps every path it had.** Claude still installs into `.claude/`, skills into `.claude/skills/` and compiled sub-agents into `.claude/agents/`. A shared payload names no source folder, so the rename reaches no share id.

**A marketplace source repository gains no provider segment.** A repo declares itself in `.agents-inc/config.ts`. One still declaring `.claude-src/config.ts` is read there with no sunset, because the CLI can never move a folder in a repository it only reads, and an author who moved it would break every consumer on an older CLI.

**`uninstall` removes the `.agents-inc/` parent** once the last provider folder under it is gone, and only when the parent is otherwise empty. A repository keeping its own state under it keeps it, and the run prints `Kept .agents-inc/ (contains user content)` rather than leaving the directory behind without a word. A scope on the legacy name has no such parent to remove.

### A compiled `agent-summoner` names the folder this installation uses

The summoner's playbook tells it where to author a consuming project's own sub-agents. That folder is now substituted at compile time (`@@SOURCE_FOLDER@@`, with `\@@SOURCE_FOLDER@@` as the escape that keeps the token literal), so a copy compiled for a `.claude-src/` installation and one compiled for `.agents-inc/claude/` each point at the folder their own installation reads. `doctor`'s `Layout` row flags a copy that names the other one.

### `uninstall` counts what it observed, on either host

The plugin count is now the plugins the host was seen to remove, rather than the plugins the plan asked about. On Codex, `plugin remove` exits 0 with the same output for a plugin that was never installed, one that really went and one removed twice, so a count built from the plan said `Uninstalled 1 plugin` for a plugin it never touched. On a machine with no host binary, the count is zero rather than a clean sweep nothing performed. The directory is still deleted and the uninstall still completes.

## Fixed

### CLI-895 — Codex: an ejected skill's copy is deleted from the folder Codex reads

`deleteLocalSkill` and `migrateLocalSkillScope` in `src/cli/lib/skills/local-skill-mover.ts` joined Claude's `.claude/skills` to the scope root, while the copy side already resolved the provider's own skills directory. On Codex that meant three things. Switching an ejected skill to plugin registered the plugin and left the ejected copy, so Codex read the skill twice. Deselecting an ejected skill in `edit` left its copy. Moving one between scopes copied it into a folder Codex never reads. Both mover functions now resolve `resolveInstallPaths(dir, scope).skillsDir`. Found by the new Codex edit-wizard lane before this release shipped. The two cases it had pinned as `it.fails` in `e2e/interactive/codex-edit-wizard-plugin-operations.e2e.test.ts` are unpinned and pass.

### CLI-896 — Codex: `uninstall` removes the role files it compiled

A project `uninstall --yes` left `.codex/agents/*.toml` in place while reporting `.codex/agents/` removed. The agent lister globbed `*.md` and read Claude's provenance marker, so on Codex it found no compiled agent at all. `listAgentFilesOf` and `splitAgentsByProvenance` now take the provider's agent codec. `uninstall`, `doctor`'s orphan check and `compile`'s stale-role prune all pass it, the last because a deselected Codex role had survived a recompile the same way. A role you wrote yourself is left alone, as `.claude/agents/*.md` is on Claude. Found by Codex running the end-to-end check itself, before this release shipped.

### CLI-898 — the editor's preview shows the skill description the install writes

On both hosts, the preview listed each skill with the catalogue's `description`, which is the wizard's short label ("Lightweight client state"). The install wrote the skill's `SKILL.md` description ("Zustand stores, client state patterns. Use when…"). They are two different fields, not drift. So every skill stating a short label previewed differently from what landed on disk. `build marketplace` now carries the `SKILL.md` description into `catalog.json` as `activationDescription`, and the preview prefers it. A catalogue built before this release falls back to the label, so the live editor shows the right text once the public marketplace's `catalog.json` is rebuilt with this CLI.

### CLI-899 — the loading spinner's last frame no longer survives into the wizard

Sometimes a spinner glyph was left above the wizard's first line, which pushed the full-height wizard's top line off the screen. Ink's render throttle holds a frame that arrives inside its window. `clear()` erased the last frame Ink had painted, and `unmount()` then painted the held frame after it, with nothing left to erase it. It took an event-loop stall bunching two ticks. `awaitUnderSpinner` in `src/cli/components/common/spinner.tsx`, now used by `init` and `edit`, freezes the spinner to a still line, waits for the render to flush, then clears and unmounts. `spinner.test.ts` reproduces the stray glyph on a headless terminal. The test tolerance added earlier the same day to let the e2e suite pass over it is gone, and the spec is strict again.

### `compile` no longer refuses an installation with sub-agents and no skills

The editor makes one ("no skills — base agent") and `init --from` installs it. `compile` then printed `No skills found … skipping` and exited 1 having recompiled nothing, so a hand edit to its `config.ts` never reached the compiled sub-agents. `init` had never refused this. `declaresOnlyBaseAgents` in `src/cli/commands/compile.ts` now lets a pass that finds no skill compile its sub-agents, but only when its config declares no active skill and turns a sub-agent on at that scope. A config that **declares** skills, none of which are on disk, is an installation whose skills were lost. It is still refused, so `compile` never rewrites every sub-agent without them.

### `edit --from` applies a configuration that only retunes a sub-agent

A shared configuration whose only difference from the installed one was a sub-agent's `model` or `effort` read to `edit --from` as no change at all. It printed `No changes made.` and wrote nothing. The receiver believed they had applied the sharer's configuration, and the sub-agent went on running as before. The diff now carries `tuningChanges`. A retune is written to `config.ts` and the compiled frontmatter, and reported as its own line: `~ web-developer (agent: defaults → model haiku, effort high)`. That line exists because a retune moves no file, so a run without it reports a heading with nothing under it.

In the same wizard, re-selecting a sub-agent whose global install the project had tombstoned rebuilt its project/global pair from scratch and reverted its model and effort. The pair now keeps the tuning of the row you were looking at (`tuningOf` in `src/cli/stores/wizard-store.ts`). The domain and stack rebuilds of the roster already kept both fields. Their specs are regression guards rather than fixes.

### A local marketplace directory whose path contains a space reaches the host

`validateMarketplaceSource` held every marketplace source to the reference pattern written for `owner/repo` and `github:org/repo`, which admits no space. So under `/Users/My Name` a marketplace directory was refused before it reached `claude` or `codex`, neither of which objects to one. A source naming a directory on this machine (an absolute path, or one opening `./` or `../`) is now held only to the length limit and the control-character refusal. A reference keeps the pattern. The pattern guarded against nothing reachable: `execCommand` spawns with an argument vector and no shell. `namesADirectoryOnThisMachine` in `src/cli/utils/exec.ts`, held by `hosts/__tests__/a-marketplace-directory-with-a-space-reaches-the-host.test.ts`.

## Removed

Nothing that shipped in 0.164.0 is removed. Two things built during this cycle were withdrawn before release, and are recorded here so they are not rebuilt:

- **`npx agents-inc migrate`.** A command that moved `.claude-src/` to `.agents-inc/claude/`, with `--adopt`, `--dry-run`, a forwarding stub at the old path, a registered-project rewrite and a git-visibility probe. It was never requested and is deleted whole. Nothing in the CLI hands out the invocation.
- **The per-agent lint and check gate** (per-agent lint hooks, the `check:` map, the Codex gate plugin and its hook trust) was reverted before release on the owner's 2026-10-01 ruling, CLI-715 is retired rather than built, and 0.163.0's typecheck `Stop` hook is unchanged.
