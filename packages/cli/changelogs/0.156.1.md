# Release 0.156.1 (2026-08-20)

A test helper that walked the long way round, and the standard that had blessed the number it walked to (CLI-595)

**No shipped code changed in this release.** Nothing under `dist/`, `assets/`, `src/agents/` or `src/schemas/` moved, so the published tarball is identical to 0.156.0's. The work is in the end-to-end harness and in the documents that describe it, and the version exists so the tree, the registry and the changelog agree on a boundary.

It is worth a release note anyway, because the defect had been shipping green. A red CI build on a commit that changed nothing relevant is the kind of thing a suite absorbs quietly — this one had been absorbing it for as long as the taxonomy has had 33 categories.

## Fixed

### CLI-595 — the focus walk looks before it presses

`BuildStep.focusSkill` drove the build grid by pressing Tab and then reading the screen, inside a fixed budget of 50 presses. Two defects fell out of that order, and only the second ever showed up as a red build.

**It pressed before it looked.** The unconditional first press was deliberate — arriving in a category via Tab is what resets the grid column to 0, so the RIGHT presses that follow have a known base. The cost was that the helper walked off a target that was already focused. Against the default catalogue the web domain paints 33 categories and `web-framework` is category 1 of 33, so a spec asking for a skill in the first category — the one focused on entry — paid a full 33-press lap to return to where it started.

**A press was assumed to have landed.** After each Tab the walk waited briefly for a fresh frame and then read whatever was on screen, tolerating a miss. Under runner contention the repaint arrives after the read, so the walk looks at the category it just left while standing on the next one, and passes its own target unseen. The second lap it then needs does not fit in what remains of the budget, because the first lap consumed 33 of 50.

The arithmetic in the failure is exact: CI run 32338714325, `edit-wizard-navigation.e2e.test.ts > should toggle focused skill scope with S key`, failing both attempts — 50 presses from category 1 lands on category 18, and category 18 is `Error Handling`, the highlighted header in the dump. A re-run of the same commit passed with that test still losing its first attempt and winning on retry, so roughly three attempts in four were failing on the runner and `retry: 1` was absorbing it. Not reproducible locally under any condition tried, including the full 229-file suite pinned to the runner's four cores, the same under eight CPU hogs, and `e2e/interactive` pinned to two.

`focusSkill` now reads the focused category first and walks only when the target is elsewhere. `advanceCategoryFocus` re-presses until the screen SHOWS a different category focused, so no category is passed while its repaint is in flight — which is what makes one lap sufficient. The column base is stated rather than assumed: `0` when the walk arrived by Tab, the tracked `gridCol` when it never moved, both stepped through one `pressRightToColumn`.

## Removed

- **`MAX_FOCUS_ATTEMPTS`.** The walk now terminates on the structure it is walking — it stops when it observes a category it has already seen, which is one real lap with every category looked at exactly once — and raises `CategoryWalkError` carrying the categories walked. A press budget reports the number it gave up at, which says nothing about what it looked at; it was never the mechanism, only the thing that ran out.

## Changed

- **`TerminalSession` records what a helper spends.** A keystroke ledger, exposed through `BaseStep.keystrokes()`. Every existing assertion about focus reads where focus ENDED, and a walk that arrives by touring the whole grid satisfies all of them — so the cost of a navigation helper had no observable at all, and that is what let this sit. `e2e/interactive/build-step-focus-walk-cost.e2e.test.ts` pins both halves of the repair: zero Tab presses when the target category is already focused, and one lap when the label is nowhere.
- **`standards/e2e/anti-patterns.md` no longer teaches its own counter-example.** `MAX_FOCUS_ATTEMPTS` was this section's worked example of a well-commented numeric bound — raised from 30 to 50 and re-commented exactly as the section prescribes — and it produced a red build anyway. The comment was accurate and the number was still wrong, because the bound was the wrong shape. That is now written where the example stood. `SOURCE_ROW_WALK_LENGTH` survives as the example, with CLI-497 named against it for being fixture-sized rather than left implied.
- **`standards/e2e/page-objects.md` and `reference/testing/e2e-infrastructure.md`** re-describe the algorithm — look first, confirm each press against the frame, terminate on a lap — and both record that `MAX_FOCUS_ATTEMPTS` no longer exists, so neither sends a reader after a deleted constant.

Inert today: `getSkillBySlug` has zero product call sites and `idToSlug` has zero readers anywhere. Armed for the first one.

## Proposed standards

Both are carried by CLI-595 and neither is written into a standards document yet.

1. **A navigation helper observes before it acts, and confirms each move before the next one.** A helper that presses and then reads cannot distinguish "the key did not land" from "the repaint has not arrived", and it silently walks past what it was sent to find. This extends the existing rule — never add a key-press method to an E2E step page object without calling `waitForWizardFooter()` first — from _a frame is painted_ to _the frame says the press took effect_.
2. **A press budget is not a search bound.** Terminate on the structure being walked — a lap, a repeat, an exhausted list — and raise an error naming what was observed. A magic N also expires silently: this one was raised when the taxonomy grew to 33 categories, and was already too thin for the two laps a single missed observation requires.
