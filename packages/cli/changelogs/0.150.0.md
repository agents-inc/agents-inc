# Release 0.150.0 (2026-08-04)

The CLI is published as `agents-inc` — one package where there were two

## Changed

### `agents-inc` is the package now, and `@agents-inc/cli` is deprecated

Until this release the CLI shipped as `@agents-inc/cli`, and `agents-inc` was a separate three-line package whose entire body was `import "@agents-inc/cli"`. It existed so that `npx agents-inc init` — the command promoted in the README, in the CLI's own messages and on agentsinc.sh — worked without anyone having to type the scope.

Those two are now one. `agents-inc` carries the CLI itself; `@agents-inc/cli` is deprecated and points at it.

**For almost everyone this is invisible.** `npx agents-inc init` does exactly what it did, minus one resolution hop. The binaries are unchanged — `bin` still registers both `agents-inc` and `agentsinc`, so a global install answers to either spelling. Nothing about how skills, agents or configs are stored moves: `DEFAULT_PLUGIN_NAME` is still `agents-inc`, so every `<skill>@agents-inc` reference in an existing install is untouched, and the `$schema` addresses written into generated metadata are unchanged.

**`@agents-inc/cli` keeps working.** Deprecating a package on npm does not remove it. Anyone already depending on it still installs it, and still gets the version they asked for — they will see npm's deprecation notice pointing here.

**A hand-written config that imports `@agents-inc/cli/config` still loads.** The current spelling of that import is `agents-inc/config`, and it is the one to use from now on, but the loader accepts both. This matters for exactly one shape of file: a `.claude-src/config.ts` written by hand against the documentation, importing real values — `defaultStacks`, `defaultCategories`, `defaultRules`. Anything `init` generates is unaffected either way, because generated configs import their types from the sibling `./config-types` with a relative path and never name the package at all.

The old spelling is a bridge rather than a fixture. It is recorded as REPO-24 in `todo/repo.md` and will be removed once the old package's downloads have stopped.

### Why collapse them

The alias was not free. `npx` caches by package spec: it resolves `agents-inc` to a version, and if that version is already in the cache it reuses the whole cached install — including the `@agents-inc/cli` that install resolved the first time. So an alias whose version number never moved would pin every repeat `npx agents-inc` user to whatever CLI build they happened to pull first, indefinitely.

The guard against that was a manual step: republish the alias at the matching version on every single release. It failed exactly as designed to fail — invisibly. 0.147.1 was tagged in the changelog, the alias shipped at that number and the CLI did not, and the `validate` fix in it reached nobody until 0.148.0 superseded it. A release could look correct from every angle — package published, changelog written, fresh machine works — while returning users ran last month's build.

One package cannot fall out of step with itself. The release checklist in `.ai-docs/standards/commit-protocol.md` loses the lockstep rule and the section explaining it, and is now one bump and one `npm publish`.

## Removed

- `packages/cli/alias/` — the alias package, its `package.json`, its `bin/run.js` and its README.
- `publishConfig.access: "public"` from `package.json`. It was doing real work while the package was scoped, since npm publishes scoped packages privately unless told otherwise. Unscoped packages are public by default, so the field is now a statement with no effect. The `registry` entry beside it stays: that one still decides where `npm publish` sends the tarball.

## Fixed

### The root of `node_modules` now says which React it holds

This is internal to the repository and changes nothing about the published package, but it is the reason the rename was not a one-line change.

The repository deliberately runs two Reacts: the CLI draws its wizard with Ink 5, which needs React 18, and the web half is on React 19. Bun installs a flat `node_modules`, so exactly one of them wins the root slot and everything without a nested copy of its own resolves to whichever that is. Ink declares React as a **peer** dependency, so it never gets a copy of its own — it takes whatever is hoisted.

That the hoisted copy was React 18 had never been decided. It was a side effect of the workspace being called `@agents-inc/cli`, which bun resolved ahead of `editor` and `@workspace/ui`. Renaming it to `agents-inc` moved it behind them, handed the root slot to React 19, and left Ink rendering against one React while the CLI's components used another. Every Ink render died — 353 unit tests, with an error about React children that names nothing to do with any of this.

The root `package.json` now declares `react` and `@types/react` at 18 and imports neither. They are there to hold the slot on purpose rather than by accident. `.syncpackrc.cjs` carries a narrow version group so that pin is not reported as version drift. Both are scaffolding for the version split and are listed with the other workarounds in REPO-06, to be deleted when the two halves finally agree on a React.
