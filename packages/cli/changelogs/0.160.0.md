# Release 0.160.0 (2026-08-25)

A category is no longer required, a mixed installation counts what it declares, and two rows close by being refuted rather than fixed (CLI-822, CLI-823, CLI-824, CLI-826, CLI-827, CLI-828, CLI-829, CLI-830)

**The recurring shape of this release is a defect that outlived its own fix.** CLI-822 was reported landed twice while a scaffold still taught the removed field to new marketplace authors, and a page-object regex still carried an optional match for the deleted marker — green forever, invisible to `tsc` and to every test run. CLI-828 was filed as cosmetic and its real value was catching that the pass before it had broken the rule it had just written. CLI-827 and CLI-830 close without a code change at all: one was refuted on evidence measured against a single TypeScript project where two exist, the other is a documented refusal proved in both directions. Every one of these was found by an agent re-deriving a claim rather than by review.

## Changed

### CLI-822 — a category is no longer required, and the wizard stops saying so

The required-category concept leaves the product entirely. Deleted: `validateBuildStep` and `BuildStepValidation`, `TOAST_MESSAGES.ONLY_SKILL_IN_CATEGORY` and its `STEP_TEXT` mirror, `SYMBOL_REQUIRED` and the `*` it painted on category headers, the `exclusive`-and-`required` deselect guard in `toggleTechnology`, and the `required` field on `CategoryDefinition`, `CategoryRow` and `CatalogCategory` together with the three Zod schemas that admitted it.

**The reported symptom was never a block.** `handleContinue` called `onContinue()` unconditionally and a test pinned "continues anyway", so the toast only ever read as a refusal. That is why this is a deletion rather than a guard change — and it reverses the deliberate warn-and-allow decision taken under CLI-367, on the ruling that the objection is to the concept rather than to its severity.

Scope reached further than the CLI. `required` was **generated data**, so `bun run generate` rewrote `types/generated/matrix.ts` and both vendored copies in `packages/matrix`, behind the `generate:matrix:check` gate. The editor reads none of it: `CatalogCategory.required` was written by the read model and read nowhere, so no editor behaviour moves.

Two defects outlived the first two "landed" reports, and neither was found by review. `skillCategoriesModule()` in `lib/marketplace-scaffold.ts` was still emitting the dead field into the `skill-categories.ts` it scaffolds for **new marketplace authors** — type-checking and parsing cleanly, because `z.object` strips unknown keys silently — and was found by a documentation agent re-deriving an unrelated count. And `getExclusiveCategorySelectedCount` in `e2e/pages/steps/build-step.ts` carried `\s*\*?\s*`, an **optional** match for the marker that had just been deleted; an optional match for something that can never appear is green forever.

### CLI-829 — an assertion binds to the constant that governs its own data

Two rules, both learned by getting them wrong in one pass. **Same value is not the same concept:** binding `SKILLS.react.id` inside a spec fed by a different fixture family trades a stale-literal vacuum for a **diverged-constant** one and is strictly worse, because it reads as rigorous while asserting nothing. **And a rendering assertion keeps its literal:** an assertion importing the very constant the component renders cannot fail when that constant changes, which is why `e2e/pages/constants.ts` mirrors the product's strings rather than importing them.

The separator is what makes the rule usable: bind when the literal names a **symbol** whose deletion should break the test, because deletion is then a compile error; keep the literal when it is **text the product renders**. Eight proposed conversions were stopped by this, each of which would have introduced the defect the pass was removing.

## Fixed

### CLI-823 — a mixed installation counts the skills its configuration declares

`countInstalledSkills` branched on `mode === "plugin"` and otherwise counted skill **directories**, so `"mixed"` fell to the eject-only arm and plugin skills were never counted. The published 0.159.0 binary printed `Skills: 2` over a configuration declaring eleven.

`countInstalledSkills`, `countPluginSkills`, `countDistinctSkillIds` and `sumOverScopes` collapse into one `countManagedSkills` — non-excluded `config.skills`, deduplicated by id — and install mode is no longer consulted. A skill present on disk but absent from the configuration is not counted; one declared at two scopes counts once.

**`list` already contained the right answer.** Its interactive branch had always filtered `config.skills` on `!excluded`, eleven lines above the piped branch that contradicted it, with nothing comparing the two paths. What prevents recurrence is the test shape rather than the fix: both surfaces are now driven over one fixture against one named constant.

### CLI-828 — the positives beside the bound negatives, and the bindings that had diverged

Filed as cosmetic and treated that way: a **positive** assertion on a stale literal fails loudly, so it cannot rot the way a negative one does. Of 246 candidates, 8 converted and 238 were left — 149 because they are text the product renders, 35 generated-source fragments, 30 with no constant to bind to, and **20 under the rule above**, where the only same-valued constant does not govern that test's data.

Its real value was catching that the earlier negative-binding pass had itself broken that rule at nine sites across seven files — the assertion bound while the fixture kept a hardcoded id. All nine were resolved, and the split is the lesson: two files took the **bind-the-data-too** outcome, so one constant now drives mock, config, stack and assertion alike; five took the **revert** outcome, because `buildSkillConfigs<Id extends string>` is generic over `string` and binding their data buys no compile error.

One genuinely vacuous assertion went with it: `toContain("web-styling")` sat beneath `toContain(SKILLS.tailwind.id)` and passed on the skill id alone, so it could not tell whether the message named the category at all.

### CLI-824 — two E2E specs describe behaviour that exists

A comment in `init-wizard-scratch.e2e.test.ts` claimed a Framework skill must be selected before advancing. Nothing requires a selection to advance — `StepBuild` handles Enter as `if (key.return) { onContinue(); }`, unconditional and with no selection count in scope — and `init-wizard-stack.e2e.test.ts` disproves it directly by advancing to the API domain while asserting `(0 of 1)`. The claim was false before the required-category removal too.

`edit-wizard-unique-skill-guard.e2e.test.ts` becomes `edit-wizard-skill-deselection.e2e.test.ts`. Its two tests are kept, not deleted: they are the only **project-scope** coverage of "one of two selected skills removed, the other survives" and "an exclusive category emptied to zero", where the nearest siblings cover both at global scope and the project-scope sibling seeds a single skill. It had no journey row — it sat in the `spec-gates` backlog, which may only shrink — and now has one on journey 9 beside those siblings.

## Removed

### CLI-826 — a fixture generator's dead return member and a silent no-op option

`TestMatrix`, `TestSourceOptions.matrix` and the `testMatrix` return member are gone from `__tests__/fixtures/create-test-source.ts`, along with what fell unreachable with them. **Zero** of the `createTestSource(` call sites ever passed `matrix:`, so a future test passing it to shape a fixture's source would have been silently ignored. `TestMatrix` was also exported with no out-of-file consumer.

The same pass typed what that generator emits. The load-bearing detail is not the variable's type: `Object.fromEntries` launders literal freshness, so the annotation on the `.map` callback is what makes each entry a checked literal — measured, because without it a stale field still compiles clean. `renderCategoriesTs` had zero callers and is deleted; `renderRulesTs` is typed to the schema it emits; `renderConfigTs` deliberately stays `Record<string, unknown>`, being a generic serialiser across 46 call sites, several of which pass invalid objects on purpose.

## Proposed standards

### CLI-827 — refuted: the factory was already correct

Filed as an unconstrained generic breaching the narrowest-union rule. It is that rule's **exception**, and the rule's silence about it is what produced the row. `buildSkillConfigs<Id extends string>` serves both the public catalogue and fixture marketplaces, whose ids come from `e2eSkillId` and are deliberately typed `string` — "casting it into one would be a lie about the catalogue". Both escapes are closed: casting namespaced ids into `SkillId` is the forbidden act, and substituting catalogue ids makes `refuseCatalogueCollisions` refuse the fixture marketplace whole.

**The row's evidence was measured against one project of two.** `tsc --noEmit` reports 6 errors in 1 file; `tsc -p e2e/tsconfig.json` reports 83 across 31. `packages/cli/CLAUDE.md` now carries the exception, the docblock test for identifying one, and the instruction to measure both projects before filing.

### CLI-830 — a documented refusal, proved in both directions

The custom matchers keep `string` parameters, and the reason is written above `declare module "vitest"` so the row cannot be re-filed on a partial measurement. The skill matchers reproduce CLI-827 exactly. **The agent matchers fail for a different reason, and that asymmetry is the find:** agents are not namespaced, and narrowing leaves six sites in one file, all a **user-authored** agent that `loadAgentsFromDir` accepts through the schema's `z.string()` base, in a spec asserting it compiles successfully — neither a parse boundary nor error-path data, so the cast is unlicensed and `AgentName | string` collapses to `string`.

Mutation-proved both ways: four plausible-but-wrong values at live call sites — a slug, two display names, a one-letter typo — are met with complete `tsc` silence under `string` and all four error under the narrowing. So both the hole and the unavailability of the remedy rest on measurement rather than on argument.
