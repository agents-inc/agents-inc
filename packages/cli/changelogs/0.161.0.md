# Release 0.161.0 (2026-08-30)

The renderers leave the CLI for a package both front doors call, an install's config arrives already formatted, and the worker gets one typed client (EDITOR-52, SERVER-02)

**The recurring shape of this release is a boundary that moved and nearly left its guards behind.** The renderers crossing into `packages/compile` would have unbound an `eslint` import ban that matches on the specifier — no directive involved, and `reportUnusedDisableDirectives` cannot see a pattern that matches nothing. `packages/api` arriving would have left `dist-staleness.ts` reading a stale `dist` as current, because `BUILD_INPUT_TREES` did not scan the new tree. A re-export facade left three test helpers parsing an emission format that had changed underneath them. In every case the guard was found by re-deriving a claim against the tree rather than by review, and two of them announced themselves by going red the moment the workspace appeared — which is the tripwire working rather than a defect.

## Added

### `generate:compile` — a fourth generator, and the drift step that holds it

`bun run generate:compile` writes `packages/compile/src/generated/corpus.ts` — 90 markdown partials and 7 Liquid templates — and `generate:compile:check` byte-compares it in CI beside `generate:schemas:check` and `generate:matrix:check`. The corpus is **generated** into the package rather than copied, with the same runner shape as the other three, so a template edit that lands without a regeneration turns the commit red instead of leaving the editor's preview drawing bytes no install writes.

`bun run generate` now runs all four in dependency order.

## Changed

### EDITOR-52 — the renderers leave the CLI for a package both front doors call

The pure config-pair and compiled-agent renderers move out of `packages/cli` into a new workspace, `@workspace/compile`, and **the CLI's own writers call it** — that was the acceptance criterion rather than a follow-up, because a shared package the editor imports and the CLI does not is client-side reconstruction with a `package.json`. `config-generator.ts`, `config-types-writer.ts` and `config-writer.ts` lose 2,141 lines between them; `config-writer.ts` is now a re-export facade over `@workspace/compile/config-source`.

**Verified by imports rather than by intent.** `pair-writer.ts` reaches `generateConfigSource` through that facade, and `e2e/lifecycle/preview-matches-install.e2e.test.ts` proves it at runtime by byte-comparing a real PTY-driven `init` against the package's own renderers.

The `no-restricted-imports` group moved with the symbols, and had to: the rule matches on the import specifier, so the extraction would have stopped it firing with nothing to signal that. Both specifiers are named — the package's subpath and the CLI's own re-export — because a re-export would otherwise be the bypass, and the subpaths are named rather than the package, because a rule refusing `@workspace/compile` outright would ban the extraction it exists to permit.

**Carried forward rather than closed:** nothing mechanically holds the editor's preview and the CLI's writers to the same answer for every input. Both were diffed by hand against a real install and `preview-matches-install` pins one journey, but neither suite can reach the other's fixtures.

### The emitted `config.ts` and `config-types.ts` are formatted at the source

Owner ruling: the two files an install writes must arrive already formatted. They are a prettier fixed point now under `semi: false, singleQuote: true, printWidth: 100, trailingComma: 'all'` — settings matching **neither** repository config, deliberately, because these bytes land in a user's project and `.claude-src/` is prettier-ignored here. So `"origin":"eject"` in a written config is `origin: 'eject'` from this release on. Both parse; the round-trip and byte-stability specs cover the change rather than describe it.

**No runtime formatter.** Prettier is a devDependency and tsup bundles those, so calling it from the renderer would have inlined the TypeScript parser into the published CLI and into the editor's preview chunk. One printer — `packages/compile/src/installed-format.ts` — replaced three serialisation styles that had coexisted in one file: compact `JSON.stringify` per entry, `JSON.stringify(value, null, 2)` for the stack, and hand-assembled template strings. Two member-count thresholds in the types half became one width rule.

**The spec was a fixed-point test, never a literal** — `expect(emitted).toBe(reformat(emitted))` — so it could not be satisfied by pasting whatever the emitter already did. 14 red across 6 scenarios × 2 files plus both blank emitters, and the tester corrected the brief by finding the second blank emitter.

A real defect the scenarios could not see was found by probing after green: a string value too long to sit beside its key was not a fixed point, and the membership is not guessable — a string, `null`, an empty array and an empty record move below the key, while a number and a boolean stay on the line however far past the width they run. A seventh scenario pins both sides of that edge.

Three test helpers turned out to **parse** the emitted config and all three broke. One matched double-quoted literals only and would have returned `[]` for every union, passing vacuously. A guard already in the tree caught the change exactly as its author intended, its comment reading "a format change would satisfy the negative for free".

### SERVER-02 — one typed client, and what it cost

`packages/api` is the one home of the `hc<AppType>` client both front doors reach the worker through, and `src/cli/lib/seed/fetch-seed.ts` stops hand-writing its fetch for `GET /configs/:id`.

**Owner ruling, overturning an earlier lane's argument the day it was made.** That round declined the package because sharing it would put `hono/client` into the published bundle for one GET. Measured rather than estimated, which is the point of recording it: the CLI's published JS went 1,755,475 → 1,765,345 bytes — **+9,870 bytes, +0.562%**. Re-derivable with `find dist -name '*.js' -not -name '*.map' | xargs du -cb | tail -1`.

Three things the new workspace owed that `deps:check` does not ask for, two of which announced themselves. `check-shared-tsconfig.test.ts` compares an exhaustive workspace list with `toStrictEqual` precisely so an arriving workspace goes red rather than defaulting, and it did. `dist-staleness.ts`'s `BUILD_INPUT_TREES` did not scan `packages/api/src`, so a `dist` built before an api change would have read as current; adding it immediately failed the suite until a rebuild, and its fixture had to learn the new tree. And tsup's `noExternal` did not name the package — it was being inlined **incidentally**, and promoting it to `dependencies` would have silently externalised it and broken `init --from` in the published CLI, which is the exact failure the note beside that list already described for `@workspace/matrix`.

## Fixed

### One description of the worker, and the no-op it was hiding

The CLI's network mocks resolve the same `packages/api-mocks` handlers the editor's two suites read. The unit suite goes through `msw/node` — `stubGlobal("fetch")` in `src/` is down from 6 to 1 — and the e2e suite through a real `node:http` server resolving those handlers via new `workerRequestFrom` and `answerFor` exports. **Injecting `NODE_OPTIONS` into the child was ruled out rather than overlooked**: the e2e suite deliberately spawns `bin/run.js` with a user's environment, and mocking the network away is the opposite of what an e2e that spawns a binary is for.

`packages/api-mocks` gained `seedPayload()`, `defaultHandlers`, and `entry-points.test.ts` — a gate that makes `msw` unloadable and asserts `./fixtures` still resolves, so the msw-free entry point is **held** rather than described. Coupling is proved in both directions: changing a status in `handlers.ts` reddens a CLI unit spec, and changing a body constant in `fixtures.ts` reddens a server spec.

**The migration introduced a defect that three lanes missed and a green suite could never show.** `stubWith` filtered against `network.listHandlers()`, which msw seeds with the fixture's initial handlers — the same instances `stubSignedOut` passes — so the filter reduced them to an empty array and `use()` returned early. `stubSignedOut` was a total no-op, and its five call sites were passing on the fixture's signed-out default rather than on the helper they name. Fixed by filtering against the module's own record of what it installed, since the baseline is precisely what `use()` exists to override. Proved load-bearing in both directions with controls on each side.

**The generalisable lesson is the verifier's.** All three lanes proved their guarantees by breaking something and watching a test go red, which is the right instrument and is why their claims held; none probed the opposite direction, whether a helper that should install something can silently install nothing. **A guard whose failure mode is silence needs a test that the guard fired.**

A second correction the session made against itself: it twice stated, from the MSW docs and from `apps/server/vitest.config.ts`'s own comment, that msw cannot run in workerd. It runs — a probe inside the pool passed with `typeof WebSocketPair === "function"` in the same file proving the runtime was genuinely workerd, and it was re-run independently before being believed.
