# Release 0.147.1 (2026-08-01)

`validate` reports why parsing failed, and the ESLint baseline goes to zero

Almost all of this release is internal. The one user-visible change is that `validate` now tells you the _cause_ of a parse failure instead of only its category. The rest is the burndown of the 148-problem baseline that the ESLint gate — added in 0.146.1 and never previously able to run — exposed on first execution.

That burndown is worth reading as more than housekeeping. Of 148 problems, five marked real defects that were invisible precisely because the binding recording them was unused.

## Fixed

### `validate` reports the underlying cause of a parse failure

Two `catch` blocks in `source-validator.ts` bound the error and discarded it — in the command whose entire purpose is telling you what is wrong with your source repo. One swallowed a `YAMLParseError` carrying line and column numbers; the other lost the reason cross-reference validation was skipped.

The second was self-evidencing, a template literal with no interpolation:

```ts
message: `Cross-reference validation skipped: failed to load categories/rules`,
```

Nothing in a toolchain produces backticks for a `${}`-free string — that is the residue of a deleted `${getErrorMessage(error)}`. The same file already interpolates correctly a hundred lines earlier, so this was drift inside one file rather than a missing convention.

**Known inconsistency, deliberately not fixed here:** `validateYamlFiles` emits the same `Failed to parse YAML` message from a bare `catch {`. With no binding there is no lint signal, so it fell outside this pass. That sentence now carries a cause from one phase and not the other. It is also the more general problem — a linter can only ever see the bound-and-discarded variant.

## Changed

### ESLint baseline: 148 → 0

No rule was disabled to get there. Four inline suppressions remain, each with its reason recorded: two pre-existing `no-control-regex` for ANSI stripping, one `no-var` that must stay (`let` would throw — the binding avoids a TDZ error in circular ESM imports), and one unused type parameter in an interface augmentation where the `_` escape hatch fails to compile (`TS2428`: merged declarations match on the parameter's _name_).

`@typescript-eslint/triple-slash-reference` is now off for `**/*.d.ts`. The idiom is correct in a declaration file, and for `@lydell/node-pty` it is the only option — it ships `"exports": "./index.js"` with no `types` condition, so its declarations are unreachable through module resolution. Scoped in the config rather than suppressed at the call site, because it is true of every declaration file.

### Dead code removed from production

37 unused imports and three dead bindings, each checked for import-time side effects first. Two that looked like defects and are not: `mode-migrator.ts` importing `warn` without calling it (it collects into `MigrationResult.warnings`, which `edit.tsx` emits), and `schemas.ts` importing `SKILL_IDS` without using it (skill IDs are leniently typed on purpose — local and custom skills legitimately fall outside the generated union, with the rationale written inline).

Also removed: an `installMode` parameter its single caller passed and its body never read, and a dead Zustand subscription in `step-agents.tsx`.

### Tests now assert what they were capturing

53 unused bindings in `src/` tests and 15 in `e2e/`. In a test, an unused binding is a different signal than in production code: a value captured from a call and never asserted on means the test **ran the code and checked nothing**.

The worst was `scope-toggle-config-snapshot.e2e.test.ts` — _"should compile agent at project scope and preserve global"_ — which snapshotted **both** configs, under a comment reading `// BEFORE: Snapshot both configs`, and compared **neither**. Its two assertions were `toContain("web-developer")` on each config, and the fixture writes `web-developer` into both files _before_ the toggle runs. Both were already true of the pre-state, so the spec would have passed with the toggle keystroke silently swallowed — a documented failure mode of this harness.

Others: a spec that captured the project config and compared only the global one while running at project scope; two `doctor` runs asserting nothing about exit status, one with the missing assertion stated in English in its own comment; and an imported-but-never-called `expectCleanUninstall`, leaving its spec's "also removes skills and agents" claim unverified.

Where the intended assertion was unambiguous it was added, always matching an expectation already written elsewhere in the same file rather than invented. Four ambiguous gaps are recorded in the findings rather than guessed at — including a test named _"should preserve domain selections when navigating back"_ whose body never navigates back.

### A loose type that was licensing a rule violation

`config-assertions.ts` imported `SkillConfig` and `AgentScopeConfig`, used neither, and declared its parameters structurally instead (`scope: string`, `source: string`) — on the two most-used config assertions in the suite. Tightening them to the real types produced exactly five type errors, all in one file, all the same defect: expected agent lists built inline instead of through `buildAgentConfigs`, the factory that file's own skill assertions use three lines below. The permissive parameter was what allowed the inline-test-data rule to be broken.

### Every `any` in the repo is gone

All 38 lived in `scripts/generate-source-types.test.ts`. Each resolved to a type that already existed; 36 needed no import at all, arriving contextually through `Stack` and `Partial<ExtractedSkillMetadata>`. The casts sat on valid union members, where the literal string _is_ the type.

Two were not noise but fabrications the cast made possible. `{ id: "web-framework-nonexistent" as any }`, in a test named _"filters out invalid skill IDs not in skillIdSet"_, could not reach `resolveStack` through any type-checked path — `as any` was the sole reason it compiled, so the test asserted correct behaviour for a scenario that cannot occur. The scenario that _can_ occur is the inverse: a valid `SkillId` absent from the set, which happens whenever `defaultStacks` — type-checked against the previous generation's union — names a skill the current source no longer provides.

`VALID_IDS` is renamed `KNOWN_SKILL_IDS`: every ID reaching that function is already valid, so calling the set "valid" is what invites the next person to fabricate an invalid one with a cast.

## Proposed standards

Not yet written into the standards docs:

- Widen CLAUDE.md's cast rule to name `as any` explicitly. It currently names only `as SkillId` / `as SkillSlug` on valid union members; `as any` is the same defect and strictly worse.
- A `catch` that discards its cause in a user-facing path is a bug, not a lint nuisance to be renamed `_error`. A `${}`-free template literal is a review smell worth grepping for.
- An unused binding in a test file should be triaged as a missing assertion before it is deleted.
- A bar for `eslint-disable`: cite the compiler error or the mechanism that makes the rule inexpressible, and prefer a scoped config override when the exemption is true of a whole file class.

## Known gaps recorded, not fixed

- `validateYamlFiles`'s bare `catch {` still discards its cause (above).
- `StepBuildProps.selectedDomains` is dead API; removing it needs production and test changed together.
- Abort exit codes are unasserted across all 14 `abortAndDestroy` call sites; fixing that needs the abort moved out of its `finally` first.
- The deduplicates-agent-names test in `generate-source-types.test.ts` regex-scans generated output, which CLAUDE.md forbids.
- `eslint-plugin-react-hooks` is not installed, so this Ink/React codebase has no hooks linting at all. Two effects in `use-measured-height.ts` would be flagged if it were added; the correct response there is `useCallback` on `measure`, not widening dependency arrays.
