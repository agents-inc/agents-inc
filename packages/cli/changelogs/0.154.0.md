# Release 0.154.0 (2026-08-10)

The wizard stops reaching through the lock (CLI-470, CLI-478, CLI-479, CLI-480, CLI-481, CLI-482, CLI-483, CLI-484, CLI-485, CLI-486, CLI-487, CLI-488, CLI-489, CLI-490, CLI-491, CLI-494, CLI-495)

Every fix in this release was found by driving the published CLI against the published marketplace by hand, and every one of them was landed the same way: a test written and watched fail first, then the fix, then the real binary run by hand to confirm the output and the files it generated. The suite was green over all of these defects, which is what the round set out to correct.

## Added

### CLI-481 — a skill's category reaches the marketplace it is published to

The category a skill declares in `metadata.yaml` was dropped at the plugin-build boundary, so `build marketplace` reported every plugin as `uncategorized` and the breakdown could never print anything else. It now travels through `PluginManifest`, the manifest schema, the skill plugin compiler and the marketplace entry. Verified against the real Claude CLI: the extra `plugin.json` key is accepted and installs succeed.

### CLI-491 — a skill that reaches no sub-agent says so

Picking a project-scoped skill while every selected sub-agent is global installs the skill and assigns it to nothing — correct, because a global sub-agent may only carry global skills, but previously silent. Both the wizard and `compile` now name the skill and the pair the scope filter dropped. The rule is unchanged; this is a signal, not a refusal.

## Changed

### CLI-478 — generated files order themselves

`config.ts` field order followed whatever insertion order the in-memory object carried, and a stack's category keys followed the wizard session's selection order, so a value-identical re-emit changed bytes and an agent whose skill set had not changed was rewritten. Both are canonical now, and emission is a fixed point. Every installed `config.ts` and compiled agent rewrites once on its next save, then never churns.

### CLI-479 — the Sources step's bulk install-mode hotkeys are withdrawn

In a project edit they rewrote inherited global rows the per-row toggle deliberately cannot reach, ran a real plugin install and rewrote the global config. The keys are gone and the surviving per-row setter is gated against the hydration snapshot, so the project half of a dual-scope pair stays editable and a fresh install is not frozen. Switch install modes per row, or from a global-scope edit.

### CLI-482 — project configurations carry the project's own name

A project's `config.ts` was named `agents-inc` on every wizard path, and under an existing global install it inherited that config's name through the merge. It now carries the project directory's name, matching what `eject` and the loader already did.

### CLI-494 — uninstall promises exactly what it removes

The preview and the removal were two predicates kept in agreement by a comment. One plan is now computed, rendered and executed, so the preview cannot promise something the run keeps.

### CLI-495 — one operation owns removing sub-agents and tidying their directory

The rule that an emptied scope directory is removed was every caller's to remember, across six sites, and the edit path had forgotten it.

## Fixed

### CLI-470 (leg 1) — the removal plan is honest when the configuration cannot be read

With an unreadable `config.ts` the plan listed the compiled agents as removals and then kept every one of them. It now says they are kept, and why. The provenance marker and the marker-driven sweep remain open.

### CLI-480 — emptied scope directories are removed

`.claude/skills/` and `.claude/agents/` survived a full collapse, and a project-only install pre-created an empty global agents directory. Emptiness is measured on disk, so a hand-authored sub-agent keeps its directory.

### CLI-483 — a scope change moves where a sub-agent lives, not what it knows

Toggling a sub-agent from global to project scope rebuilt its skill catalogue from defaults and silently shrank it — seven skills to four, with nothing on screen to say so.

### CLI-484 — `list` counts the plugin skills a project owns

A plugin install reported `Skills: 0` from a project directory and `Skills: 7` from the home root. A project owns what is installed globally too, and the count now says so.

### CLI-485 — `init` names the configuration that holds the assignments

After a wholly global install run from a project directory, the closing block told the user to edit a configuration that carries no assignments and to run `compile` where its pass recompiles nothing global.

### CLI-486 — a refusal no longer paints over a live spinner

Every refusal inside `edit`'s and `init`'s context load fired while the loading spinner was still mounted.

### CLI-487 — a moved source is downloaded once per run

Revalidation memoised its verdict but not its side effects, so the second load in a command discarded and re-downloaded the copy the first had just fetched — a full duplicate tarball for `github:` sources — and printed its notice twice.

### CLI-488 — the home root stops calling the global configuration a project one

`compile` printed `Source: project` above "Compiling global agents...", `edit` said `(project)` on a screen refusing scope toggles as global, and `doctor` announced the global configuration as a project one. Also: a source named internally is no longer attributed to a `--source` flag the command refuses.

### CLI-489 — the eject direction of a mode switch reports its copies

Switching to plugin narrated every install; switching back reported nothing, though the copies happened.

### CLI-490 — `search` names the skill and the source it found

The `ID` column rendered display names and `Source` printed one constant for every row, local skills included.
