# Release 0.146.0 (2026-07-30)

Cross-scope rules: globally installed items become immutable from project scope, colliding installs are masked rather than left both active, and the Sources tab stops disagreeing with the confirm step (D-277, D-278, D-279)

Every defect here was found by running the CLI rather than by a failing test. Three of them were introduced by 0.145.0's own marker work; the fourth predates it. The suite was green throughout, because the bugs lived in the gap between two implementations of the same idea — which is the theme of this release.

## Changed

### D-277 — globally installed items are immutable from project scope (breaking)

A globally installed skill or agent belongs to the global config, which every project shares, so no project may remove it. The rule already held in an edit, but four paths escaped it:

- An init-mode arm bypassed every global-item guard.
- A scope move to global followed by a deselect minted a tombstone for a skill that was never installed globally, because the installed-id probe ignored scope.
- Toggling an agent off tombstoned the global entry.
- Deselecting a domain tombstoned that domain's global skills, with no guard at all.

Deselecting a domain is now a **view filter**: it hides the domain's skills and drops only what the project owns, leaving global entries untouched — neither dropped nor masked. Agent-roster rebuilds merge instead of replacing, so a globally installed agent outside the selected domains' roster is no longer silently uninstalled. Skill removal keeps inherited global installs by ownership, which also preserves the property that a skill added by accident during a session stays deselectable.

**Breaking:** a globally installed skill or agent can no longer be deselected from a project in any flow, including during `init`. To keep a global skill out of a project, leave it out of that project's agent stacks — see the new section in [docs/guides/editing-config.md](../docs/guides/editing-config.md). To uninstall it outright, edit at global scope (`agentsinc edit` from your home directory).

The domain-deselect path had no reachable UI surface — the domains step cannot be reached from an edit session — so that portion is invariant hardening rather than a user-visible change.

### D-278 — the Sources tab now agrees with the confirm step

The two surfaces each computed "what changed this session" independently and disagreed, because the confirm step keys on the `(id, scope)` slot while the Sources tab keyed on the id alone. Three consequences, all user-visible:

- **A deselected global skill vanished at global scope.** The removal collector was switched off whenever the edit was global, on the stated premise that a removal there is "a genuine uninstall rather than a project-overlay change" — which is backwards: a genuine uninstall is the case that most needs showing, and the confirm step has never had such a gate.
- **Adopting a globally installed skill at project scope showed no `+`.** The id was already in the snapshot even though the project slot was new, and the flag was only ever applied to the single-row shape, so the dual-scope shapes dropped it.
- **A focused row lost its diff colour**, printing `+` in white instead of green. The diff colour now survives focus, while ordinary focused rows stay white — neutral grey on the focus background is the low-contrast pairing, so reusing it would dim every ordinary row to fix rows that have no diff to show.

Removal detection is slot-keyed too, so a collapsed dual-scope pair now renders **two** rows: the surviving locked global row, plus a red inert pending-removal row for the emptied project slot. That mirrors the confirm step, which already reported that state as a removal at Project. A slot an emitted row already renders never gets a removal row stacked on top of it, so an inherited global install does not read as both locked and removed.

Both surfaces now build their keys with one shared `skillSlotKey`, so they cannot drift apart again.

## Fixed

### D-279 — a global install could sit active beside a project-owned one

Cross-scope reconciliation compared skill ids and knew nothing about category exclusivity. A project owning Angular at project scope had a globally installed React inlined beside it as a second **active** entry — two live skills in one exclusive category. The wizard showed both selected, and the next save seeded both into a fresh agent stack, compiling an agent instructed to load two frameworks. `doctor` reported the install clean and `validate` exited 0, because neither checks config semantics.

Only one of the two write paths reconciled at all. The project's own save path split by scope and wrote with no reconciliation step, so it also lost the plain same-id pairing that propagation handled correctly: a project owning a skill that was separately installed globally ended up claiming both, with the global copy invisible in the wizard because hydration prefers the project entry.

One shared reconciliation step now runs immediately before **both** project-config writes. It masks a live global entry on an identity collision (skills and agents) or when the project owns a different active skill in the same exclusive category (skills only — agents have no categories), and it drops a mask once the collision that produced it clears. It is idempotent, reads the exclusive flag from the merged matrix so a source repo's overrides are honoured, treats an undeclared flag as non-exclusive because a rule that masks persisted entries must only fire on a flag the data actually carries, never throws on custom skills absent from the matrix, and never writes a tombstone into the global config.

The project's own skill wins locally. That is deliberately asymmetric with the guard that refuses a user-initiated exclusive swap over a globally locked skill: there the user is displacing a shared install, whereas here a global install has landed on top of existing project state, and letting it win would silently uninstall the user's own skill.

### Mask lifetime

With no store path able to mint a user-authored mask, every bare mask is system-derived by construction. The self-heal therefore generalises from "only in categories that are both exclusive and required" to "keep it only while the collision that would re-derive it still exists", with an agent equivalent. The narrow rule existed solely because a derived mask and a deliberate exclusion were indistinguishable on disk; after D-277 they no longer coexist.

## Internal

- Four end-to-end specs drive the real binary through each scenario. The dual-scope specs build their configs directly rather than through the editable-project fixture: that fixture pins both halves of a skill to eject, and the overwrite guard refuses the scope press for an eject-over-eject pair with no tombstone, so a spec built that way would fail on a swallowed keystroke instead of the assertion under test.

- Two test fixtures were repaired that had never tested what their names claimed. One built a project-to-global migration while asserting "project-scoped, previously installed as project"; its incidental row-count assertion had been pinning the id-keyed behaviour for an unlisted shape. The other two pinned exclusion-by-deselection, the semantics D-277 removes, and now pin the dual-scope pairing they were really about.

- `prepublishOnly` runs `typecheck` before build and test. Its absence is how a broken typecheck reached 0.144.1.

- An expressive-TypeScript pass over the new code removed a find-predicate written three times, a row shape assembled twice, an imperative accumulation in skill removal, and four hand-rolled scope rules that the shared predicate module already owned.
