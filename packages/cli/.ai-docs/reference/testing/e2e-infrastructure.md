# E2E Test Infrastructure

> **Split from:** `reference/test-infrastructure.md`. See also: [infrastructure.md](./infrastructure.md), [factories.md](./factories.md), [mock-data.md](./mock-data.md).

## E2E Tests

**Config:** `e2e/vitest.config.ts` (separate Vitest config, no `setupFiles` — matchers imported per-test)
**Projects:** two named projects over one tree, split by FILENAME — `e2e` includes `e2e/**/*.e2e.test.ts`, `smoke` includes `e2e/**/*.smoke.test.ts`. There is no top-level `include`; every other setting below is shared through `extends: true`. Each project is selected by its own script (`test:e2e`, `test:smoke`) — a project no script names by name runs only when the OTHER project is asked for and never otherwise, which `src/cli/lib/__tests__/spec-gates.test.ts` now enforces
**Timeout:** `testTimeout: 30_000`, `hookTimeout: 60_000`
**Pool:** `forks` (process isolation) with `maxWorkers: Math.min(16, os.availableParallelism())` — PTY-driven wizard tests are load-sensitive, so the count is capped at **both** ends. The flat `16` guarded only the top: a four-core CI runner then put four PTY workers on every core, which is the exact contention the cap exists to prevent, inverted. Measured — 16 workers run the suite in ~6m20s locally; 4 workers finish in ~19 minutes of `check-cli`'s 25-minute job, inside its 40-minute bound
**Retry:** `retry: 1`. The flake a higher retry was once tuned against was Ink's CI detection buffering every frame, fixed by the render wrapper (see [`harness-decisions.md`](./harness-decisions.md) § 1.8). Measured after the fix: the full suite passed at retry `0` with zero retries used. One retry stays because runner contention is the one variable a local run cannot measure; it bounds a genuine failure's cost at 2x rather than 3x, and a retry that fires shows up in vitest's flaky report instead of passing silently. **Do not raise it back to hide a failure**
**Global Setup:** `e2e/global-setup.ts` (teardown function only — lists marketplaces via `claudePluginMarketplaceList` and removes names starting with `e2e-test-` via `claudePluginMarketplaceRemove`; best-effort, swallows list errors)

Note: the split is by filename, not by directory. `*.smoke.test.ts` files belong to the `smoke` project and run only under `test:smoke`; `pom-framework.e2e.test.ts` sits inside `e2e/smoke/` and belongs to the `e2e` project, because it validates OUR page objects rather than probing the `claude` binary.

**One concern per file, because the pool parallelises per file.** A large file serialises everything inside it against one worker, so coverage of a single subject is spread across sibling files sharing a prefix — `plugin-uninstall-*`, `edit-wizard-plugin-*`, `dual-scope-edit-*`, `install-mode-*`, `scope-toggle-*`. When adding a case, add it to the sibling whose prefix already names its concern rather than growing one file.

**There is no `search-interactive.e2e.test.ts`.** `search-static.e2e.test.ts` is the whole of the `search` E2E surface; the interactive search flow is exercised from inside the wizard specs that open the modal.

**Dual-scope specs are named for the `s` round-trip contract, never for SPACEBAR.** Spacebar's meaning depends on the path, so a name built on it says nothing about what the spec pins. `dual-scope-s-round-trip-space-inert.e2e.test.ts` is where the two are held together: the `s` round trip, plus what spacebar owns beside it — it drops a skill pair's PROJECT half, and stays inert on an agent pair.

### Two `TERMINAL_SIZE` hazards, both of which turn a failing spec into a hanging one

**1. `SHORT.rows` is coupled to a production constant, and going under it hangs rather than fails.**

`TERMINAL_SIZE.SHORT.rows` must equal `MIN_TERMINAL_SIZE.ROWS` in `src/cli/consts.ts` (currently `{ COLS: 80, ROWS: 20 }`) — the single live size gate, enforced by `isTerminalLargeEnough` in `src/cli/utils/terminal.ts` and called from both the pre-Ink startup gate in `src/cli/base-command.ts` and the `WizardLayout` guard. The value is duplicated rather than imported because `e2e/pages/constants.ts` is deliberately free of `src/cli/` imports.

Set it **lower** and the startup gate blocks before Ink mounts: every spec using `SHORT` sits on `Terminal too short (need 20). Please resize.` until its 45s `WIZARD_LOAD` timeout expires. That is a hang, not an assertion failure — so it presents as flake rather than as the miscalibration it is, and the natural response (raise the timeout, add a retry) buries it further.

Set it **higher** and those specs stop exercising the tightest geometry the wizard claims to support, which is the only reason `SHORT` exists.

`MIN_TERMINAL_SIZE.ROWS = 20` is measured, not chosen: on the build step 16 and 17 render corrupt, 18 is the first clean frame (where `SCROLL_VIEWPORT.MIN_VIEWPORT_ROWS` starts being satisfied), and 20 buys two rows of margin while staying under the 24-row default of common terminals. `LOGO_MIN_TERMINAL_ROWS` (26) is a **separate, non-gating** threshold governing only whether the stack step paints its six-row ASCII banner — do not conflate the two.

**2. `BELOW_MINIMUM` must never LAUNCH a session.**

`{ rows: 16, cols: 100 }` is under the gate by design. Passing it as `cols`/`rows` to any launcher hits the startup gate before Ink mounts, so the session never reaches a wizard frame — the same full-timeout hang. It is reachable only through `BaseStep.resizeBelowMinimum()`, on a session that started at a clearing geometry.

**Corollary — clearing the size gate is not evidence the content is visible.** At `SHORT`, the confirm step's summary viewport measures five rows and all five are consumed by the `Marketplace` / `Stack` header block (two label rows, a padding row, the divider, a margin row). The first summary row does not appear until scroll offset 6, against a content height of 17 and a scroll range of 12. A spec needing a summary row on screen must call `ConfirmStep.scrollSummaryToBottom()` first; asserting at offset 0 asserts about a frame that paints none of the rows in question. Two specs shipped that way — see [standards/e2e/anti-patterns.md § Weak Assertions](../../standards/e2e/anti-patterns.md).

##### `focusSkill` — closed-loop category Tab-walk

`focusSkill` is closed-loop, and must stay that way. **Dead-reckoning rows does not work here:** arrow-DOWN does not reset the grid column — the grid PRESERVES and CLAMPS it (`use-focused-list-item.ts`: `finalCol = min(currentCol, newColCount - 1)`) — so a second `focusSkill` in the same domain starts its RIGHT presses from a wrong column and, with cyclic wrap, toggles the WRONG skill rather than failing.

Two observability facts drive the current design:

| Fact                                                                                                                                                                                                                                                  | Consequence                                                                             |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| The focused CELL has no text signal under `NO_COLOR`. `SkillTag` distinguishes it only via `borderColor`/`borderDimColor`, which the harness strips.                                                                                                  | Cell-level focus cannot be verified from the frame; no design may depend on reading it. |
| The focused CATEGORY HEADER **is** observable: it paints as one background-highlighted text with one extra leading space (`  Framework (1 of 1)` focused vs ` Framework (1 of 1)` unfocused; the outer space on both is `WizardLayout`'s `paddingX`). | Row/category focus can be closed-loop verified by re-parsing the viewport.              |
| Tab moves focus to the next category AND resets the column to 0 (`use-category-grid-input.ts` does `setFocused(nextSection, 0)`). DOWN does not.                                                                                                      | Only Tab yields a known column, so the walk is built on Tab, not DOWN.                  |

Algorithm: parse the current viewport into `VisibleCategory[]` (header lines are non-empty, box-drawing-free lines immediately followed by a `┌` line; cells are the `│`-delimited segments up to the next header, flattened in option order; each carries the header's own text as its `label`) → read the focused category and return immediately if it holds the target → otherwise Tab-walk, where `advanceCategoryFocus` re-presses until the frame SHOWS a different category focused, so no category is passed while its repaint is in flight → walk RIGHT to the target column from a stated base: `0` when the walk arrived by Tab, the tracked `gridCol` when it never moved. Termination is a lap, not a budget — the walk stops on observing a category already seen and raises `CategoryWalkError`, whose `categoriesWalked` says what it looked at.

`MAX_FOCUS_ATTEMPTS` no longer exists. It was deleted 2026-08-20: pressing before looking cost a 33-category lap whenever the target sat in the category the grid opened on, and a press assumed to have landed let the walk skip its own target, so a single missed observation needed a second lap that 50 presses could not fund. CI run 32338714325 is the failure and `2026-08-20-focus-walk-presses-before-it-looks.md` the finding; `e2e/interactive/build-step-focus-walk-cost.e2e.test.ts` pins both properties by asserting what the helper SPENDS.

**Labels are matched EXACTLY, not by substring.** `cellLabel()` strips leading `P`/`G` scope badges and `+ - ✓ ✗ ⏏` diff glyphs (`CELL_LEADING_MARKERS`) plus the trailing compatibility annotation `(requires … | required by … | incompatible | discouraged)` (`CELL_ANNOTATION`), then trims. So `"React"` no longer stops the walk on a `"React Query"` cell, nor `"Vite"` on `"Vitest"`. Both regexes are deliberately narrow: the marker tokens must be followed by whitespace (so `"Pinia"` / `"GraphQL"` are never clipped) and the annotation must open with one of the four keywords (so `"Gel (EdgeDB)"` keeps its parentheses).

The one residual open-loop spot is `focusColumnInSingleCategory`: when the grid has a single visible category with no scroll affordance, Tab is a guarded no-op (`use-category-grid-input.ts` skips `setFocused` when the next section equals the current), so the walk cannot reset the column. A single-cell category needs no navigation (the grid clamps to 0); a multi-cell one falls back to the private `gridCol` hint using the grid's real cyclic-wrap arithmetic. Single-category domains in the standard E2E source are all single-cell, so the fallback is effectively unreachable there. `gridCol` is a best-effort HINT consulted ONLY by that fallback — it is reset on domain change and on `navigateToNextCategory`.

## Scope & HOME model

The E2E sandbox never lets `HOME` collapse onto the project dir by accident. Both the interactive path (`TerminalSession`, `helpers/terminal-session.ts`) and the non-interactive `runCLI` default `HOME` to a freshly-created SIBLING temp dir (prefix `ai-e2e-home-`), distinct from `cwd`/`projectDir`, and remove it on teardown. Because `os.homedir()` therefore never equals the project dir, a project `edit`/`init` stays at genuine PROJECT scope (`isEditingFromGlobalScope === false`) instead of silently running as a global edit. An explicit `env.HOME` always wins and is never auto-removed.

Skills and agents default to GLOBAL scope, so their installed content (`.claude/skills`, compiled agents, `settings.json`) lands under that global HOME, NOT `projectDir`. The scope-explicit wizard launchers expose that dir as `wizard.globalHome`:

- `launchInProject()` allocates a fresh global HOME distinct from `projectDir` — models a project install: global-default content is observable at `wizard.globalHome`, while `config.ts` stays under `projectDir`. An optional `globalHome?` reuse param lets a multi-phase test share one global HOME across launches (allocator owns cleanup).
- `launchInGlobal()` sets `HOME === cwd === projectDir` — models editing the global install, so every artifact collapses back onto `projectDir`.
- A plain `launch()`/`launchRaw()` wizard uses an internal auto-allocated HOME and `wizard.globalHome` throws.

`CLI.run` and the `WizardResult`/`ProjectHandle` handle carry the same `globalHome` (see [E2E Fixtures](#e2e-fixtures-e2efixtures)), so a follow-up command reads the same global root the wizard wrote.

Pick the launcher by what the test does — asserting installed content vs. toggling a global skill's source vs. running a cwd-resolving follow-up (`cc uninstall`, `claude plugin install`). Those decision rules are the prescriptive standard [Choosing the Wizard Launcher by Scope](../../standards/e2e/anti-patterns.md#choosing-the-wizard-launcher-by-scope); this doc only describes the mechanism.

## E2E Source Factories (`e2e/helpers/create-e2e-source.ts`, `create-e2e-plugin-source.ts`)

**Reach for a factory only when the shared frozen trees are not what the spec is about.** `globalSetup`

## Remote Source Server (`e2e/helpers/tarball-source-server.ts`)

`startTarballSourceServer(sourceDir)` serves a source directory as a gzipped tarball over HTTP —
`http://localhost:<port>/source.tar.gz`, a value `init --marketplace`, `CC_MARKETPLACE` at init and a stored
config source all accept (the source
validator allows `localhost` explicitly; a numeric private IP is refused as SSRF). It exists because
**a local path cannot test caching at all**: local sources are read in place and never cached, so
only a remote can be stale, and only a server the spec controls can decide when the ETag moves.

| Member               | Purpose                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------ |
| `url`                | The source value naming this server                                                                                |
| `publish(sourceDir)` | Serve that directory from now on, under a new ETag — the source moving on                                          |
| `requests`           | Every request the CLI made, in order, as `"<METHOD> <status>"` — the proof-of-execution surface for a revalidation |
| `close()`            | Stop serving; further loads see a refused connection. Idempotent, so `afterAll` may close a spec that already did  |

The bytes are packed once per `publish` and held. Packing per request would move the ETag on every
request (gzip stamps its own header) and every load would look like a change. The archive wraps the
directory in one top-level entry, the shape a git host's tarball has and the one giget strips on
extract.

**Source-of-truth title maps** (`create-e2e-source.ts`): written into each fixture's `metadata.yaml`, so they ARE the text the wizard renders. Assertions matching rendered skill/agent text MUST key off these instead of re-typing strings. `E2E_AGENT_TITLES` is re-exported by `fixtures/expected-values.ts` as `E2E_AGENT_DISPLAY`; both maps are also re-exported through `helpers/test-utils.ts`.

**The fixture source is a custom marketplace, so its skill ids are namespaced.** `E2E_SKILLS` (module-private in `create-e2e-source.ts`) is the SOLE definition of what a fixture ships; each entry's `id` is composed at runtime by `e2eSkillId(bare)` = `` `${E2E_MARKETPLACE_NAME}-${bare}` ``. Those ids are typed `string`, never `SkillId`: the generated union is the PUBLIC catalogue's, and a namespaced id is not a member of it.

`E2E_SKILL_TITLES` — `as const satisfies Record<E2ESkillSlug, string>`, **keyed by SLUG and total over the set**, all 10 entries, bound to source by `scripts/check-enumeration-drift.ts`:

| Slug                   | Bare id (namespaced at runtime)         | Display title          |
| ---------------------- | --------------------------------------- | ---------------------- |
| `react`                | `web-framework-react`                   | `E2E React`            |
| `vitest`               | `web-testing-vitest`                    | `E2E Vitest`           |
| `zustand`              | `web-state-zustand`                     | `E2E Zustand`          |
| `hono`                 | `api-framework-hono`                    | `E2E Hono`             |
| `research-methodology` | `meta-methodology-research-methodology` | `Research Methodology` |
| `reviewing`            | `meta-reviewing-reviewing`              | `Reviewing`            |
| `cli-reviewing`        | `meta-reviewing-cli-reviewing`          | `CLI Reviewing`        |
| `vue-composition-api`  | `web-framework-vue-composition-api`     | `Vue Composition Api`  |
| `pinia`                | `web-state-pinia`                       | `E2E Pinia`            |
| `visual-regression`    | `web-testing-visual-regression`         | `Visual Regression`    |

**Keyed by slug for two reasons, and the first is not a preference.** An id is namespaced at runtime, so it is no longer a literal type and can key nothing exhaustively; a slug is written literally and is not namespaced. Second, a marketplace rename moves every id and no slug. `E2E_SKILLS` decides which skills need a title and this map only decides what each one SAYS — a missing or surplus key is a compile error. The VALUES are not derived from ids at all — a title must be neither an id nor a public-catalogue display name. An id is a strict substring of the namespaced id the wizard paints beside it, so a `toContain(display)` assertion is answered by the id and proves nothing about the title; a bare catalogue name (`React`, `Vitest`) collides when a spec renders the fixture source and the default source at once, and `focusSkill` then takes whichever cell comes first. The `E2E ` prefix is what the fixture's own stack already does (`E2E_STACK_NAME` is `E2E Test Stack`). `CLI Reviewing` and `Visual Regression` are still verbatim catalogue titles and are the remaining hazard of the second kind. The build grid sorts by display name, so a title that tracked its id would also relocate every cursor target the moment ids change.

**The row binds this table as PAIRS, so the Display title column is checked and the two column headings are load-bearing.** `scripts/check-enumeration-drift.ts` reads the `Slug` and `Display title` columns BY NAME and compares `slug = title` against the same encoding taken off the object literal, so renaming either heading refuses the run by name rather than silently unbinding the column. Bound as keys alone this table reported the suite clean while five of its titles were wrong — the slugs were right, and the slugs are not what any assertion matches on. The middle column is deliberately unbound: it states bare ids, which are namespaced at runtime and are `E2E_SKILLS`' business rather than this map's, and a third column standing between the two named ones is exactly why the reader names its columns instead of counting them.

`E2E_AGENT_TITLES` — `as const satisfies Partial<Record<AgentName, string>>`, both entries: `web-developer` → `Web Developer`, `api-developer` → `API Developer`. Agent names are NOT namespaced — the namespace rule governs skill ids alone, and marketplaces do not ship sub-agents.

`E2E_SKILL_IDS` is **derived** from `E2E_SKILLS` (`E2E_SKILLS.map(s => s.id).sort()`, typed `readonly string[]`), not a hand-written second list — a skill added to the source and not to the list left every "the install wrote exactly these" assertion quietly short. `fixtures/expected-values.ts` re-exports it (see the [E2E Fixtures](#e2e-fixtures-e2efixtures) table).

## Type-Narrowing Probe (`e2e/helpers/type-check-probe.ts`)

Verifies that a project's generated `config-types.ts` union aliases still REJECT bogus values — asserting the property that matters, not the emitted text. A union that has collapsed to `string` passes a text assertion but silently accepts everything; this probe makes `tsc` render the verdict.

| Export                      | Signature                                                                                                     | Purpose                                                                                                                                                                                                                                                                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `probeConfigTypesNarrowing` | `(claudeSrcDir: string, aliases: readonly GeneratedAlias[]) => Promise<{ exitCode: number; output: string }>` | Writes a probe module next to `config-types.ts` assigning a bogus literal to each alias, runs the repo-local `tsc` on it, removes the probe, returns tsc's verdict. **Judged on `TS_NOT_ASSIGNABLE` in `output`, never on `exitCode`** — tsc exits non-zero for any diagnostic, a malformed probe included. |
| `typecheckGeneratedConfig`  | `(claudeSrcDir: string) => Promise<{ exitCode: number; output: string }>`                                     | Type-checks the written `config.ts` itself against its own generated types, with `--skipLibCheck`. The positive half of the pair the probe supplies the negative half of.                                                                                                                                   |
| `TS_NOT_ASSIGNABLE`         | `"TS2322"`                                                                                                    | TypeScript's "type X is not assignable to type Y" diagnostic code; asserted in `output` to confirm narrowing.                                                                                                                                                                                               |
| `TS_UNKNOWN_PROPERTY`       | `"TS2353"`                                                                                                    | "Object literal may only specify known properties" — the diagnostic a config carrying a field its types do not declare produces.                                                                                                                                                                            |
| type `GeneratedAlias`       | `"SkillId" \| "AgentName" \| "SelectedAgentName" \| "ProjectAgentName" \| "Domain" \| "Category"`             | The argument type. It exists because the probe takes ALIAS NAMES and handing it a skill id instead emits `import type { web-framework-react }`, which tsc rejects as a SYNTAX error — non-zero for a reason that has nothing to do with narrowing.                                                          |

Mechanics: the bogus literal is `__agentsinc-e2e-bogus-literal__` (module-internal `BOGUS_TYPE_LITERAL`, not exported). The compiler is the repo-local `node_modules/typescript/bin/tsc` resolved through `createRequire` (an `npx tsc` from a temp dir resolves the wrong package). Flags are passed positionally under `--ignoreConfig` so the temp directory's own tsconfig cannot perturb the verdict, and they state the FLOOR a consumer's tsconfig is assumed to meet rather than mirroring this repo's. The probe file is removed in a `finally`, leaving the installed file tree byte-identical for the caller's subsequent filesystem assertions.

## `e2e/assertions/` Carries No Tests, and a Test Put There Would Not Run

Five modules — `config-assertions.ts`, `four-surfaces.ts`, `phase-assertions.ts`,
`scope-assertions.ts`, `uninstall-assertions.ts` — and no `*.test.ts` beside any of them. That is
not an omission a file added here would fix: `e2e/vitest.config.ts` collects only
`e2e/**/*.e2e.test.ts` and `e2e/**/*.smoke.test.ts`, and the package's own `vitest.config.ts`
includes only `src/**` and `scripts/**`, so `e2e/assertions/config-assertions.test.ts` is collected
by no project and would read as coverage while running never. `src/cli/lib/__tests__/helpers/` is
the only directory a tested helper can live in — the rule and the `e2e/helpers/test-utils.ts`
re-export route are in [`standards/e2e/README.md`](../../standards/e2e/README.md).

**Both config normalisers took that route and are no longer here.** `normalizeConfigPreservingOrder`
and `normalizeGlobalConfig` sit together in `src/cli/lib/__tests__/helpers/config-comparison.ts`,
built on one `significantLines` implementation and covered by one test file, and E2E reaches them
through `e2e/helpers/test-utils.ts`. They differ in exactly one step: both drop the machine-specific
`"projects"` line, and only `normalizeGlobalConfig` sorts what survives, which is what makes it
order-INSENSITIVE. The two names are the only signal at a call site, which is why the
order-preserving one is named for the property rather than for the action.

**Swapping one normaliser for the other under an existing assertion is an assertion change, not a
refactor.** It can only loosen or tighten what the test detects, and it compiles and passes either
way. The one consumer, `e2e/lifecycle/scope-toggle-roundtrip.e2e.test.ts`, asserts that a
passthrough edit rewrote the config byte-for-byte; under the sorting sibling that becomes "kept the
same set of lines in any order", which is the regression class the spec exists to catch.

**`expectNoDuplicates` is what the move left behind, and it is untested.** It is now the whole of
`config-assertions.ts`, and it carries real logic — it filters an array for repeats, totals each
one, and folds `label` and `context` into the failure message — which is exactly the shape the rule
above says belongs in `src/cli/lib/__tests__/helpers/` with a test beside it. Three lifecycle specs
call it (`agent-scope-toggle-agents-array`, `init-then-edit-merge`, `re-edit-cycles`); nothing
exercises it directly, and nothing can while it sits in this directory.

## The Four Assertion Surfaces (`e2e/assertions/four-surfaces.ts`)

The shared strictness core. `standards/e2e/user-journeys.md` defines four surfaces a journey owes an
assertion on; three of them are read here — the compiled agent files, the written `config.ts`, and
the generated `config-types.ts`. The fourth, rendered output, belongs to whoever drove the command
and is asserted at the call site.

| Export                  | Signature                                                        | Purpose                                                                               |
| ----------------------- | ---------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| `inspectFourSurfaces()` | `(dir, options?: SurfaceOptions) => Promise<SurfaceReading>`     | Reads all three and REPORTS what each holds, without throwing                         |
| `expectFourSurfaces()`  | `(dir, options?: SurfaceOptions) => Promise<SurfaceReading>`     | The same reading, THROWN as a vitest assertion naming every claim that failed and why |
| type `SurfaceFinding`   | `{ claim: string; held: boolean; detail?: string }`              | One claim's verdict                                                                   |
| type `SurfaceReading`   | `{ skillIds, agentsAtThisScope, compiledFiles, findings, held }` | What the scope holds, plus every finding                                              |
| type `SurfaceOptions`   | `{ globalHome?: string; expectEmpty?: boolean }`                 | `globalHome` defaults to `dir`; `expectEmpty` asserts the scope owns nothing          |

**One core with two presentations, deliberately.** The specs call `expectFourSurfaces` and the
hand-run calls `inspectFourSurfaces` through `handrun-surfaces.ts`, so a spec and a hand-run cannot
drift on what "strict" means — which they did: the hand-run's first pass asserted presence where the
suite asserted content, and neither noticed.

Two facts about the reading that are easy to get backwards, and expensive both ways:

**Never `os.homedir()` for `globalHome`.** The spec's own process runs under the machine's home
while the binary it spawned runs under a temp one, so reading it there checks the WRONG tree and
passes anyway. `globalHome` is a parameter with `dir` as its default — right for a global install,
and stated explicitly by every project-scope caller.

**A `[P][G]` pair is ONE name at TWO scopes, so a name present at this scope is never a leak.** A
config records agents at both scopes but only this scope's compile lands here, so the "no other
scope's agent is compiled here" claim subtracts the names this scope owns before it looks: the other
side compiles its own half. Reading the two scopes as disjoint sets condemns every dual-scope pair.

What each claim asks, when `expectEmpty` is not set:

| Claim                                                           | The defect it catches                                                                                           |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| every ejected skill sits at the scope its entry claims          | Config and disk disagreeing — the defect class the scope system keeps producing                                 |
| every skill entry names its origin                              | An entry with no provenance                                                                                     |
| every agent at this scope is compiled here                      | A declared agent nothing wrote                                                                                  |
| no other scope's agent is compiled here                         | A cross-scope leak, after the `[P][G]` subtraction above                                                        |
| nothing is compiled that the config does not declare            | An orphan `.md` the config never named                                                                          |
| no compiled agent references a skill this config does not carry | A dangling skill reference — the failure a directory listing cannot see                                         |
| `config.ts` type-checks against its own generated types         | `typecheckGeneratedConfig`                                                                                      |
| `config-types.ts` still rejects a literal outside its union     | `probeConfigTypesNarrowing`, judged on the DIAGNOSTIC, because a union degraded to `string` type-checks cleanly |

The `scope` field is deliberately NOT asserted: the loader has already narrowed it to one of two
values, so asserting it is tautological.

## The Hand-Run (`e2e/handrun-*.ts`, `scripts/handrun.mjs`)

Step 4 of the repository's change workflow — "run it by hand through the CLI" — has a harness.
It drives the real binary through journeys and prints a transcript for a person to judge; it is not a
gate and no script runs it in CI.

**Run it from `packages/cli` with `node scripts/handrun.mjs`.**

| File                      | What it is                                                                                                                                                                 |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `e2e/handrun-journeys.ts` | The journeys themselves, driven entirely through the page objects and fixtures the E2E suite already uses — `InitWizard`, `seed-config-store`, `dual-scope-helpers`, `CLI` |
| `e2e/handrun-driver.ts`   | Transcript printing ONLY: `section`, `note`, `verdict`, and `attempt(label, journey)`, which runs a journey so a failure is reported and the rest of the run continues     |
| `e2e/handrun-surfaces.ts` | `checkFourSurfaces(label, dir, options?)` — the hand-run's presentation of `inspectFourSurfaces`                                                                           |
| `scripts/handrun.mjs`     | Bundles `handrun-journeys.ts` with esbuild and imports the bundle                                                                                                          |

**`handrun-driver.ts` no longer drives anything, and that is the point.** It once tried to walk the
wizard itself. `e2e/pages/` already does that correctly, and knows two things a naive waiter does
not: the tab bar renders every step's name on every screen, and `waitForText` matches the whole
output rather than the current frame — so a keystroke fires early and silently no-ops. Use the page
objects.

**The bundle must land at `e2e/helpers/handrun.gen.mjs` and nowhere else.** `CLI_ROOT` is derived
from `import.meta.url`, so a bundle written anywhere else resolves the package root differently and
silently points the spawned binary at the wrong tree. It is gitignored at the repository root, sits
in `eslint.config.js`'s `globalIgnores` as `e2e/helpers/*.gen.mjs`, and is listed in
`.prettierignore` — it is mostly vendored third-party source, so linting it reports against code
nobody here can edit, including `eslint-disable` comments that `reportUnusedDisableDirectives`
would judge against THIS config rather than the one they were written for.

The esbuild call externalises the native and heavy dependencies (`@lydell/node-pty`, `jiti`, `zod`,
`execa`, `fs-extra`, `yaml`, `chalk`, `ink`, `react`, `@oclif/core`, `fast-glob`), adds a
`createRequire` banner so CommonJS interop resolves under ESM, and carries a `js-to-ts` resolver
plugin because the source uses `.js` specifiers that answer to `.ts` files.

## Test-Lifecycle Patterns

E2E files consistently follow this shape (see `plugin-install-failure-hard-error.e2e.test.ts`, `info-panel-scope-toggle-diff.e2e.test.ts` as representative examples):

```ts
beforeAll(async () => {
  // Neither the dist door nor a source is built here. `e2e/setup.ts` registers the door once for
  // every spec file, and `E2E_SOURCE` is the shared frozen plain tree and `InitWizard`
  // defaults to it; `EditWizard.launch({ projectDir, source: E2E_SOURCE })` names it because
  // `edit` records it. A spec builds its own only when the source IS its subject, and then it
  // owns the `afterAll` cleanup for the temp dir that call returns.
}, TIMEOUTS.SETUP);

afterEach(async () => {
  await wizard?.destroy(); // close PTY, cleanup temp project + temp dirs
  wizard = undefined;
});
```

Key rules enforced across the suite:

- **in `beforeAll`** — every interactive/lifecycle/command file calls it once.
- **Source creation in `beforeAll`** — E2E sources are expensive; never re-create per-test.
- **Project dir creation per-test** — use `ProjectBuilder` (`fixtures/project-builder.ts`) in `beforeEach` / `it()` body so each scenario starts clean.
- **Cleanup in `afterEach`** — PTY sessions and per-test projects are torn down via the page object's `destroy()` (InitWizard/EditWizard/DashboardSession all expose it; there is no `dispose()`); source teardown lives in `afterAll`.
- **`describe.skipIf(!claudeAvailable)`** — tests that exercise the real `claude plugin install` pipeline (e.g. `plugin-install-failure-hard-error.e2e.test.ts`, `plugin-lifecycle.e2e.test.ts`) are gated on `isClaudeCLIAvailable()`. Note: `real-marketplace.e2e.test.ts` is gated instead on `hasSkillsSource` (a `directoryExists` check for the local skills repo under `SKILLS_SOURCE`), NOT on the Claude CLI.

## Timeout Infrastructure

`TerminalSession` has a `defaultTimeout` readonly property (set from `TerminalSessionOptions.defaultTimeout` or CI-aware defaults: `TIMEOUTS.SESSION_DEFAULT` (10s) locally, `TIMEOUTS.SESSION_DEFAULT_CI` (20s) in CI). Methods `waitForText()` and `waitForExit()` use this as their fallback timeout.

`BaseStep` sets its own `defaultTimeout` to `TIMEOUTS.WIZARD_LOAD` (45s) -- intentionally different from the session default -- used by `waitForStep()`, `waitForStepAfter()`, `waitForWizardFooter()`, `waitForWizardFooterAfter()`, and the `*Awaiting` raw-output waits. Every unqualified step wait is therefore a 45s upper bound.

`InitWizardOptions` and `EditWizardOptions` both accept `defaultTimeout` which is passed through to `TerminalSession`. `InitWizardOptions` also accepts `loadTimeout` to override the initial `waitForReady()` timeout separately.

## Custom Matchers (`e2e/matchers/`)

Imported per-test via `import "../matchers/setup.js"`. The setup extends `expect` with matchers from both `project-matchers.ts` and `agent-matchers.ts`.

**Project matchers (`project-matchers.ts`):**

- `toHaveConfig()` - Verify project config exists with expected content
- `toHaveCompiledAgents()` / `toHaveCompiledAgent(name)` - Verify agent compilation
- `toHaveCompiledAgentContent(name, { contains, notContains })` - Verify agent content
- `toHaveSkillCopied(skillId)` - Verify skill was copied
- `toHaveLocalSkills(expectedIds?)` / `toHaveNoLocalSkills()` - Verify local skills
- `toHavePlugin(key)` / `toHaveNoPlugins()` - Verify plugin state
- `toHavePluginInRegistry(key, scope?)` - Verify plugin registry. **Not a registry-presence check alone:** for every installation listed under the key it runs `describeMissingContent(installation, pluginId)` and FAILS when the entry has no content on disk, naming what is missing. A registry row pointing at nothing is the exact "artefact that looks like verification and cannot fail" shape, so do not weaken this back to a JSON-key lookup.
- `toHaveEjectedTemplate()` - Verify ejected template exists
- `toHaveSettings(expectations?)` - Verify settings file

**Agent matchers (`agent-matchers.ts`):**

- `toHaveAgentFrontmatter(agentName, { name?, description?, model?, effort?, noEffort?, tools?, skills?, exactSkills?, hasSkills?, noSkills? })` — parses the YAML frontmatter and checks the named fields. `AgentFrontmatterExpectations` declares exactly these; `skills` is a SUBSET check and `exactSkills` is the whole preload list in order, so a spec meaning "preloads react and nothing else" must use the latter — `skills: [react]` is satisfied by an agent that preloads everything it holds. `noEffort` reads the parsed YAML rather than the raw text, because the word `effort` occurs in agent prose.
- `toHaveAgentDynamicSkills(agentName, { skillIds?, noSkillIds?, hasActivationProtocol?, allPreloaded? })` — strips the LEADING frontmatter block and runs `body.includes(id)` over the whole remaining file. Not scoped to `<skill_activation_protocol>` — see [standards/e2e/assertions.md § Agent Matchers](../../standards/e2e/assertions.md) for what each expectation therefore proves.

## BaseStep Primitives Contract

`BaseStep` (`e2e/pages/base-step.ts`) is the superclass for every wizard step page object. It provides raw PTY-input primitives, output-scraping accessors, and a small set of composition helpers. Subclasses (`BuildStep`, `DomainStep`, etc.) compose these into step-specific methods.

**Design intent:** primitives are intentionally "raw" — they write to the PTY and wait only for a minimal intra-keystroke debounce. They do NOT call `waitForWizardFooter`. The footer wait is the responsibility of each composed step method (see [Page-Object Keypress Rule](#page-object-keypress-rule-waitforwizardfooter)). This keeps primitive cost flat and lets callers batch operations without paying for a stability probe on every character.

### Key-Press Primitives (protected)

All key-press primitives share the same contract: write one PTY token, then `await delay(INTERNAL_DELAYS.KEYSTROKE)` (150ms) — except `pressEnter`, which uses `INTERNAL_DELAYS.STEP_TRANSITION` (500ms) because Enter typically advances wizard state.

| Primitive         | Writes to PTY          | Post-press delay                        | Pre-press `waitForWizardFooter`? |
| ----------------- | ---------------------- | --------------------------------------- | -------------------------------- |
| `pressEnter`      | `session.enter()`      | `INTERNAL_DELAYS.STEP_TRANSITION` 500ms | NO                               |
| `pressSpace`      | `session.space()`      | `INTERNAL_DELAYS.KEYSTROKE` 150ms       | NO                               |
| `pressKey(k)`     | `session.write(k)`     | `INTERNAL_DELAYS.KEYSTROKE` 150ms       | NO                               |
| `pressEscape`     | `session.escape()`     | `INTERNAL_DELAYS.KEYSTROKE` 150ms       | NO                               |
| `pressArrowDown`  | `session.arrowDown()`  | `INTERNAL_DELAYS.KEYSTROKE` 150ms       | NO                               |
| `pressArrowUp`    | `session.arrowUp()`    | `INTERNAL_DELAYS.KEYSTROKE` 150ms       | NO                               |
| `pressArrowRight` | `session.arrowRight()` | `INTERNAL_DELAYS.KEYSTROKE` 150ms       | NO                               |
| `pressCtrlC`      | `session.ctrlC()`      | `INTERNAL_DELAYS.KEYSTROKE` 150ms       | NO                               |

**Contract:** returns after the PTY write flushes AND the fixed delay elapses. Does NOT guarantee React has committed, effects have flushed, or a new frame has painted.

**Invariants assumed:** caller has ensured the previous frame is stable and the relevant `useInput` handler is mounted. Violating this is the general PTY-write-vs-React-commit race the page-object keypress rule guards against. (The specific `focusedSkillId` seeding race that originally motivated the rule was closed — the store now seeds `focusedSkillId` synchronously; see the keypress-rule section below.)

#### Every wizard keypress asserts the frame is wholly on screen

`waitForWizardFooter()` does two things: it waits for the footer sentinel, and it then calls the
private `assertWizardScreenIsWhollyVisible()`, which throws if anything sits above the top of the
viewport. **Every interactive spec inherits that check at every keypress**, because the page-object
keypress rule already routes every press through this one method — it is the only place in the suite
that knows a wizard frame is painted, so the obligation hangs off it rather than off one spec.

| Piece                                  | Where                              | What it answers                                                                        |
| -------------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------- |
| `TerminalSession.linesAboveViewport()` | `e2e/helpers/terminal-session.ts`  | `readonly string[]` — the buffer rows above `viewportY`, one entry per row off the top |
| `assertWizardScreenIsWhollyVisible()`  | `e2e/pages/base-step.ts` (private) | Throws when that array is non-empty, quoting the lost rows and the screen              |

**Zero is the floor here and nowhere else.** An ordinary command is entitled to scroll, and `search`
and `list` do. What makes a wizard different is that `WizardLayout` sizes its root box to
`height={terminalHeight}` (`src/cli/components/wizard/wizard-layout.tsx`), so a correct frame fills
the viewport exactly and there is no room above it — and that a load which opens a wizard prints
nothing on the way there, because `init` and `edit` pass `captureStartupMessages` and the buffered
lines are painted as a band INSIDE the frame. Anything on the terminal when a full-height frame is
appended is scrolled off by it. The rule is therefore confined to `BaseStep`, the only page object
that drives `WizardLayout` screens.

**Two mechanisms put a line up there and the check does not tell them apart, because the user
cannot.** Either the frame is taller than the terminal and drives its own header off the top, or
something wrote to the terminal on the way to the mount and a frame that fits perfectly well pushed
it off. The second is what a `warn()` raised from `src/cli/stores/wizard-store.ts` during store
hydration used to do — raised after the load's buffer was drained, so it went to stderr as a plain
line and the first frame scrolled it away. That is the arm this guard caught; see
[wizard-flow.md](../features/wizard-flow.md) for the buffering window that fixed it.

**The tolerant version of this rule was written first and is measured to be blind.** Recording the
viewport at the first frame and demanding it not GROW reads as the safer invariant and cannot see
the defect worth catching: a layout that overflows by a constant — the shape a mis-measured terminal
height produces, and the shape a user reports as "the header is gone" — overflows the FIRST frame
too, so the baseline absorbs it and every later comparison agrees with it.

**What it cannot see:** a frame that overflowed and has already been replaced by one that fits. Ink
reprints an overflowing frame behind its own `clearTerminal`, which empties the emulator's scrollback
as well as its screen, so `linesAboveViewport()` gauges the frame painted NOW rather than a running
total. Read it while the frame is on screen.

### Cursor / Screen Queries (public / protected)

| Method                               | Access    | Returns                                                                                                                                                                                                                                                                               |
| ------------------------------------ | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `getOutput()`                        | public    | xterm's PROCESSED buffer — current screen plus whatever genuinely scrolled off. NOT a frame log (see below).                                                                                                                                                                          |
| `getScreen()`                        | public    | **NOT viewport-only, despite its name** — see the correction below. Reads absolute buffer lines `0 .. viewportY + rows`, i.e. scrollback PLUS viewport.                                                                                                                               |
| `getRawCursor()`                     | protected | Raw-output byte offset snapshot, for pairing with `*After` wait methods.                                                                                                                                                                                                              |
| `getSummaryDiffEntries(displayName)` | public    | Parses `SkillAgentSummary` panel; returns `{prefix, scope}[]` for the given display name (splitting the columns on the `│` divider so Project/Global scope is attributed per column). Internally calls `waitForWizardFooter` once before scraping — the only read query that does so. |

#### `getScreen()` is not viewport-only

`TerminalSession.getScreen()` (`e2e/helpers/terminal-session.ts`) does:

```ts
getScreen(): string {
  return this.readBufferLines(this.xterm.buffer.active.viewportY + this.xterm.rows);
}
```

`readBufferLines(n)` reads absolute buffer lines `0 .. n-1`. `viewportY` is the absolute row of the **top** of the viewport, so the range is **scrollback + viewport**, not the viewport. While a session has produced no scrollback (`viewportY === 0`) the two coincide, which is why the name reads as harmless: most specs assert positively, and most short sessions never scroll.

**Consequence: every `not.toContain(...)` on a screen is scrollback-sensitive.** Any text that was legitimately drawn earlier in the session is still matchable. Shrinking a terminal from 60 rows to 16 pushes the whole pre-shrink frame into scrollback, so `expect(screen).not.toContain(STEP_TEXT.BUILD)` fails against residue _whether or not the guard under test works_ — and the failure looks like a product bug rather than a harness one.

This is the converse of the `getOutput()` rule below, not a restatement of it. That rule warns against asserting a PAST frame was **present**; this one is about asserting a past frame is **absent** now.

**Prove a negative by ORDER or by BEHAVIOUR.** Order: `toMatch(/Please resize\.$/)` — the prompt is the last thing painted, so nothing was drawn after it. Behaviour: drive the session and assert the outcome the absent element would have changed. The method's own JSDoc states the same range and the same consequence, so the two agree.

#### `getOutput()` is a buffer, not a frame log

`BaseStep.getOutput()` → `TerminalSession.getFullOutput()` reads `xterm.buffer.active` — the current screen plus whatever genuinely scrolled off. **Ink redraws in place**, so when a frame fits the viewport (the common case at `TERMINAL_SIZE.TALL`) each repaint OVERWRITES the previous one and nothing enters scrollback. A value that was rendered and then re-rendered differently is not retrievable from it.

The only frame-accumulating surface is `TerminalSession.getRawOutput()` — every byte the process wrote, including text Ink later overwrote. It is reachable from the wizard objects (`InitWizard.getRawOutput()`, `EditWizard.getRawOutput()`, `WizardResult.rawOutput`) and from `TerminalScreen.getRawOutput()` / `waitForRawText` / `waitForTextAfter`, but is deliberately NOT exposed on `BaseStep`. Empirically verified against the real binary: a `+ E2E React` marker present in `getOutput()` before a `navigateDown()` is absent from `getOutput()` after it, while `getRawOutput()` still holds it.

Practical consequence for the toast-asserting methods (`toggleFocusedSkillAwaiting`, `toggleFocusedAgentAwaiting`, `confirmAwaiting`): toasts render in an absolutely-positioned row Ink rewrites in place, so the processed buffer has already lost the text by the time a test reads it. Those methods snapshot a raw cursor before the press and wait on raw output after it. The failure this replaces was a spec that pressed a navigation key and then read `getOutput()`, on the assumption that the accumulated output would still hold an earlier frame; it does not, and the assertion had also been silently depending on which row started focused (`SourceGrid` seeds focus with `firstFocusableRowIndex(rows, 0)` and `step-sources.tsx` passes no `defaultFocusedRow`, so focus starts on the FIRST focusable row). Capture before the key, or assert on raw output.

#### Resizing mid-session

`TerminalSession.resize(cols, rows)` resizes the PTY **and** the xterm instance. Both, always:

```ts
resize(cols: number, rows: number): void {
  this.ptyProcess.resize(cols, rows);
  this.xterm.resize(cols, rows);
}
```

Resizing only the PTY delivers `SIGWINCH` to the process but leaves xterm laying the new output out at the old geometry, so `getScreen()` reads a viewport the process never drew. Resizing only xterm never reaches the process at all, so nothing repaints. Either half alone desynchronises the emulator buffer from the process.

The size gate is enforced twice: once pre-Ink in `BaseCommand`, and again by the `WizardLayout` guard, which **replaces** the wizard tree when a running session shrinks under `MIN_TERMINAL_SIZE` (Ink lays a mounted subtree out at the small size regardless of what is drawn on top, so overlaying would not work). Selections survive the round trip.

**A resize paints twice, so a cursor-anchored negative does not rescue an absence assertion either.** Ink's own `resized()` handler re-renders the current tree synchronously, and only then does the dimensions hook's `setState` produce the guarded render. The post-cursor raw slice therefore holds `[old wizard frame] + [prompt frame]`, so `not.toContain("Framework")` fails there as surely as it does on `getScreen()`. Both helpers are built as **positive** cursor-anchored waits for exactly this reason.

Both are `BaseStep` members, so the [keypress rule](#page-object-keypress-rule-waitforwizardfooter) scope applies: valid only on `WizardLayout` screens.

**`pressEnterAndWaitFor` invariant:** the sentinel text MUST be unique to the next step's first frame — text appearing in the current footer (e.g. `"select"`) returns instantly on the Enter's own repaint and defeats the closed-loop retry.

### Where the keypress wait lives

`await this.waitForWizardFooter()` sits upstream of every PTY write in each composed method —
including inside loop bodies (`waitForItemVisible`, `navigateCursorToItem`,
`domain-step.deselectAll`, `build-step.focusSkill`,
`sources-step.commitFocusedColumnOnEveryRow`) and both composition
helpers (`pressEnterAndWaitFor`, `build-step.pressEnterWaitNewFrame`). **Raw primitives stay
cost-flat and do NOT wait** — moving the wait into `press*` would make every primitive pay a footer
probe, over-serialise tests that legitimately batch keystrokes, and hard-couple every primitive to a
footer that non-`WizardLayout` screens never paint. The cost of the composed-method form is
near-zero because `pollUntil` evaluates its predicate before its first `delay`, so a footer already
in scrollback returns synchronously.

**The hole this section used to describe is closed.** `abort()` on `InitWizard` and `EditWizard`
and `escape()` / `ctrlC()` on `DashboardSession` were once `void` and called unawaited across the
suite, which is why they could not be made to wait for anything: adding a wait meant making them
`async`, and that would have left a floating promise at every one of those call sites. All four are
now `async` and carry `INTERNAL_DELAYS.KEYSTROKE`, every call site awaits them, and `abortAndDestroy`
is what the specs mostly reach for — 25 spec files use it, against one that calls a bare `abort()`
(`init-wizard-sources-added-markers.e2e.test.ts`, for the deliberate reason recorded in
[standards/e2e/page-objects.md](../../standards/e2e/page-objects.md)). `InitWizard.escape()` was
deleted outright once its last caller went; `DashboardSession.escape()` is a different method on a
different class and is live.

What these four still do NOT do is wait on a sentinel before the press, and that is by design rather
than a residual gap: an abort is valid from any screen including ones that paint no `WizardLayout`
footer, and the dashboard paints none at all, so `waitForWizardFooter()` on either would hang for
the full `TIMEOUTS.WIZARD_LOAD` instead of settling. The keystroke delay is the whole guard, and it
is the same one every raw press primitive carries.

### Primitives That Already Wait

The only `BaseStep` members that do NOT `await waitForWizardFooter` before their action are:

- The **raw key-press primitives** — `pressEnter`, `pressSpace`, `pressKey`, `pressEscape`, `pressArrowDown/Up/Right`, `pressCtrlC` — by documented design intent (callers own the wait).
- The **read-only queries** — `getOutput`, `getScreen`, `getRawCursor` — they scrape without pressing.
- The **resize helpers** — `resizeBelowMinimum`, `resizeAboveMinimum`. They press no key; they snapshot a raw cursor, resize the PTY and emulator, and then wait on a cursor-anchored sentinel. A pre-resize footer wait would be pointless (the shrink invalidates the frame it waited for) and, at `BELOW_MINIMUM`, impossible — the guarded screen paints no footer.

Everything that presses a key now guards first: `navigateDown/Up/Right`, `abort`, `waitForItemVisible` and `navigateCursorToItem` (inside their loop bodies), `pressEnterAndWaitFor`, and the scraping query `getSummaryDiffEntries`. The one exception is `retryEnterUntil`'s internal press loop, which IS the stability primitive (its `confirmPainted(cursor)` post-condition detects a dropped Enter) and is guarded once at each call site instead.

## Page-Object Keypress Rule (waitForWizardFooter)

### Invariant

Every page-object method that sends a key press (keystroke, Space, Enter, Escape, arrow, Tab, literal char, `session.*`) MUST `await this.waitForWizardFooter()` **before** the press. Post-press waits do not substitute. This applies to every method on every step, not just the first interaction after a step transition.

**Precondition — `WizardLayout` screens only.** `waitForWizardFooter` matches the single footer string `"select"`, which only `WizardLayout` paints. The rule therefore binds `BaseStep` subclasses; a page object for a footer-less screen (`DashboardSession`) must gate on its own sentinel instead. Applying the guard to the dashboard once cost 72 failures across 35 files — see the findings at the end of this section.

### Why (PTY-Write-vs-React-Commit Race)

- **The general hazard (still live):** under parallel-suite contention a PTY write can land between React commit and the incoming frame's `useInput` handler registering. The keystroke reaches the new frame, but the handler hasn't mounted yet, so the press silently no-ops. In isolation the race is invisible (slack in the event loop); under load it surfaces as flake on whichever scenario loses the race first. This is why the rule applies to every keypress, not just the first after a transition.
- **Seed synchronously, never in a mount effect.** The `s` scope-toggle handler in `wizard.tsx` HOTKEY_SCOPE reads `store.focusedSkillId`. The store seeds it synchronously via `seedFocusedSkillForActiveDomain()` (`src/cli/stores/wizard-store.ts`) at hydrate (init and edit), at build-step entry and on every domain transition, from the same `buildCategoriesForDomain` derivation the grid renders. Seeding it from a post-mount `useEffect` instead leaves it `null` until the effect flushes, which `waitForWizardFooter` cannot observe — that is a race no page-object delay can close.

### How `waitForWizardFooter` Works

Defined on `BaseStep` (`e2e/pages/base-step.ts`), delegates to `TerminalScreen.waitForWizardFooter` (`e2e/pages/terminal-screen.ts`), which polls for the footer sentinel `"select"` in full output until `TIMEOUTS.WIZARD_LOAD` (45s — a footer-less screen burns the full 45s before the wait gives up).

**It then asserts as well as waits.** Once the sentinel settles, `assertWizardScreenIsWhollyVisible()` throws if `TerminalSession.linesAboveViewport()` is non-empty. So this method is not only the keypress rule's precondition — it is where every interactive spec picks up the "the whole frame is on the user's screen" obligation, at every press. Full mechanics: [the viewport guard](#every-wizard-keypress-asserts-the-frame-is-wholly-on-screen).

| Observes                                        | Does NOT observe                                 |
| ----------------------------------------------- | ------------------------------------------------ |
| Footer "select" text in PTY scrollback          | React `useEffect` having flushed                 |
| Frame layout having painted                     | `useInput` handler being registered on new frame |
| Wizard has reached a renderable, laid-out state | Store fields seeded by post-mount effects        |

**Scrollback hazard:** The footer "select" is emitted by every wizard step. On step transitions where previous frames sit in scrollback, `waitForWizardFooter` can return instantly on stale residue — use `waitForWizardFooterAfter(cursor)` (cursor-anchored, footer match post-cursor).

### Do not absorb a seeding race with a page-object delay

`BuildStep.toggleScopeOnFocusedSkill` is exactly two lines, and must stay that way:

```ts
async toggleScopeOnFocusedSkill(): Promise<void> {
  await this.waitForWizardFooter();
  await this.pressKey("s");
}
```

If a keypress ever depends on store state seeded by a post-mount effect that `waitForWizardFooter`
cannot observe, fix the seeding layer — seed synchronously in the store, as
`seedFocusedSkillForActiveDomain()` does — rather than widening a delay here.

### Tighter primitives, deliberately not built

`waitForWizardFooter` observes terminal output, not React lifecycle. Two tighter primitives are
rejected because synchronous store seeding solves the same problem without them:

- **ANSI focus-indicator parse** — detect that `CategoryGrid` emitted the focused skill's
  inverted-style marker before the keypress. Tighter than a footer match, but needs per-screen
  parsing logic.
- **Store snapshot probe** — a debug hook printing `focusedSkillId` to stderr, polled until
  non-null. Needs product-code instrumentation.

### Scope: Where the Rule Applies

- **All step page objects** (`e2e/pages/steps/*.ts`) — every public method that presses a key. NOT `e2e/pages/dashboard-session.ts`: the dashboard paints no wizard footer, so the guard can never match there.
- **`BaseStep` helpers** (`e2e/pages/base-step.ts`) — the `pressEnter` / `pressSpace` / `pressKey` / `pressEscape` / `pressArrowDown` / `pressArrowUp` / `pressArrowRight` / `pressCtrlC` primitives do NOT wait internally (there is no `pressArrowLeft`). Callers (subclass methods) are responsible.
- **Higher-level `BaseStep` methods** (`waitForItemVisible`, `navigateCursorToItem`, `navigate*`, `abort`, `pressEnterAndWaitFor`) — these send keystrokes and all `await waitForWizardFooter` before every press (inside the loop bodies for `waitForItemVisible` / `navigateCursorToItem`). See "Primitives That Already Wait" above. The one exception is `retryEnterUntil`'s internal press loop, which IS the stability primitive and is guarded once at each call site.
- **All interactions, not just keypress:** The rule applies to any `session.*` write — character input (`build-step.toggleLabels`), navigation, modifier keys, Ctrl+C. The race is between PTY write and React commit+effect, independent of the key's semantic.
- **Not applicable:** `render`-inspection methods (`getOutput`, `getScreen`, `getRawCursor`, `getScopeBadgesForSkill`, `getExclusiveCategorySelectedCount`, `getScopeBadgesForAgent`, `getSummaryDiffEntries`) — these only read output. (`findSkillGridPosition` no longer exists: the parse-then-dead-reckon navigator it backed was replaced by `focusSkill`'s closed-loop Tab-walk.)
