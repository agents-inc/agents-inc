# Code Generation Pipeline and Generated Artefacts

Three generators under `scripts/` produce checked-in source. **None ever runs as part of a build, a
test or a commit hook** — everything they emit is a working-tree file a human regenerated by hand.
Three **checks** cover them, and they do not all work the same way.

| Check                    | Command                                                               | How it detects staleness                 | Where it runs                                 |
| ------------------------ | --------------------------------------------------------------------- | ---------------------------------------- | --------------------------------------------- |
| `generate:schemas:check` | `generate:schemas` then `git diff --exit-code src/schemas/`           | Regenerates, then diffs the working tree | CI's `check-cli` job **and** `prepublishOnly` |
| `generate:types:check`   | `generate:types` then `git diff --exit-code src/cli/types/generated/` | Regenerates, then diffs the working tree | `prepublishOnly` **only**                     |
| `generate:matrix:check`  | `bun scripts/run-generate-matrix-package.ts --check`                  | Compares **in memory**; writes nothing   | CI's `check-web` job                          |

**`generate:matrix:check` is the only one that can report a file that is not committed at all.** The
other two ask `git diff` whether tracked files moved, and a diff cannot see a file that never
existed — so a generator that starts emitting a new output stays green while the committed set is
incomplete. The check-mode comparison treats a missing file as drift, by construction
(`matchesCommitted` requires `existsSync` before comparing bytes).

**`generate:types:check` is deliberately absent from `ci.yml`**, and adding it there would break
every run: `generate:types` reads a `skills` checkout, and every `ci.yml` job checks out this
repository and nothing else. It lives in `prepublishOnly` because the publishing machine has the
marketplace beside it. Do not "complete the pair" in `ci.yml`.

**One runner does have the marketplace, and it is not `ci.yml`.**
`.github/workflows/regenerate-catalog.yml` checks `agents-inc/skills` out explicitly and runs all
three generators against it — so "no runner anywhere can run `generate:types`" is not the reason,
and a reader who finds that workflow has not found a stale document. The reason is per-workflow:
`ci.yml`'s jobs have no such checkout and are not going to grow one, because their subject is this
repository's own tree.

### The marketplace has three downstream artefacts, not one

**Any change to the skills marketplace requires all three generators to run and all three outputs to
be committed together.** `generate:types` (skills repo -> `src/cli/types/generated/`) is the only one
that reads the marketplace, and both of the others read what it wrote: `generate:matrix` copies those
files into `packages/matrix/src/vendor/generated/`, and `generate:schemas` copies `SKILL_SLUGS` and
`CATEGORIES` verbatim into `metadata.schema.json`'s `slug` and `category` enums (see Ordering below).

`generate:schemas` is the one that hides — the names `generate:types` and `generate:matrix` do not
suggest it, and a marketplace change is not obviously "about" JSON schemas. Omitting it produces a
regeneration that reviews clean and merges, and then turns `main` red on the **next** push, in
`check-cli`'s `generate:schemas:check`, one commit after the change that caused it and in a job whose
name mentions neither schemas nor the marketplace. Omitting `generate:matrix` fails the same way one
job over: `check-web` regenerates the matrix package and compares.

The write order is `generate:types`, then `generate:schemas`, then `generate:matrix` — and
`bun run generate` (below) is that sequence as one command.

**This document owns three counts:** the number of entries in `SCHEMA_ENTRIES` (**10**), the number
of files in `src/schemas/` (**12**), and the number of files `generate:matrix` emits (**8** —
`VENDORED_TYPE_FILES`'s seven plus `AGENTS_FILE`). The
first two disagreeing is the load-bearing invariant below. Union sizes (`SkillId`, `SkillSlug`,
`Category`, `Domain`, `AgentName`) belong to `reference/type-system.md` and the Zod schema count to
`reference/types/zod-schemas.md` — they are named here, never quantified.

## The three generators

| Generator                            | npm script                                                        | Runtime | Writes to                        | Reads                                                                                                                                                                                                                                                |
| ------------------------------------ | ----------------------------------------------------------------- | ------- | -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scripts/generate-source-types.ts`   | `generate:types` -> `bun scripts/generate-source-types.ts`        | `bun`   | `src/cli/types/generated/`       | The skills repo sibling to the monorepo root (`../skills` relative to the repo root — i.e. `packages/cli/../../../skills` — by default, overridable as `argv[2]`), `src/agents/**/metadata.yaml`, and three `lib/configuration/default-*.ts` modules |
| `scripts/generate-json-schemas.ts`   | `generate:schemas` -> `bun scripts/generate-json-schemas.ts`      | `bun`   | `src/schemas/`                   | Ten named exports from `src/cli/lib/schemas.ts`, plus `CATEGORIES` from `src/cli/types/generated/source-types.ts`                                                                                                                                    |
| `scripts/generate-matrix-package.ts` | `generate:matrix` -> `bun scripts/run-generate-matrix-package.ts` | `bun`   | `packages/matrix/src/` (8 files) | Seven files under `src/cli/types/`, `src/agents/*/*/metadata.yaml`, and this package's own `defaultStacks`                                                                                                                                           |

**All three run under `bun`, and `bun` is undeclared.** It is in neither `dependencies`,
`devDependencies` nor `engines` (which names only `node >=22`) — it is assumed present, as it is on
every machine and every CI job in this repository. `prettier` and `tsc`, by contrast, are local
binaries.

**Neither `npx` nor `npm` may appear in a script in this package.** `tsx` is in no dependency list
and absent from `node_modules/.bin`, so an `npx tsx` script reaches the registry on demand and the
generator stops working offline.

### Ordering: `generate:types` must run first

`generate-json-schemas.ts` imports `src/cli/lib/schemas.ts`, which imports `SKILL_SLUGS` and
`CATEGORIES` from `src/cli/types/generated/source-types.ts` — the _other_ generator's output. Those
two arrays are `z.enum()` inputs for `metadataValidationSchema`, so they are copied verbatim into the
emitted `metadata.schema.json` as the `slug` and `category` enums. **Regenerating schemas without
first regenerating types republishes the previous run's vocabulary.** This is not hypothetical: the
shipped `metadata.schema.json` has drifted this way before, its `slug` and `category` enums lagging
`source-types.ts` far enough behind to reject legitimate slugs and categories outright.

The dependency does **not** run the other way at runtime. `generate-source-types.ts` reaches
`src/cli/types` only through `import type`, and its five value imports
(`GENERATED_AT_BUILD` from `consts.ts`, `default-categories`, `default-rules`, `default-stacks`,
and `mergeMatrixWithSkills` from `matrix/skill-resolution`) transitively reach `consts.ts` and
`utils/logger.ts`, neither of which imports a generated file. So the type
generator bootstraps from an empty `src/cli/types/generated/` — but `tsc -p tsconfig.scripts.json`
does **not**, because type-only imports still have to resolve.

## Invocation surface, and what actually gates it

| Script                   | Definition                                                                      |
| ------------------------ | ------------------------------------------------------------------------------- |
| `generate`               | `bun run generate:types && bun run generate:schemas && bun run generate:matrix` |
| `generate:types`         | `bun scripts/generate-source-types.ts`                                          |
| `generate:schemas`       | `bun scripts/generate-json-schemas.ts`                                          |
| `generate:matrix`        | `bun scripts/run-generate-matrix-package.ts`                                    |
| `generate:matrix:check`  | `bun scripts/run-generate-matrix-package.ts --check`                            |
| `generate:schemas:check` | `bun run generate:schemas && git diff --exit-code src/schemas/`                 |
| `generate:types:check`   | `bun run generate:types && git diff --exit-code src/cli/types/generated/`       |
| `typecheck:scripts`      | `tsc -p tsconfig.scripts.json --noEmit`                                         |

**`generate` is the composite, and it is the one to call.** It encodes the dependency order in the
only place that can be authoritative, so no caller has to re-derive the sequence or remember that
there are three generators rather than two — the failure this exists to prevent. Its `package.json`
`"//generate"` note records that. It covers the **write** path only: the `:check` variants stay
separate because the gates deliberately run different subsets of them in different jobs.
`.github/workflows/regenerate-catalog.yml` still spells the three steps out one per step and could
call this instead; nothing in this repository is broken by it not doing so yet.

**There is one more entry point, in another workspace, and it is a different command with the same
name.** `packages/matrix`'s own `generate` script is `cd ../cli && bun run generate:matrix` — a
one-line delegation to a single generator, not a second writer and not this package's composite. It
is kept alive because the files the generator emits carry the header line ``Do not edit manually —
run `bun run generate` in packages/matrix.``: deleting the script would make every emitted file
instruct the reader to run something that does not exist. Its `package.json` records the reason in a
`"//generate"` field. **A generator whose output embeds its own invocation command is coupled to
that command** — moving one means keeping an entry point at the old name or rewriting every header.
Read the header's `in packages/matrix` as load-bearing: the same words in `packages/cli` run all
three.

Where each one runs:

| Gate                | Composition                                                                                                                                                       | Runs a generator?                                                           |
| ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `prepublishOnly`    | `format:check && lint && typecheck && generate:schemas:check && generate:types:check && build && test`                                                            | **Schemas and types**, via their checks                                     |
| `.husky/pre-commit` | `bunx lint-staged` -> `bunx turbo run lint typecheck test --filter='...[HEAD]'` (changed packages and dependents)                                                 | **No**                                                                      |
| `.husky/pre-push`   | `bunx turbo run lint test test:e2e`, once per side touched                                                                                                        | **No**                                                                      |
| GitHub Actions      | `ci.yml`: `check-cli` runs `generate:schemas:check`; `check-web` runs `generate:matrix:check` (from `packages/cli`, before its own suites)                        | **Schemas and matrix** (`ci.yml` has no marketplace checkout, so not types) |
| GitHub Actions      | `regenerate-catalog.yml`: checks `agents-inc/skills` out, runs `generate:types` -> `generate:schemas` -> `generate:matrix`, opens a pull request with the outputs | **All three, as writers** — the only workflow that can run `generate:types` |

**`generate:matrix:check` is run by `check-web`, not `check-cli`, and from `packages/cli` anyway.**
The files it guards belong to the web side; the writer and every input belong to the CLI. The job
sets `working-directory: packages/cli` for that one step.

The two hook rows split on 2026-08-07; before that, everything in the `pre-push` row ran at commit
time. **Neither row is a full-suite run.** `pre-commit` runs `lint`, `typecheck` and `test` for the
packages the commit moves and the packages that depend on them — turbo's `...[HEAD]` filter, which
does see the staged set, because a one-ended range makes turbo ask `git diff --cached` alongside its
`diff-tree`. `typecheck` joined that line on 2026-08-08; until then no hook had ever run it.
`pre-push` is the coarse one: it reads the paths in `'@{push}..HEAD'` and decides which **side** of
the monorepo moved — a path under `packages/cli/` or `packages/matrix/` sets the CLI side; any other
path under `apps/` or `packages/` sets the web side; a root tooling file (`package.json`,
`bun.lock`, `turbo.json`, `tsconfig.json`, or anything under `.husky/` or `.github/`) sets **both**,
because it changes how both sides install, build and run — and then runs that side's **whole**
`lint test test:e2e` set through turbo, `--filter=agents-inc` for the CLI and
`--filter='!agents-inc'` for the web. Only `packages/cli` and `apps/editor` define `test:e2e`, so
each side runs the end-to-end suite it owns and nothing else, and a push confined to documentation
or other root files sets neither flag and runs neither suite. ESLint runs in **both** places as of 2026-08-08,
and the split is the point: `lint-staged` runs `eslint --fix` over the staged files as the fast
half, and the whole-workspace `lint` on the turbo line stays because a workspace run sees reports a
staged-file run cannot — the type-aware rules read a whole program, so a staged change can raise a
report in a file the commit does not touch. (`lint-staged` could not host ESLint at all until
recently, because flat config resolved from the working directory; that stopped being true at
ESLint 10, which resolves from the directory of the file being linted. See
[`../monorepo-layout.md`](../monorepo-layout.md) -> "The commit and push hooks" for the mechanism
and the measurements.)

**The push tier's coarseness is deliberate, and narrowing _it_ is the regression.** The
changed-package filter cannot be trusted on its own: a commit to `packages/matrix` once selected
matrix and `apps/editor` but **not** `apps/server`, which depends on matrix too, so a change that
broke the API worker committed clean. Scoping by side cannot miss a dependent, because it never
tries to work out what the dependents are — which is precisely what makes the fast filter safe at
commit time now that the slow one stands behind it.

**Publish now checks both artefacts.** `prepublishOnly` is
`format:check && lint && typecheck && generate:schemas:check && generate:types:check && build && test`,
so a stale `src/schemas/` or `src/cli/types/generated/` stops the publish rather than shipping — which
matters because `src/schemas/` is listed in package.json `files` and the `raw.githubusercontent.com`
URLs in `SCHEMA_PATHS` serve whatever is on `main`. What is still unguarded is the window between
commits: neither check runs in the pre-commit hook, so a stale artefact can sit on `main` until the
next CI run (schemas) or the next publish (types).

Two further asymmetries in the same table:

- **`typecheck` covers `scripts/`.** The root `tsconfig.json` includes `src/**/*`
  only; `tsconfig.scripts.json` extends it with `include: ["scripts/**/*"]`, `noEmit` and
  `allowImportingTsExtensions` (the last is required because `generate-json-schemas.ts` imports
  `../src/cli/lib/schemas.ts` with the extension). The `typecheck` script runs **three** tsc
  programs — `tsconfig.json`, `tsconfig.scripts.json` and `e2e/tsconfig.json` — so `scripts/` is
  type-checked at pre-commit, in CI and at publish. `typecheck:scripts` still exists as a standalone
  entry point, but it is not the only way to reach that program.
- **ESLint also covers `scripts/`.** `TYPESCRIPT_SOURCES` in `eslint.config.js` includes
  `scripts/**/*.ts`, and `parserOptions.projectService.allowDefaultProject` names `scripts/*.ts`
  explicitly, with a comment recording why: the project service only discovers `tsconfig.json` and
  never finds `tsconfig.scripts.json`. That carve-out is unaffected by `typecheck` gaining the
  scripts program — the two mechanisms are separate.

## Invariant: `src/schemas/` is 10 generated files + 2 hand-written files

**This is the trap the rest of this document exists for.** `SCHEMA_ENTRIES` in
`scripts/generate-json-schemas.ts` declares exactly ten filenames. `src/schemas/` contains twelve.

| File                                    | Origin              |
| --------------------------------------- | ------------------- |
| `agent.schema.json`                     | generated           |
| `agent-frontmatter.schema.json`         | generated           |
| `hooks.schema.json`                     | generated           |
| `marketplace.schema.json`               | generated           |
| `metadata.schema.json`                  | generated           |
| `custom-metadata.schema.json`           | generated           |
| `plugin.schema.json`                    | generated           |
| `skill-frontmatter.schema.json`         | generated           |
| `stacks.schema.json`                    | generated           |
| `stack.schema.json`                     | generated           |
| **`project-config.schema.json`**        | **hand-maintained** |
| **`project-source-config.schema.json`** | **hand-maintained** |

Neither of the last two appears in `SCHEMA_ENTRIES`, so the generator will never emit them and never
overwrite them. The consequence is a **silently asymmetric edit rule**:

- Hand-editing one of the ten is **reverted** by the next `npm run generate:schemas`. Fix the Zod
  schema in `src/cli/lib/schemas.ts` instead, or add a `postProcess` hook.
- Hand-editing one of the two is **correct and required** — there is no other way to change them.

Nothing in the files themselves marks the difference: all twelve carry the same `$schema`, `$id`,
`title`, `description` header shape, and none carries an "AUTO-GENERATED" banner (unlike the two
files in `src/cli/types/generated/`, which do). The only on-disk tell is mtime — the ten generated
files share one timestamp from their last regeneration run, the two hand-written ones are months
older. **Verify against `SCHEMA_ENTRIES`, never against the file header.**

Lineage, so this reads as a deliberate state rather than an oversight: release 0.24.3 introduced the
generator, moved ten schemas to `z.toJSONSchema()` and removed the rest of the hand-maintained set.
These two were not migrated, because no Zod schema in `schemas.ts` describes the consumer-facing
`.claude-src/config.yaml` shapes they validate.

## How a schema is emitted

`generate()` at the tail of `scripts/generate-json-schemas.ts` is a straight loop over
`SCHEMA_ENTRIES`. Per entry:

1. `z.toJSONSchema(entry.schema, { target: "draft-07" })`.
2. Build `output` with `$schema` (taken from the generated object), then `$id`, `title`,
   `description` from `entry.metadata`, then **all remaining generated keys spread last**, with only
   `$schema` filtered out of the spread.
3. Run `entry.postProcess?.(output)` if present.
4. `writeFileSync(JSON.stringify(output, null, 2) + "\n")`.

After the loop, a single `execSync('bunx prettier --write "<SCHEMAS_DIR>/"')` formats the **whole
directory**.

Three consequences worth having in hand:

- **The metadata overlay is key-ordering only, not precedence.** Because the generated keys are
  spread _after_ `$id`/`title`/`description`, any `$id`, `title` or `description` that
  `z.toJSONSchema` itself produces (e.g. from a Zod `.meta()`/`.describe()`) **overrides** the
  `SCHEMA_ENTRIES` metadata while keeping the metadata's position in the key order. No entry hits
  this today — every emitted `title` matches its `SCHEMA_ENTRIES` value — but the failure mode is a
  silently ignored `metadata` block, not an error.
- **The blanket prettier pass touches the two hand-written files too.** It reformats the whole
  directory, not the ten files just written. `src/schemas/` is not in `.prettierignore`, so this
  keeps the directory consistent with `format:check` — and it means `generate:schemas:check` can
  report a diff on a hand-written file that was merely unformatted.
- **`generate:schemas:check` uses `git diff`, not `git diff HEAD`.** It compares the working tree to
  the _index_. Regenerated output that has already been staged produces a clean exit. Read the check
  as "the working tree matches what regeneration produces", not "the commit is up to date".

### `postProcess` hooks

There are exactly two, and the audit trail for this doc had them attributed to the wrong entries —
verify against the source, not against a summary:

| Target                        | Hook                             | What it does                                     |
| ----------------------------- | -------------------------------- | ------------------------------------------------ |
| `custom-metadata.schema.json` | inline arrow                     | `delete schema.additionalProperties` (root only) |
| `stacks.schema.json`          | `injectSubcategoryPropertyNames` | Recursively injects a `propertyNames.enum`       |

`plugin.schema.json` has **no** `postProcess`.

**The custom-metadata hook deletes the ROOT key only.** Custom skills may carry extra top-level
fields, so root `additionalProperties: false` has to go — but the emitted file still carries a nested
`additionalProperties: false` under `properties/forkedFrom`. A custom skill's `forkedFrom` object
therefore still rejects unknown fields while the document root accepts them. That asymmetry is a
consequence of the hook's shape, not a decision recorded anywhere.

### `injectSubcategoryPropertyNames` — the recorded "why", and the fact that it no longer fires

The doc-comment above the function records the reasoning, and it is the single piece of "why" in this
area that a future agent would otherwise have to re-derive from Zod internals:

> `stackAgentConfigSchema` uses `z.record(z.string(), …)` with `superRefine` for runtime key
> validation, **because `z.record(z.enum(...))` would demand every enum value as a mandatory
> property**. `z.toJSONSchema()` cannot represent a `superRefine`, so the `propertyNames` enum is
> injected into the emitted JSON schema afterwards, **for IDE validation only**.

Keep that paragraph. The `z.record(z.enum())` constraint is the reason the Zod schema looks lax, and
an agent "tightening" it to `z.enum` would break every stack config that omits a category.

**However — as emitted today, the hook is inert.** Its detection guard requires the stringified
`additionalProperties` to contain the literal SkillId pattern
`(web|api|cli|mobile|infra|meta|security)-.+-.+`. That string does not appear in **any** file in
`src/schemas/`, and the emitted `stacks.schema.json` contains **zero** `propertyNames` objects
carrying an `enum` — every one is still the bare `{ "type": "string" }` the guard is meant to
replace.

The mechanism: the skill-assignment union in `stackAgentConfigSchema` is built from
`z.string() as z.ZodType<SkillId>` and `skillAssignmentSchema`, whose `id` is a plain
`z.string().min(1)`. **`as z.ZodType<SkillId>` is a TypeScript-level cast with no runtime Zod
refinement**, so `z.toJSONSchema` emits `{"type": "string"}` with no `pattern` — and the guard's
`includes()` test can never match. `STACK_SUBCATEGORY_ENUM`, and with it the generator's entire
`CATEGORIES` import, is dead at runtime.

Practical reading for an implementing agent:

- Do not cite `stacks.schema.json` as the place a stack's category keys are enum-validated. It is
  not, at any layer of the emitted schema.
- If you intend to restore the injection, the fix is at the **guard**, not at the enum — either
  detect the stack-agent shape structurally, or give `skillAssignmentSchema.id` a real `.regex()` so
  the pattern reaches the JSON schema. The second option changes runtime validation behaviour and is
  not a free move.

### `z.toJSONSchema` behaviours this pipeline depends on

Established from the emitted artefacts, not from the Zod docs:

| Behaviour                                                                              | Evidence in `src/schemas/`                                                                                   |
| -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| A plain `z.object()` emits `additionalProperties: false` — `.strict()` is not required | `stacksConfigSchema` has no `.strict()`, yet `stacks.schema.json` carries root `additionalProperties: false` |
| `z.record(k, v)` emits `propertyNames` + `additionalProperties: <v>`                   | `hooks.schema.json` root; the `agents` node of `stacks.schema.json`                                          |
| `superRefine` emits nothing                                                            | the whole reason `injectSubcategoryPropertyNames` exists                                                     |
| `x as z.ZodType<T>` emits nothing                                                      | `stacks.schema.json` `id` is `{"type": "string"}` despite the `SkillId` cast                                 |
| `z.enum(ARRAY)` inlines the array                                                      | `metadata.schema.json` `slug`/`category` enums are `SKILL_SLUGS`/`CATEGORIES` verbatim                       |

The first row is the one that surprises: it means every generated schema is closed by default, and
opening one requires a `postProcess` — which is exactly what `custom-metadata` does.

## `generate-source-types.ts` — two phases, two files

`generate()` runs `extractSkills()` (walks `<skills-source>/src/skills/*/`, reading `metadata.yaml`
and the `SKILL.md` frontmatter), then `extractAgents()` (walks `src/agents/<group>/<agent>/metadata.yaml`,
skipping `_templates`), then the two phases, then `bunx prettier --write` over the output directory.

| Phase | Function         | Output                                    | Emits                                                                                                                                      |
| ----- | ---------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 1     | `generatePhase1` | `src/cli/types/generated/source-types.ts` | `SKILL_MAP`, `SkillSlug`, `SkillId`, `SKILL_SLUGS`, `SKILL_IDS`, `CATEGORIES`, `Category`, `DOMAINS`, `Domain`, `AGENT_NAMES`, `AgentName` |
| 2     | `generatePhase2` | `src/cli/types/generated/matrix.ts`       | `BUILT_IN_MATRIX`, `SKILL_IDS_BY_CATEGORY`, `CATEGORIES_BY_DOMAIN`                                                                         |

Union sizes are owned by `reference/type-system.md`; the `BUILT_IN_MATRIX` composition (via
`mergeMatrixWithSkills(defaultCategories, defaultRules.relationships, skills)`) is documented in
`reference/features/skills-and-matrix.md`.

**Determinism is engineered, not incidental.** Every emitted list is sorted (`SKILL_MAP` and
`SKILL_SLUGS` by slug, `SKILL_IDS`/`CATEGORIES`/`DOMAINS`/`AGENT_NAMES` by value, and both derived
lookup maps through `sortedGroupBy`, which sorts outer keys _and_ inner arrays). Phase 2 additionally
overwrites `matrix.generatedAt` with the fixed string `"build"` — a timestamp there would make every
regeneration a diff. Preserve both properties in any change; without them
`generate:schemas:check`-style diffing is worthless for the type artefacts too.

**Skips are warnings; contract violations are throws.** A skill directory missing `metadata.yaml` or
`SKILL.md`, or missing SKILL.md frontmatter, logs `⚠ Skipping` and continues; a skill carrying
`custom: true` is skipped silently (custom skills register at runtime). But a missing
`cliDescription` or `displayName` **throws**, as does a duplicate slug or duplicate skill ID in
`generatePhase1`. Uniqueness of both keys is a hard precondition of `SKILL_MAP`, which is the basis
for the `SkillSlug`/`SkillId` unions.

**Boundary casts are deliberate and narrowly scoped.** `extractSkills` narrows YAML strings to union
members at the parse boundary. `resolveStack` uses two field-level casts (`skills`, `allSkillIds`)
rather than one blanket `as ResolvedStack`; the blanket cast was removed precisely because it hid
field mismatches (`agent-findings/2026-07-19-untypechecked-scripts-hid-phantom-tags-and-invalid-skillids.md`).
Do not re-widen it.

**Two of the three keep their entry point out of module scope, by different means.**
`generate-source-types.ts` ends with an `isDirectRun` check
(`import.meta.filename === process.argv[1]`); `generate-matrix-package.ts` exports `generate` /
`check` and puts argv, logging and the exit code in a separate `run-generate-matrix-package.ts`.
Either shape lets a spec import the module without writing files. `generate-json-schemas.ts` calls
`generate()` unconditionally at module scope — which is why it has no test and cannot get one
without that being changed first.

### Traps in the emitted TypeScript

- **`matrix.ts` emits its import block unconditionally.** `CategoryMap`, `ResolvedSkill`,
  `ResolvedStack`, `SkillSlugMap`, `AgentName` and `SkillSlug` each appear exactly once in the file —
  in the import statement, and nowhere else. They are unused imports by construction.
- **That is why the whole `generated/` directory sits in ESLint's `globalIgnores`.** The entry is
  `src/cli/types/generated/**`, and its comment reads "Emitted by `npm run generate:types` — fix the
  generator, not the output." Take the instruction literally: a lint fix applied to the artefact is
  erased by the next run.
- **The generated directory is _not_ prettier-ignored.** `.prettierignore` covers `dist/`,
  `node_modules/`, `.cache/`, `coverage/`, `*.js.map` and `.claude_backup/` — not
  `src/cli/types/generated/` and not `src/schemas/`. The types and schemas generators each run
  prettier over their own output for exactly this reason; skipping that step makes `format:check`
  fail. **`generate-matrix-package.ts` is the exception and must stay one:** it writes outside this
  package, and the repository-root `.prettierignore` names `packages/matrix/src/vendor/` and
  `packages/matrix/src/generated/`, so formatting them would show up as drift against the generator
  on the next check.
- **`tsc` still type-checks the generated files** (`include: ["src/**/*"]`), so a generator change
  that emits invalid TypeScript fails `npm run typecheck` even though ESLint ignores the output.
- **`matrix.ts` imports from `../matrix`, which re-exports from `./generated/source-types`.**
  `src/cli/types/matrix.ts` value-re-exports `CATEGORIES` and `DOMAINS`, `types/skills.ts`
  re-exports `SKILL_MAP`/`SKILL_IDS`/`SKILL_SLUGS`, and `types/agents.ts` re-exports `AGENT_NAMES`.
  The generated Phase 2 file therefore points back through the hand-written barrel at the generated
  Phase 1 file. Type-only in the emitted direction, so no runtime cycle — but it does mean Phase 1's
  output must exist before Phase 2's output type-checks.

## `generate-matrix-package.ts` — the single writer of `packages/matrix`'s generated surface

`packages/matrix` is a private workspace holding browser- and Worker-safe data for `apps/editor` and
`apps/server`. Everything under its `src/vendor/` and `src/generated/` is emitted by this script and
nothing else; `src/read-model/`, `src/schema.ts` and `src/seed.ts` are hand-written code with their
own tests and are **not** touched.

**The eight emitted files, in emission order** (paths relative to `packages/matrix/`, and this
document owns the count):

| #   | Emitted file                           | Produced by            | From                                              |
| --- | -------------------------------------- | ---------------------- | ------------------------------------------------- |
| 1   | `src/vendor/matrix.ts`                 | `vendoredTypeFiles`    | `src/cli/types/matrix.ts`, copied verbatim        |
| 2   | `src/vendor/skills.ts`                 | `vendoredTypeFiles`    | `src/cli/types/skills.ts`                         |
| 3   | `src/vendor/agents.ts`                 | `vendoredTypeFiles`    | `src/cli/types/agents.ts`                         |
| 4   | `src/vendor/config.ts`                 | `vendoredTypeFiles`    | `src/cli/types/config.ts`                         |
| 5   | `src/vendor/stacks.ts`                 | `vendoredTypeFiles`    | `src/cli/types/stacks.ts`                         |
| 6   | `src/vendor/generated/matrix.ts`       | `vendoredTypeFiles`    | `src/cli/types/generated/matrix.ts`               |
| 7   | `src/vendor/generated/source-types.ts` | `vendoredTypeFiles`    | `src/cli/types/generated/source-types.ts`         |
| 8   | `src/generated/agents.ts`              | `agentDefinitionsFile` | every `src/agents/<flavor>/<agent>/metadata.yaml` |

The list is `VENDORED_TYPE_FILES` plus `AGENTS_FILE` — two module-level constants. Adding an output
means adding a name there, and `generate:matrix:check` will report the new file as drift until it is
committed.

A ninth file, `src/generated/stack-preloads.ts`, was emitted until CLI-400 (2026-08-06). It carried
the load flags the built-in stacks hand-wrote, flattened to one verdict per skill because the editor
had one toggle per skill — so a framework preloaded on its own domain's developer claimed to preload
on every summoner in the stack too. The flags are gone from `defaultStacks` and the mapping in
`packages/matrix/src/read-model/preload-defaults.ts` answers instead: `expandStack` resolves each
`(skill, sub-agent)` pair through `resolveAssignment`, so there is per-agent fidelity where the
flattening lost it, and nothing left for the generator to write.

**Emission properties, all deliberate:**

| Property                               | Mechanism                                                                                                        |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `AGENT_DEFINITIONS` is sorted          | `.sort((a, b) => a.id.localeCompare(b.id))` in `agentDefinitionsFile` — an unsorted emit would diff on every run |
| Absent metadata fields are omitted     | `serializeAgentDefinition` filters `value !== undefined`, so no key is written as an explicit `undefined`        |
| `_templates` is skipped                | `RESERVED_FLAVOR_PREFIX = "_"` filters the flavor directories                                                    |
| `flavor` and `path` come from the tree | `path` is `${flavor}/${agent}`, derived from the directory, not from `metadata.yaml`                             |

**Two entry points, and the generator is not one of them.** `generate-matrix-package.ts` exports
`generate({ matrixRoot, cliRoot? })` and `check({ matrixRoot, cliRoot? })` and **runs nothing at
module scope**, so importing it writes no files. `scripts/run-generate-matrix-package.ts` owns
`process.argv`, the console output and the exit code (`EXIT_CODES.ERROR` on drift). That split is
what makes the generator testable — the failure mode `generate-json-schemas.ts` is stuck with.

`cliRoot` defaults to the package root and is a parameter so the suite can drive the generator
against a fixture checkout; `matrixRoot` is resolved by the wrapper as `../../matrix`.

## Where the artefacts are consumed

### `src/schemas/*.json`

`SCHEMA_PATHS` in `src/cli/consts.ts` builds
`https://raw.githubusercontent.com/agents-inc/agents-inc/main/packages/cli/src/schemas/<file>` URLs from the private
`SCHEMA_PKG_PREFIX` constant, for `# yaml-language-server: $schema=` comments emitted by
`yamlSchemaComment()` (`src/cli/utils/yaml-schema.ts`). The key/URL table is owned by
`reference/utilities.md` — not restated here. Two facts that belong to _this_ doc:

- **Two of its keys — `projectConfig` and `projectSourceConfig` — point at the hand-maintained
  pair.** An agent tracing a `SCHEMA_PATHS` entry back to a Zod schema will find nothing for those
  two, and that is correct, not a broken link.
- **Only one key has a runtime consumer.** `SCHEMA_PATHS.metadata` is used by
  `src/cli/lib/skills/skill-metadata.ts`. `customMetadata`, `agent`, `marketplace`,
  `projectConfig`, `projectSourceConfig` and `stacks` currently have **zero** call sites — they are
  addressable URLs, not live wiring. Do not infer from a `SCHEMA_PATHS` entry that the CLI writes
  that `$schema` comment anywhere.

The URLs resolve for published consumers because `src/schemas/` is listed in package.json `files`.
Note the coupling this creates: the URL is pinned to `main`, so a published CLI validates against
whatever the branch holds — not against the schemas that shipped in its own tarball.

### `src/cli/types/generated/*.ts`

| Artefact                                  | Importers                                                                                                                                                                    |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `generated/source-types.ts`               | `types/skills.ts`, `types/matrix.ts`, `types/agents.ts`, `lib/schemas.ts`, `utils/type-guards.ts`, `e2e/fixtures/project-builder.ts`, and `scripts/generate-json-schemas.ts` |
| `generated/matrix.ts` (`BUILT_IN_MATRIX`) | `lib/loading/source-loader.ts`, `lib/matrix/matrix-provider.ts`, plus four test files                                                                                        |

**There is a consumer outside this package.** Both files are copied verbatim into
`packages/matrix/src/vendor/generated/` by `generate:matrix` (above), which is what lets
`apps/editor` and `apps/server` read the catalog with no CLI runtime.

What enforces freshness is the `check-web` job in `.github/workflows/ci.yml`, which runs
`generate:matrix:check` from `packages/cli` before any of the suites — a stale catalog means
something was left uncommitted, and saying so takes seconds.

So **regenerating `src/cli/types/generated/` has consequences beyond this package:** leaving
`packages/matrix` unregenerated turns CI red. Both regenerations belong in the same commit.

## Test surface

| Covered                                                  | Not covered                                         |
| -------------------------------------------------------- | --------------------------------------------------- |
| `scripts/generate-source-types.test.ts` — **35 tests**   | `scripts/generate-json-schemas.ts` — **zero tests** |
| `scripts/generate-matrix-package.test.ts` — **20 tests** |                                                     |

Re-derive both by running the file (`npx vitest run scripts/<name>.test.ts`), never by counting
`it(` — `scripts/` as a whole is **139 tests across 7 files**, the other five being the four
`check-shared-*` suites and `check-enumeration-drift`.

The matrix-package suite runs `generate` and `check` against the **real** `packages/matrix` as well
as against a fixture `cliRoot` in a temp directory. It pins: that importing the module writes
nothing (every mtime under `packages/matrix/src/` unchanged across a `vi.resetModules()` re-import);
the emitted vendor file set; `AGENT_DEFINITIONS` ordering,
its one-entry-per-`AgentName` completeness and its per-agent fields; byte-identity against the
committed tree and across two consecutive runs; and that check mode reports the drifted path and
leaves the tree untouched. It uses the shared harness — `createTempDir` / `cleanupTempDir`,
`renderAgentYaml`, `AGENT_DEFS` — not bespoke fixtures.

The type-generator suite exercises `sortedGroupBy`, `resolveStack`, `extractSkills`, `extractAgents`,
`generatePhase1` and `generatePhase2` against a temp directory, using `createTempDir` /
`cleanupTempDir` from `src/cli/lib/__tests__/test-fs-utils`, `createMockExtractedSkill` from the
skill factories, and `renderSkillMd` from the content generators — i.e. the same shared harness as
`src/`, not bespoke fixtures. It is picked up by the `unit` vitest project, whose `include` names
`scripts/**/*.test.ts` explicitly; that is the only reason `scripts/` is in the test run at all.

The schema generator has no test because it cannot be imported without executing (no `isDirectRun`
guard) and because `SCHEMAS_DIR` is hardcoded to `../src/schemas` with no override — importing it in
a spec would rewrite the repository's schemas and shell out to prettier. Both would have to change
before a test is possible.

**Fixtures here must use real union members and real fields.** A phantom `tags` field that
`ExtractedSkillMetadata` never had, and fabricated non-union skill IDs, both survived in this suite
while `scripts/` sat outside the typecheck programs. Do not reintroduce either by casting.
`reference/testing/infrastructure.md` carries the harness.

## Known gaps (open — do not paper over)

1. **`generate:types:check` runs at publish only, not in `ci.yml`.** It is in `prepublishOnly` and
   cannot move into `ci.yml`, whose jobs check out this repository alone while `generate:types`
   reads a `skills` checkout — do not "complete the pair" there.
   `regenerate-catalog.yml` is the exception that proves the shape: it checks the marketplace out
   and runs the generator as a **writer**, which is a different job from checking a committed
   artefact against it. `generate:schemas:check` runs in CI's `check-cli` job and in
   `prepublishOnly`; `generate:matrix:check` runs in `check-web`. **No generator check runs at
   pre-commit**, so a stale artefact reaches `main` and is caught at the next CI run (schemas,
   matrix) or the next publish (types). `generate:matrix:check` covers the downstream half of the
   types chain, so a stale `src/cli/types/generated/` does turn CI red — one step later, and
   reported against the matrix package rather than against the file that moved.
2. **`injectSubcategoryPropertyNames` is dead code that reads as live.** The function, its
   doc-comment, `STACK_SUBCATEGORY_ENUM` and the generator's `CATEGORIES` import are all retained and
   all inert. Recorded here rather than deleted because the doc-comment's `z.record(z.enum())`
   reasoning is worth keeping even if the injection is not.
3. **Cross-surface mismatch, reported not fixed:** `reference/features/agent-system.md` pairs
   `src/schemas/agent.schema.json` with Zod schema `agentYamlConfigSchema`. The generator's
   `SCHEMA_ENTRIES` uses `agentYamlGenerationSchema` — a different export in the same file. That doc
   is outside this file's scope; the mismatch is recorded here per the count/claim-ownership rule.
