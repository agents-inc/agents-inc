# E2E Testing Standards

Standards and conventions for the E2E test suite. These docs govern how tests are written, structured, and maintained. For API details, read the source files directly.

**Audience:** Developers and AI agents writing or modifying E2E tests.

---

## Architecture

The framework uses a Page Object Model adapted for terminal-based CLI testing. Each layer has a single responsibility.

```
+-------------------------------------------------------------------+
|  TEST LAYER                                                        |
|  e2e/{commands,interactive,lifecycle,integration,smoke}/*.test.ts  |
|  Uses: CLI.run, page objects, matchers. Never touches Session.     |
+-------------------------------------------------------------------+
                              |
+-------------------------------------------------------------------+
|  PAGE LAYER                                                        |
|  e2e/pages/dashboard-session.ts                                    |
|  e2e/fixtures/interactive-prompt.ts                                |
|  Launch a command, press keys, wait for text.                      |
+-------------------------------------------------------------------+
                              |
+-------------------------------------------------------------------+
|  SCREEN LAYER                                                      |
|  e2e/pages/terminal-screen.ts                                      |
|  Auto-retrying text search.                                        |
+-------------------------------------------------------------------+
                              |
+-------------------------------------------------------------------+
|  SESSION LAYER (framework-internal)                                |
|  e2e/helpers/terminal-session.ts                                   |
|  Raw PTY (node-pty + @xterm/headless). Never used in tests.       |
+-------------------------------------------------------------------+
```

**Horizontal layers** support all vertical layers:

| Layer      | Files                                                                                                                                                                                                                       | Purpose                                                                                                                                                           |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Matchers   | `e2e/matchers/project-matchers.ts`, `agent-matchers.ts`, `setup.ts`                                                                                                                                                         | Custom Vitest matchers for file-based assertions                                                                                                                  |
| Assertions | `e2e/assertions/{phase,scope,uninstall,config,source-folder}-assertions.ts`, `four-surfaces.ts`                                                                                                                             | Composite assertion helpers (plain functions, NOT called via `expect()`)                                                                                          |
| Fixtures   | `e2e/fixtures/project-builder.ts`, `cli.ts`, `dual-scope-helpers.ts`, `interactive-prompt.ts`, `expected-values.ts`, `plugin-install-state.ts`, `seed-config-store.ts`, `codex.ts`, `codex-responses-mock.ts`, `codex-*.ts` | Project creation, CLI execution, scope helpers, canonical expected values, the seed config store stand-in, the pinned Codex runner and its Responses API stand-in |
| Constants  | `e2e/pages/constants.ts`                                                                                                                                                                                                    | All UI text, paths, timeouts, exit codes                                                                                                                          |


## Test Categories

| Category    | Directory      | Tool                                     | Description                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ----------- | -------------- | ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Command     | `commands/`    | Mostly `CLI.run()`                       | Commands: flags, output, exit codes, file side effects. One `describe` per command; split into files when a command has 15+ tests.                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Interactive | `interactive/` | `InteractivePrompt` / `DashboardSession` | Specs that drive the CLI through a terminal (PTY). A spec that only calls `CLI.run()` belongs in `commands/` or `lifecycle/`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Lifecycle   | `lifecycle/`   | Both                                     | Multi-phase: init, edit, compile, uninstall across shared project state. Single `it()` block per lifecycle.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Integration | `integration/` | `CLI.run()`                              | Cross-command pipelines (e.g., eject then compile)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Smoke       | `smoke/`       | Various                                  | Third-party probes (Claude CLI, Codex). May import the Claude host's own functions from `lib/hosts/claude-host.ts` (`claudePluginInstall`, etc.), and `execCommand` from `utils/exec.ts`, because they test the host binary directly, not our CLI. A probe about what the CLI does THROUGH the seam uses `hostFor("claude")` instead — `plugin-host-contract.smoke.test.ts` is the one that does. Claude probes use `describe.skipIf(!claudeAvailable)`. Codex probes run through `e2e/fixtures/codex.ts` and do not skip: the binary is a pinned devDependency, so a skip would read as a green run. |

## File Naming

- Test files: `{feature}.e2e.test.ts`
- Smoke tests: `{feature}.smoke.test.ts`
- Split at 300 LOC or when a file covers 2+ unrelated concerns
- Use descriptive names: `edit-from-plugin-migration.e2e.test.ts`, not `edit-2.e2e.test.ts`
- No task IDs (`D-NNN`) in `describe()` / `it()` names, assertion messages (2nd arg to `expect`), or inline test-body comments. File-level JSDoc at the top of the file is the only permitted location. Test names describe BEHAVIOR, not tickets — names rot, and IDs look authoritative but become meaningless once the task is closed.
- A `describe` heading, an `it` name and an assertion message are part of a rename. They describe behaviour in the product's vocabulary, so a vocabulary change moves them — and because none of the three is executed, none can be caught later by running anything: they are corrected in the same pass or not at all. Full rename procedure and the new-value grep it needs: `clean-code-standards.md` 17.4.

## Vitest Configuration

**File:** `e2e/vitest.config.ts`

| Setting       | Value                                     | Notes                                                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pool`        | `"forks"`                                 | Process isolation between test files                                                                                                                                                                                                                                                                                                                                                                                   |
| `maxWorkers`  | `Math.min(16, os.availableParallelism())` | Capped at BOTH ends. PTY-driven tests are load-sensitive: at one worker per core (21+ on dev machines) dropped keystrokes and slow installs produce flake that never reproduces solo — and a flat `16` on a four-core CI runner puts four PTY workers on every core, the same contention inverted.                                                                                                                     |
| `testTimeout` | `30_000`                                  | Default per-test timeout                                                                                                                                                                                                                                                                                                                                                                                               |
| `hookTimeout` | `60_000`                                  | Default for beforeAll/afterAll                                                                                                                                                                                                                                                                                                                                                                                         |
| `retry`       | `1`                                       | One automatic retry. It bounds a genuine failure's cost at 2x rather than 3x, and a retry that fires shows up in vitest's flaky report instead of passing silently. **Do not raise it to hide a failure.**                                                                                                                                                                                                             |
| `projects`    | `e2e` and `smoke`                         | Two named projects over one tree, split by FILENAME rather than by directory: `e2e` includes `e2e/**/*.e2e.test.ts`, `smoke` includes `e2e/**/*.smoke.test.ts`. Every other setting in this table is shared via `extends: true`. Each project needs its own script (`test:e2e`, `test:smoke`) — a project nothing selects by name never runs; `src/cli/lib/__tests__/spec-gates.test.ts` is what enforces the pairing. |
| `setupFiles`  | `./e2e/setup.ts`                          | Once per spec file: `assertDistIsPresent`, and `guardAgainstDistReplacement` before and after every test and at `afterAll`                                                                                                                                                                                                                                                                                             |
| `globalSetup` | `./e2e/global-setup.ts`                   | Pre-suite setup                                                                                                                                                                                                                                                                                                                                                                                                        |

Long tests override per-test: `it("...", { timeout: TIMEOUTS.LIFECYCLE }, async () => {})`.

## Constants Quick-Reference

These live in `e2e/pages/constants.ts`.

Three of the directory names below name a source folder and they are not interchangeable.
`SOURCE_CLAUDE` (`.agents-inc/claude`) is what a FRESH Claude install creates and `SOURCE_CODEX`
(`.agents-inc/codex`) what a Codex one does — the folder is the only record of which provider an
installation belongs to, so a Codex spec asserting the absence of `SOURCE_CLAUDE` is asserting
that nothing was half-routed; `SOURCE_ROOT` (`.agents-inc`) is the parent uninstall removes once
the last provider folder under it goes. Both `SOURCE_*` provider names are two segments, which
makes them unusable with `listFiles`, a top-level readdir that can only ever see the first.

**Directories (`DIRS`):** `CLAUDE`, `SOURCE_ROOT`, `SOURCE_CLAUDE`, `SOURCE_CODEX`, `RETIRED_SOURCE`, `SKILLS`, `AGENTS`, `EXAMPLES`, `PLUGINS`, `PLUGIN_MANIFEST`, `CODEX`, `CODEX_PROJECT_SKILLS`, `CLAUDE_BACKUPS`, `SOURCE_CACHE`, `SOURCE_CACHE_COPIES`, `GIGET_CACHE`

## Critical Rules

**Run the suite the way CI does: `bun run test:e2e --filter=agents-inc` from the repository root.** The root script is `turbo test:e2e`, and `packages/cli/turbo.json` makes this package's own `build` a dependency of its `test:e2e`, so `dist/` is rebuilt first. E2E specs execute the compiled binary at `dist/` via `bin/run.js`, so a source edit is invisible until a build runs. A direct `vitest --config e2e/vitest.config.ts` run does not build: `e2e/global-setup.ts` calls `assertDistIsFresh`, which refuses an absent `dist/`, or one older than any tree compiled into it by more than `CLOCK_STEP_TOLERANCE_MS` (`BUILD_INPUT_TREES`: `packages/cli/src` and the `src/` of `packages/matrix`, `packages/compile` and `packages/api`), before a spec is collected, and names the fix. `test:smoke` has no turbo task; CI runs it from `packages/cli` after `test:e2e` has built.

**One build at a time.** tsup empties `dist/` at the start of every build (`clean` in `tsup.config.ts`), so a second build — another agent's `bun run build`, or a second turbo run that rebuilds — empties `dist/` under a suite that is running from it. `guardAgainstDistReplacement`, registered by `e2e/setup.ts`, then fails the test in flight with `dist/ was replaced while this run was in flight.` instead of an ordinary assertion failure. That run is evidence of nothing; re-run it with no other build in flight.

**State-change verification.** Any test that runs a command that creates, modifies, or removes files or config entries MUST assert the resulting state of both config AND filesystem. If the operation should NOT change something, snapshot before and assert identical after. Never check only one side. This is the file-and-config half of a wider demand — a spec that drives a transition owes an assertion on what the OLD state left behind, on every surface that holds one: [assertions.md § Assert the Departure, Not Only the Arrival](./assertions.md).

**A spec that spawns a third-party binary must pin where THAT binary keeps its state.** Every isolation rule this suite has is about our own state — a fake HOME, a temp project, a temp source — and the suite spawns `claude`, which keeps its own. Faking `HOME` is not sufficient and is not always what the binary reads: measured against Claude Code 2.1.231, `CLAUDE_CONFIG_DIR` redirects the whole config tree for **writes** as well as reads, and it **beats `HOME`** — with both set to different directories the fake HOME stayed completely empty. So a suite that only fakes `HOME` is isolated exactly until a developer exports one, and before this landed three specs registered marketplaces into `~/.claude/plugins/known_marketplaces.json` on the machine running the suite, pointing at temp directories those same specs then deleted (`cleanupFixture` removes the tree, not the registration). Three obligations follow, and `createIsolatedClaudeHome()` in `e2e/helpers/test-utils.ts` carries all three: pin the binary's own state variable **explicitly**, **derive it from the fake HOME** so our CLI and the third-party binary see one installation (`<home>/.claude`, the tree `getUserPluginsDir()` reads the plugin registry out of under the same HOME), and **allocate it inside the temp tree** so cleanup removes the state rather than merely the fixture. A helper that shells out to such a binary takes the location as a parameter — the `HostCallOptions` the seam carries on every member, spelled `ClaudeConfigOptions` in `src/cli/lib/hosts/claude-host.ts` — because an in-process caller has no spawned environment to inherit and an ambient read makes the isolation invisible at the call site. All three E2E doors — `CLI.run`, `runCLI` and `TerminalSession` — pin it after `options.env` is applied, and pin `CODEX_HOME` to `codexHome(home)` beside it, because Codex is the second binary the suite spawns and `CODEX_HOME` beats `HOME` there too; `src/cli/lib/__tests__/e2e-runner-environment.test.ts` holds both pins at every door by driving each one with a caller env that contradicts them. The guard that keeps the whole answer true for Claude is `e2e/smoke/home-isolation.smoke.test.ts`, which is mutation-checked (neuter `configDirEnv` and 6 of its 7 tests go red, each for the reason its name claims). `e2e/smoke/codex-lane.smoke.test.ts` is its Codex counterpart: it snapshots the machine's own `~/.codex` — each entry's path and `lstat` mtime, because a list of names can come back identical after a leak — around every test, and its JSDoc records the mutation runs it was checked against.

**A spawned binary is told about every environment variable the product reads — including the harness's own.** Every runner hands `bin/run.js` the environment of whoever ran the suite unless it clears it, so a spec's result becomes the developer's shell's rather than the code's. The product's own overrides are the obvious half — an exported `CC_MARKETPLACE` (`SOURCE_ENV_VAR` in `src/cli/lib/configuration/config.ts`) points `init` at a marketplace no spec declares, `AGENTS_INC_API_URL` answers `--from`, `XDG_CACHE_HOME` serves a source this run never fetched, and `GIGET_AUTH` authenticates a fetch that should have failed. **The inverted case is the one the class was found through:** `VITEST` is the HARNESS's variable and not the product's. It is cleared at the runners rather than gated in the product, because a spawned `bin/run.js` is a user's binary and should see a user's environment.

Every runner answers for the whole roster, because a variable one clears and another does not is not half-solved — the leaking specs are simply the ones on the runner nobody checked, and nothing about them says so. **There are three, and the third is the one that was missed:** `e2e/fixtures/cli.ts` is the non-interactive runner, `e2e/helpers/terminal-session.ts` the PTY harness, and `runCLI` in `e2e/helpers/test-utils.ts` the bare-directory command runner, which cleared nothing at all while a roster naming the first two called itself complete in its own comment. Each writes `<NAME>: undefined` for `CC_MARKETPLACE`, `XDG_CACHE_HOME` and `GIGET_AUTH` ahead of `options.env`, and defaults `AGENTS_INC_API_URL` to an unroutable loopback (`NO_LIVE_SEED_API`) instead, because the product falls back to the live store when it is unset; a session that needs a value still names its own. **`VITEST` is the one exception, and the asymmetry is deliberate:** `e2e/fixtures/cli.ts` and `runCLI` clear it ahead of the spread like the rest, while `e2e/helpers/terminal-session.ts` places it AFTER — pinned rather than defaulted, so a caller of the PTY harness cannot re-inject it. That door drives the interactive prompts and the dashboard, where a silenced product warning is exactly the failure the suite exists to catch, and no spec has a legitimate reason to want it back; a spec that genuinely needs `VITEST` set re-injects it through `CLI.run`, which defaults. Do not move it above the spread for consistency. Two specs hold this. `src/cli/lib/__tests__/e2e-runner-rosters-match-the-tree.test.ts` reads every `process.env` touch in `src/cli/`, refuses a shape it cannot classify (an unclassifiable read would be reported as read-by-nobody and every assertion under it would agree), and holds the named roster and the constant-keyed reads against that scan. `src/cli/lib/__tests__/e2e-runner-environment.test.ts` exports every rostered variable in its own process, opens each runner with both spawners recorded rather than run, and requires the environment each child would be handed to carry none of them, with the seed API at that unroutable default. **The membership of the runner roster is DERIVED, which is the half that stops it going stale again the next time a door is added:** one `it` in the rosters spec holds the runner files against the doors `scripts/check-spawn-doors.ts` reports, and that scan finds a door by the constant it starts the binary through rather than by having been told about it — so a new runner reddens the roster instead of quietly inheriting the developer's shell. The environment spec reads what the child receives rather than the runner's code, so it holds however a door clears a variable. `src/cli/utils/exec.ts` is the single declared whole-environment forwarder — it spawns the Claude CLI, a different program entitled to the user's environment — so a second such spread arrives at that list with its own reason instead of passing as this one's twin. `CI` and `GITHUB_ACTIONS` are deliberately left untouched: `src/cli/components/render.ts` must trust the real pseudo-terminal this harness provides over them, and leaving them in is what proves it does.

**Wait for the frame that will receive a key press before sending it.** Under parallel suite contention the PTY write can land between Ink's render commit and the `useEffect` that registers the new frame's `useInput` handler, so the keystroke is silently swallowed and the test passes by not exercising the behaviour it claims to test. A post-press wait doesn't substitute — the guard must sit upstream of the keystroke. `InteractivePrompt.confirm()` / `deny()` wait for nothing first, so the obligation is the caller's: the prompt specs wait on the question's own text (`STEP_TEXT.SHARED_CONFIG_APPLY_CONFIRM`, `SHARED_CONFIG_INSTALL_CONFIRM`) before pressing. Teardown keys are the exception: `escape()` / `ctrlC()` on `DashboardSession` and `InteractivePrompt` are valid from any screen, so they take `INTERNAL_DELAYS.KEYSTROKE` after the press instead of a pre-press wait — they are `async`, and every caller awaits them.

**Navigation must be closed-loop.** After moving focus, verify the focused row from the rendered screen — the `❯`-marked row, not mere visibility of its label — before acting on it; never maintain a keystroke-count model of position across calls. `DashboardSession.chooseOneKeyAtATime(downs, focusedRow)` is the canonical implementation (`chooseInOneBurst` is open-loop on purpose: its subject is a burst). See [anti-patterns.md § Index-Based Navigation](./anti-patterns.md) and [page-objects.md](./page-objects.md).

**`getOutput()` is a buffer, not a frame log.** `getOutput()` / `getFullOutput()` return xterm's PROCESSED buffer — the current screen plus whatever genuinely scrolled off. Ink repaints overwrite in place, so a value that was rendered and then re-rendered differently is NOT retrievable from it. Never assert "some earlier frame contained X" via `getOutput()`. Assert at the moment the frame is on screen, or use a raw-output surface (`getRawOutput()`, `waitForRawText`) — raw PTY output is append-only and is the only frame-accumulating surface.

**Never broaden assertions.** When a strict assertion fails, investigate why — don't weaken it. If the failure is a fixture limitation, keep the strict assertion as a commented-out `// KNOWN GAP:` with an explanation. If it's a product bug, use `it.fails`.

**Mutation-check every regression guard — green after a fix is not evidence.** A spec that has never been observed to fail is indistinguishable from one that cannot. Before calling a spec a guard: revert the fix in `src/`, `npm run build`, run the spec, confirm it is red **and red for the reason the test name claims**, then restore. This applies to repaired assertions as much as to new ones — a "fixed" vacuous assertion nobody has watched go red is exactly the vacuum it replaced.

**Where the spec asserts that something did NOT change, mutate the FIXTURE instead — the `src/` revert returns a false "already covered" for that whole class.** A guarantee not to write and a bug that skipped the write are the same bytes on disk, so reverting the fix leaves the spec green and the literal reading of the procedure above concludes the behaviour was already covered — shipping a spec that can never fail. Make the subject change by hand at the point the operation would have changed it, confirm the spec reddens on the assertion whose message claims the guarantee **and on nothing else**, then remove the mutation and record in the spec's JSDoc that this is how it was checked, so the next reader does not repeat the revert and draw the wrong conclusion. `e2e/lifecycle/install-update-source-drift.e2e.test.ts` is the worked example — one line appended to the INSTALLED `SKILL.md` immediately before the run. The class is large: every "must not touch", "must not recompile", "must not rewrite the config" assertion is in it. Full case: [anti-patterns.md § Never call a spec a regression guard until you have watched it go red](./anti-patterns.md).

**A refusal pinned on its own cannot tell a correctly-scoped guard from one that has swallowed its domain, and the pairing rule for that lives outside this page.** Both outcomes leave the config and the filesystem byte-identical and both exit 0, so the assertion reads the same either way and stays green while the guard grows. The requirement — pin a state where the same operation is ALLOWED in the same file, and the permitted case in a different spec is not a control because nothing makes the two move together — is in [`packages/cli/CLAUDE.md`](../../../CLAUDE.md) § Test Assertions, with the guard that produced it, the narrowed predicates and the worklist grep. It is stated there rather than here because it binds unit specs as much as E2E ones.

Two mechanisms make a spec pass for the wrong reason, and neither is visible by reading it:

1. **The fixture is smaller than production, so the defect's blast radius differs.** `createE2ESource()` writes one stack and ten skills; the real marketplace carries many more of each. For a size-dependent rendering defect, how far an overpaint reaches scales with list length. Record in the spec which assertion carries the red under this fixture, so a later reader does not simplify it down to the one that does not.
2. **The assertion's subject is not painted in the captured frame.** See the absence rule below.

**The rule covers every gate-style assertion, not only specs — and a shared helper is where it is easiest to skip, because the specs calling it are green.** A composite assertion module, a probe, a matcher and a hand-run verdict each report a pass or a fail and are each trusted on that report. None of them has been shown to assert anything until it has been watched produce the fail. Two live instances, and mutation is the only thing that separated either from a working check:

| The verdict                                   | Why it could not fail                                                                                                                                                                                                                                                                                    |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `probe.exitCode !== 0` on the narrowing probe | The probe was handed a skill id where it takes type ALIAS names, so it rendered unparseable TypeScript and `tsc` exited non-zero on a **syntax** verdict without ever type-checking an assignment. The collapse it exists to catch produced the same non-zero exit as success. See the probe rule below. |
| `after.length >= 0 && before.length >= 0`     | A length is never negative. The verdict reported success against every pair of directory listings it was ever given, while reading as a comparison of two.                                                                                                                                               |

**A verdict is judged on the specific signal that answers its question, never on a coarser one that a failure also produces.** `TS2322` answers "does this alias still reject the value", a non-zero exit answers "did tsc have anything to say at all", and the second holds for a probe that compiled nothing. The same distinction applies wherever a check reads an exit code, a non-empty output or a thrown error: name the signal, not the symptom.

The vacuous-comparison half of this is now mechanical, and it is answered in two places. `packages/cli/eslint.config.js` carries `VACUOUS_COMPARISONS` — `no-restricted-syntax` selectors for a `length`, a `size` or a `byteLength` compared against zero in either operand order. `packages/eslint-config/base.js` carries core ESLint's `no-self-compare` for `x === x`, which reaches **every** workspace: it takes no options, so it merges across config blocks, and `x === x` is not a mistake this package has a special claim on. The selectors cannot follow it there for exactly the reason the next paragraph gives.

**`@typescript-eslint/no-unnecessary-condition` does not and cannot catch either**: it asks whether a value's TYPE settles a condition, and `number >= 0` is a `boolean` that the type `number` leaves open, because there is no non-negative number type for a count to narrow to. The shape is only ever reachable syntactically. A `||` of two loose conditions is the same class and stays un-lintable — whether either side can be false is a question about the subject, not the syntax, so it is what the mutation run is for.

**A widening is measured before it lands, never assumed.** `size` and `byteLength` joined `length` on 2026-08-18 on the numbers: the selector reaches a property by NAME, so a domain object's own `size` field is condemned alongside `Map.prototype.size`, and that is where a false positive would come from. Twelve comparisons of a `.size`, `.byteLength` or `.count` against a literal exist across every workspace and every one is discriminating; none sits in the vacuous direction, so the widening condemns nothing that exists. `count` was measured and left out — it names no builtin, so a `count` field is whatever its owner made it. This is the standard two candidate sentinel checks were **refused** against, and a widening is held to it too.

`no-restricted-syntax` options are **not** merged across config blocks: the last block naming the rule for a file owns all of them, so a zone declaring it for its own reason silently drops every selector it did not restate, and a zone no block names has none. `src/cli/lib/__tests__/spec-gates.test.ts` lints one real file per zone against the loaded config, once for every shape in its `ESCAPE_SHAPES` table, and requires the vacuous form to be reported and the discriminating form to be left alone — the positive half is the subject guard for the negative one, and the fixture is thrown on rather than counted if it fails to parse, for the reason the probe row above gives. A fifth gate beside it lints under `packages/eslint-config/base.js` and nothing else, which is the only way to tell a rule the shared base carries from one this package adds on top; the loaded config cannot, because there the two are indistinguishable.

**Absence is the hardest thing to assert in a terminal, and two separate traps make it vacuous.** (a) `getScreen()` is **not** viewport-only despite its name — it reads scrollback plus viewport, so `not.toContain(X)` matches anything the session ever drew; prove negatives by ORDER (`toMatch(/…$/)`) or by BEHAVIOUR. (b) A negative rendering assertion needs a **positive subject guard** in the same captured frame — `not.toContain("<bug shape>")` passes for free where none of the rows the shape is made of are painted, and clearing the size gate is not evidence the content is visible. Full detail: [assertions.md § Negative Assertions](./assertions.md) and [anti-patterns.md § Weak Assertions](./anti-patterns.md).

**A workaround in a test's JSDoc is a defect report.** When a spec sidesteps a rendering difference to assert something else, it must cite a finding for that difference or point at the spec that pins the un-worked-around form. Otherwise every later spec inherits the dodge, none asserts the real form, and the defect becomes structurally invisible — the suite green precisely because nothing looks.

**Prove the code path fired — don't just assert the contract.** When a test depends on a specific conditional code path running (e.g. `propagateGlobalChangesToProjects` fires only when `globalConfig.projects?.length` is truthy; a merger step fires only when a field is present), add a proof-of-execution assertion (file-content diff, mtime change, side-effect invariant) alongside the contract assertions. Otherwise a regression that short-circuits the path before the contract code runs produces a vacuous pass — the contract assertions hold trivially because the post-state equals the pre-state. If the pre-condition cannot be met on current `main` (blocked by a known bug), comment the proof-of-execution assertion as `// KNOWN GAP:` with a finding reference so it can be uncommented once unblocked. Cross-link to branch selectors when the trigger path is ambiguous. Every proxy named above is a WRITE, so none of them is available to a flow whose correct behaviour is to write nothing — there the proof has to be an observable the run emits on the way to its decision, and reaching for a write instead pins the opposite of the contract: [assertions.md § A Proof of Execution Names a Side Effect the Flow Is Supposed to Produce](./assertions.md).

**Diff-shape assertions prove BOTH positive and negative shape.** For diff collections (config section diffs, the marker rows of `edit`'s Changes block) use `toStrictEqual` on a scope-anchored slice, NOT `expect.arrayContaining` — `arrayContaining` passes as long as expected entries exist and silently tolerates extra wrong entries. When two rows share the same prefix, prove it by exhaustively negating all other prefixes rather than extracting to a parsed struct.

**Every parameter shape in the `declare module "vitest"` block must be an imported named type.** `e2e/matchers/setup.ts` augments Vitest's `Assertion` and `AsymmetricMatchersContaining` with this suite's custom matchers. Every expectation shape in both declarations must be a named type imported from the matcher that implements it — never an inline object or array literal. An inline shape is a second, silent definition of a parameter that already has one, and the two typecheck independently, so nothing at review time distinguishes a declaration that still tracks its implementation from one that stopped. It matters more than a duplicated type usually does because a spec resolves `expect(x).toMatcher(…)` against the AUGMENTATION, not against the implementation: the stale copy is the one gating every call site, and the implementation's real signature is reachable from nowhere a test can see.

Measured on `toHaveLocalSkills`, whose parameter type `LocalSkillIds` is exported beside the implementation in `e2e/matchers/project-matchers.ts` and imported by both declarations. Change the implementation's parameter to an element type no call site can satisfy, then run `tsc -p e2e/tsconfig.json --noEmit`:

| Declaration form                                      | `tsc` errors                                                                                                     |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| Inline — the array literal written out in both blocks | **1**, inside the matcher's own file. Every call site compiles clean against the augmentation that did not move. |
| Imported named type — `LocalSkillIds`                 | The same 1, plus one at every call site per element that no longer fits.                                         |

The comment above the block asserts this guarantee in prose. One opted-out declaration makes it false for the whole block without changing a word of it, which is why the rule is structural rather than a review habit.

**No parser/extractor helpers in test files.** Never define loops, regex scans, or state machines inside a test file to pick data out of rendered output (`lastFrame()`, `getFullOutput()`) or config text. If a helper has non-trivial logic it would need its OWN tests to be trusted; an uninstrumented parser silently produces wrong answers when layout changes. Assert directly on the raw output with `toContain`, `toMatchInlineSnapshot`, or a structural load (e.g. `loadProjectConfig` for config.ts). If genuinely reusable across tests, live it in `src/cli/lib/__tests__/helpers/` WITH its own tests. A tested helper lives where a vitest project COLLECTS its test: `src/cli/lib/__tests__/helpers/` for one shared across the CLI, or a `__tests__/helpers/` beside the code it serves for one that is not — `src/cli/lib/hosts/__tests__/helpers/fake-child-process.ts` and its `fake-child-process.test.ts`, collected by the `src/**` project, are the live example. What is forbidden is a helper test somewhere no project looks, and under `e2e/` that is everywhere: no vitest project collects `*.test.ts` under `e2e/helpers/` — the projects in `vitest.config.ts` include only `src/**` and `scripts/**`, and those in `e2e/vitest.config.ts` require an `.e2e.test.ts` or `.smoke.test.ts` suffix — so a helper test placed beside an `e2e/helpers/` module never runs, and reads as coverage while proving nothing. E2E specs reach these helpers through `e2e/helpers/test-utils.ts`, which imports each one by name and names it in its single `export { ... }` block; `normalizeGlobalConfig` and `writeTestPackageJson` are the live examples of that route, and `journey-page.ts` is one carrying its own `journey-page.test.ts` beside it.

**Two halves of one module take the same door.** `helpers/config-comparison.ts` exports both normalisers, and routing the order-sensitive one through `test-utils.ts` alongside its sibling REMOVED an import from its one E2E caller rather than adding one: `scope-toggle-roundtrip.e2e.test.ts` carried a second import line for it and now names it inside the `test-utils.js` block it already had. The cost of the alternative is not the extra line — it is that two halves of one module arriving in the suite by two different doors reads, a year later, as a deliberate distinction someone is expected to preserve, and the next helper is filed by whichever precedent was found first.

**A narrowing probe is judged on `TS2322`, never on a non-zero exit code.** `probeConfigTypesNarrowing` asks whether a generated alias still REJECTS a value it should never accept, and only `TS_NOT_ASSIGNABLE` in its `output` answers that question. `exitCode` answers a different one — tsc exits non-zero for ANY diagnostic — so `expect(probe.exitCode).not.toBe(0)` passes on a probe that never type-checked an assignment at all. The failure mode is not theoretical: the probe takes ALIAS NAMES to import, and handing it a skill id instead renders `import type { web-framework-react }`, which is unparseable. Measured against a `config-types.ts` degraded to `SkillId = string` — the exact collapse the probe exists to catch — a literal argument produced the same non-zero exit as a correct narrow union, so the check could not tell the defect from success. The argument type (`GeneratedAlias`) now makes that particular mistake a compile error; the rule stands anyway, because an exit-code check is uninformative however the non-zero arose.
