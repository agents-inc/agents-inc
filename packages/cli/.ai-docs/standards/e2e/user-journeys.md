# Canonical user journeys

The list of journeys the product must prove it can perform end to end — across the CLI and the
editor, which are one arc rather than two products — and what a spec has to assert before it counts
as proving one. Every spec the `e2e` project collects belongs to a journey on this page, bar those
whose subject is the harness itself and which are named below; a CLI journey with no from-scratch
spec is a hole in the suite regardless of how many variant specs branch off it. A journey with no
CLI surface at all is a different thing and says so — see
[Which suites this page governs](#which-suites-this-page-governs).

That opening requirement is now held in BOTH directions.
`src/cli/lib/__tests__/spec-gates.test.ts` reads row → spec three ways, and spec → row once —
against `SPECS_BELONGING_TO_NO_JOURNEY`, the backlog of specs this page did not name on the day
that gate landed. The backlog may only shrink: a spec added without a journey fails there, and a
spec that gains a row leaves the list in the same commit. Until it existed the matrix could not
report its own omissions, which is how five corrupt-config specs went unrowed while a ruling landed
on the behaviour they covered.

**Audience:** whoever writes or reviews an E2E spec, and whoever decides what to test next.

**Sources.** Journeys 1–11 are the flows driven by hand in
[`todo/plans/cli-flow-verification-2026-08-08.md`](../../../../../todo/plans/cli-flow-verification-2026-08-08.md)
and its [re-run](../../../../../todo/plans/cli-flow-verification-rerun-2026-08-08.md); the
[fifth pass](../../../../../todo/plans/cli-flow-verification-fifth-pass-2026-08-10.md) drove 23 rows
against published artifacts on both sides. The rest were named by the owner. The coverage column is
re-derived from the
[strictness audit](../../../../../todo/plans/CLI-444-e2e-strictness-audit.md), whose journey map
links here.

## What "from-scratch" means

A **from-scratch** spec starts with nothing on disk at the relevant scope, drives the real binary
(the wizard through a PTY, or a non-interactive command), and asserts observable output. A spec
that begins from a `ProjectBuilder`-written config is a **variant** — legitimate for covering a
branch, never sufficient to prove the journey is reachable.

### Which suites this page governs

**This page registers the product's journeys across both front doors** — the CLI at
`packages/cli/e2e/` and the editor at `apps/editor/e2e/specs/`. They are one arc rather than two
products, and the arc runs in both directions: a configuration built in the browser is installed by
the binary, and an installation the binary holds is opened in the browser. A page registering one
half would report a flow as unproved while the other half proved it, and would never name the
crossing that neither half proves — which is the only place a defect can sit where both ends are
individually correct.

**A from-scratch spec is still a run of the compiled binary**, and nothing here relaxes that. That
is the CLI's unit of proof: a spec that never spawns the binary cannot close a CLI leg however
completely it covers the same user-facing behaviour. `apps/editor/e2e/specs/` is a Playwright suite
in another workspace, driving a browser against a stubbed HTTP surface, and a row names its specs as
**counterpart legs** so a reader can see which half is proved where.

**Some rows have no CLI leg at all, and they carry that rather than being left off the page.**
Signing in, saving a stack to an account, composing a selection from a sentence and folding the
grid away are browser-and-worker journeys; the first three end at a payload, which is where the CLI
picks the arc back up, and the fourth has no CLI subject in any direction. Their From-scratch column
reads `none` with the reason, because that column asks whether the binary has been run and the
honest answer is that it has not.

**What the GATE reads is still the CLI suite alone.**
`src/cli/lib/__tests__/spec-gates.test.ts` resolves the From-scratch column against
`packages/cli/e2e/` and would fail on an editor spec named there. That is a property of the gate
rather than of this page, and it is why every counterpart leg is named in the Status cell instead —
`namedOnJourneyPage` reads the whole page, so a CLI spec is claimed wherever it appears.

**A payload field's FORM is part of the contract, and a counterpart leg proves nothing about it
unless the two suites carry the same value.** Holding the payload still is what makes the
arrangement work, and it is also what hides a disagreement about what a field may hold: each side
pins a value legal on its own terms, both suites go green, and no run anywhere carries the form the
other side actually produces. The `marketplace` ref found that out. A bare `owner/repo` and an
absolute directory are both legal refs; the editor minted the first and the CLI's spec pinned the
second; and the form that crossed between them resolved to a path in the receiver's own working
directory, so every id one half produced was one the other half refused. A row spanning both suites
therefore has to record WHICH form each side exercises, and must never read a green pair as
agreement about a form neither of them carried.

**`e2e/handrun-journeys.ts` closes no row.** It is a hand-run script: neither `include` glob in
`e2e/vitest.config.ts` matches it, no package script runs it, and `scripts/handrun.mjs` only bundles
it for a human to drive. Its `verdict(...)` HOLDS are a report from one operator's machine, so a
journey it walks is covered only by the specs a row names.

`e2e/vitest.config.ts` declares two named vitest projects, and this page governs the **`e2e`** one —
`e2e/**/*.e2e.test.ts`, run by `test:e2e`. The **`smoke`** project (`e2e/**/*.smoke.test.ts`, run by
`test:smoke` and by one CI step) probes the real `claude` binary rather than a journey, so its files
are claimed by `src/cli/lib/__tests__/spec-gates.test.ts` and by no row here. That gate asserts both
halves, because either alone is satisfiable by doing nothing: every spec file on disk is included by
some project, AND every project is named by a package script.

**The filename is the discriminator, not the directory.** `e2e/smoke/pom-framework.e2e.test.ts`
carries the `.e2e` suffix and therefore runs in the `e2e` project. It,
`e2e/matchers/project-matchers.e2e.test.ts`, `e2e/commands/warn-suppression-stops-at-the-harness.e2e.test.ts`,
`e2e/interactive/smoke.e2e.test.ts`, `e2e/pages/retry-space.e2e.test.ts` and
`e2e/pages/list-row-toggle.e2e.test.ts` are the exception to "every spec belongs to a journey":
their subject is the harness — the page objects, the custom matchers, the Space retry loop and the
list-row toggle built on it, the environment a spawned binary inherits and that the binary answers
at all — rather than anything the CLI does for a user. The last two spawn no binary at all: they
drive `retrySpaceUntilToggled` and `toggleListRowUntilRendered` against fakes that lose a press on
demand, because the race they exist for is not reproducible on a real PTY.

## The four assertion surfaces

A journey spec asserts on all four surfaces below. One missing surface makes the spec incomplete by
definition, however strong its other assertions are — each surface fails independently of the
others, and three of the four have shipped a defect the others were green through.

| #   | Surface              | What it is                                                                | Read it with                                                                                                  |
| --- | -------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 1   | Compiled agent files | `.claude/agents/*.md` at each scope the journey touches                   | `readCompiledAgents`, `listFiles(agentsPath(dir))`, `toHaveAgentFrontmatter`, `toHaveAgentDynamicSkills`      |
| 2   | CLI rendered output  | what the user saw — wizard frames and command stdout/stderr               | `getOutput()` on a step page object, `CLI.run().output`, `STEP_TEXT`                                          |
| 3   | Written `config.ts`  | the configuration the run persisted, at every scope it could have written | `loadConfigOrFail` / `readSkillEntries` + `toStrictEqual`; raw bytes when proving something did NOT move      |
| 4   | `config-types.ts`    | the generated type surface the config is checked against                  | `readTestFile(configTypesTsPath(dir))`, or `type-check-probe.ts` for "a bad value must still be a type error" |

**The journey tables' "Surfaces asserted" column is a union across the row's named specs, not a
per-spec claim.** A row reading `1, 3, 4` over three specs says every listed surface is asserted by
at least one of them; it says nothing about any single spec reading all of them.

Surface 4 is the one specs skip. It is not decoration: the aliases are what make a hand-edited
`config.ts` fail loudly instead of silently, so a journey that changes the installed skill set and
does not re-check them has not proved the install is still coherent.

**Negative form.** For a scope a journey must NOT touch, the same four surfaces are asserted
byte-identical (or absent) rather than skipped. "Nothing changed here" is a claim and needs
evidence. `readTreeSnapshot(dir)` in `e2e/helpers/test-utils.ts` is the one call that discharges all
four at once: it walks the tree recursively and records content **and** mtime per file, so a
`toStrictEqual` against a pre-run snapshot covers the compiled agents, both generated files and
everything else in one assertion. A row whose subject is a refusal or a decline owes that snapshot,
not four separate absences.

### The fifth surface: the payload

The share family (`share`, `edit --ui`, `init --from`, `edit --from`) has a surface the four above
cannot describe — the JSON that crosses the wire. It is the only place a defect can live where both
ends are individually correct, and it is what makes the two suites' halves comparable.

| What to assert                | Read it with                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------- |
| What the CLI posted           | `JSON.parse(store.requests.filter(r => r.method === "POST")[0].body)`           |
| The id a run minted           | `store.minted` on the `SeedConfigStore`                                         |
| That a refusal spent no write | `expect(store.requests).toStrictEqual([])`                                      |
| What the CLI was served       | `store.publish(id, buildSeedPayload({ … }))` from `factories/seed-factories.ts` |

The store is `e2e/fixtures/seed-config-store.ts` — a real loopback HTTP server, not a module mock,
so the flag reaching the command and the payload surviving the wire are both inside the test. It
content-addresses a posted body exactly as the worker does, which is what lets a spec assert that
re-sharing an unchanged installation returns the id it already had. The wire contract itself is
`seedPayloadSchema` in `packages/matrix/src/seed.ts`.

## Coverage vocabulary

| Marker                    | Meaning                                                                                                                                                                                                                                                            |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **COVERED**               | A from-scratch spec exists and is named                                                                                                                                                                                                                            |
| **PARTIAL**               | A from-scratch spec exists but does not assert all four surfaces — the missing surfaces are named                                                                                                                                                                  |
| **TO TEST**               | No from-scratch spec                                                                                                                                                                                                                                               |
| **PARKED**                | Owner ruling: the implementation is changing, so no spec work happens here                                                                                                                                                                                         |
| **(blocked)**             | Qualifier on TO TEST: the spec cannot be written without the real Claude CLI present                                                                                                                                                                               |
| **PARTIAL by subject**    | Fewer than four surfaces because the journey has no subject on the others — a read-only browse installs nothing, a refused build writes no config                                                                                                                  |
| **COVERED, browser-side** | The journey's own behaviour is proved by a Playwright spec and no run of the binary is owed for it — either because it has no CLI surface at all, or because the CLI surface it ends at is ANOTHER row's subject. Distinct from TO TEST, which means a run IS owed |

### Prefix journeys

**Where one journey is a prefix of another, they are one journey.** Driving A→B and A→B→C
separately buys nothing: the longer run exercises every seam the shorter one does, and two rows
over one arc means two specs to keep in step and one of them silently rotting.

A merge is correct only when the longer journey **subsumes** the shorter one _and_ **asserts the
same surfaces at the same strength**. Three shapes look like merges and are not:

1. **The shorter row asserts a negative.** A byte-identity snapshot, a refusal, a "this must not
   have happened" — the longer chain almost never asserts it, because it is busy going somewhere.
   That is a gap in the longer journey, not redundancy in the shorter. Fold the negative in
   explicitly or keep the row.
2. **The shorter row is PARTIAL.** Merging it into a COVERED row makes the outstanding surface
   disappear from the page. Carry every unclosed surface forward by name, or the merge has closed a
   gap by deleting the record of it.
3. **The shorter row is runnable and the longer one is blocked.** Every install-mode spec is
   `describe.skipIf(!claudeAvailable)`. Folding a runnable leg into a blocked chain makes the whole
   thing skip wherever the Claude CLI is absent, which is most machines and every CI runner that has
   not installed it. Blocked legs stay separable.

## Journey 42 — the name a run prints itself under

`branding.name` is a declared field of the project config: admitted by the loader schema, published
in `src/schemas/project-source-config.schema.json`, and answered by `resolveBranding`. This journey
is the claim that it reaches the terminal — that a user who white-labels their configuration changes
what every command naming the product calls it, rather than only what the file says. Which functions
read it, and the posture each takes over a configuration that cannot be evaluated, are in
[reference/features/configuration.md](../../reference/features/configuration.md).

**`branding` publishes one field, and did not always.** `tagline` sat beside `name` in the type, the
loader schema and the published JSON schema, promising _"Custom tagline shown in wizard header"_ — and
no wizard header ever rendered it, so it was accepted, resolved and never printed. It was deleted on
2026-08-24 (owner ruling), which is why this journey names `branding.name` rather than `branding`:
the two were never both reaching the terminal, and only one ever could.

**The resolution beneath it changed on 2026-08-24 and this journey did not.** `resolveBranding` fell
back per FILE — the project's config if one existed, the global one otherwise — so a project config
declaring no `branding` resolved to the shipped default and never consulted the global config
behind it. A user who branded globally stopped seeing their own name the moment any project config
existed, which is every installed project. It is per FIELD now: this project, then the global
config, then `DEFAULT_BRANDING`, each field independently. The journey's claim is unchanged — the
name reaches the terminal — but it is now true for a global brand under a project that says nothing

## Using this page

**Writing a spec.** Find its journey. If the journey is TO TEST, the spec is a from-scratch one and
owes all four surfaces. If the journey is COVERED, the spec is a variant and may branch off the
existing from-scratch spec — name that spec in the JSDoc so a reader can see what proves the state
is reachable.

**Reviewing a spec.** Check the four surfaces before checking anything else. A spec asserting three
of them is not "mostly done"; it is a spec that will stay green through a defect on the fourth.

**Closing a TO TEST row.** Name the new spec in the row and change the marker in the same commit
that lands the spec. A row that says TO TEST after the spec exists is worse than no row, because it
sends the next reader to write a duplicate.

**Adding a row.** Before adding one, read the prefix rule above. A journey that is a prefix of an
existing row belongs inside that row as a named leg, not beside it.

## Journey 26 — the ruling: marketplace-namespaced ids

What happens when the global install came from marketplace X and a project installs from
marketplace Y? **Nothing special — because the two can no longer name the same skill.**

**The ruling: every skill id carries its marketplace as a prefix, written by the marketplace
author.** A marketplace named `acme` ships `acme-web-frontend`, never a bare `web-frontend`. The
public marketplace is the sole exception — its skills stay unprefixed, so `agents-inc` is the
implicit namespace and is not available to anyone else.

**Why this closes the journey rather than answering it.** The whole problem was two marketplaces
supplying one id: the skill id is the name of the directory it installs into
(`unresolved-skill-entries.ts` joins `skillsDir` with the id), and Claude reads `~/.claude` and
`./.claude` together, so two different skills under one name means one silently shadows the other.
Unique ids make that unrepresentable. A `[P][G]` pair is a pair of the SAME id, so a cross-marketplace
pair cannot be constructed — no guard, no refusal path, no per-scope catalog reasoning. **Dual scope,
tombstones, propagation and the scope toggles are unchanged.**

**Author time, not load time (owner ruling).** The id in the marketplace repository IS the id
everywhere — no transform on ingest. This is deliberate: a load-time namespace would have to be
applied independently by the CLI and the editor, and two implementations of one rule is the failure
class where the same question is answered differently by two code paths. It also removes the
question of what the prefix derives from, since nothing derives it.

**Enforcement is the load-bearing part**, and it is journey 33. A convention with no validator is a
collision waiting to land on a user rather than on the author:

- `build marketplace` refuses a skill whose id does not carry the marketplace's prefix, naming the id
  it expected. It already loads a kebab-case marketplace name from `package.json` (with a `--name`
  override for npm-scoped names) and already runs `validateKebabCaseName`, so the expected prefix is
  in hand at the right moment.
- The load side refuses a custom source whose ids collide with the default catalog — a set
  intersection, no transform. This is what stops a marketplace that skipped the build step, and what
  stops anyone claiming the `agents-inc` namespace.

**Skills with no marketplace take the `external-` namespace (owner ruling).** An externally-added or
locally-created skill answers to no marketplace, so it would otherwise collide with the public
catalog — a local `web-frontend` against the published `web-frontend` is the exact failure this rule
exists to prevent. It becomes `external-web-frontend`, same shape as a marketplace prefix, and
nothing parses it positionally so the shape costs nothing.

Two consequences:

- **`agents-inc`, `external` and `local` are RESERVED marketplace names.** The build-side validator
  refuses a marketplace claiming any of them, or the namespace stops separating anything. `new
marketplace` refuses them too, before it writes a directory.
- **`external-` does not make external skills unique against each other** — it separates them from
  marketplaces, not from one another. Two added skills resolving to the same id is a real
  possibility, since external skills come from arbitrary repos rather than a curated set. It is
  detectable at add time with the id in hand, so the intake refuses the second one and names the
  skill already holding the id. Deliberately not solved by deriving a longer id from the repo owner:
  these are eject-only, per-install files, so the requirement is uniqueness within one machine's two
  scopes, not global uniqueness.

**Separator: `-`, and it must stay filesystem-legal.** `:` and `/` are out — the id is a directory
name and has to work on Windows. The standing invariant that an id always includes its category is
about what the id CONTAINS, so the two rules compose.

> **Nothing parses a skill id positionally — not the product, and not the test factories.** Every
> `split("-")` site in production code under `src/cli/` takes an AGENT id, which is what makes a
> namespaced skill id safe in shipped code. `createTestSkill` and `createMockSkill`
> (`src/cli/lib/__tests__/factories/skill-factories.ts`) read `domain`, `category` and `slug` from a
> canonical taxonomy registry keyed by the whole id, and throw naming the id when it holds no entry;
> a caller with a novel id passes those fields in `overrides`.
>
> **Do not reintroduce a split there.** It fails silently rather than loudly: given
> `e2e-test-fixture-web-framework-react` a positional derivation yields `domain: "e2e"`,
> `category: "e2e-test"` and a fabricated slug with no error at all, because the two fields are
> `as`-cast at the boundary and the canonical-category lookup simply misses. It also breaks two
> standing repository rules at once — deriving `slug` from a skill id, and a multi-tier category
> fallback.
>
> `categoryPartOf` / `domainOf` in `src/cli/lib/__tests__/fixtures/create-test-source.ts` are not
> the same shape and are unaffected: they split a CATEGORY, and a category keeps its `domain-…`
> form under the namespace rule.

**Namespacing an id removes it from every built-in table keyed by the generated `SkillId` union.**
The coupling is a catalogue MEMBERSHIP test, not a parse, so the audit above does not cover it: a
`Record<SkillId, …>` lookup with a namespaced key misses, and the miss usually has a silent fallback
rather than an error. Before adding or changing one, classify it.

| Kind of table                                | What a miss means                                | What to do about it                                                                                |
| -------------------------------------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Values **derivable from a skill's taxonomy** | The lookup asked the wrong question              | Take a taxonomy instead of an id, so a namespaced skill is answered on its own domain and category |
| Values **authored per id**                   | The skill has no row and no row it could inherit | State the row-less answer as a rule, in the table's own doc comment, and do not derive one         |
| Genuinely **about the public catalogue**     | Correct — the skill is not the catalogue's       | Say so where the lookup is, or the next reader reads it as the first kind                          |

The two live examples are deliberately different and are the pattern to reason from. `resolveAssignment`
(`packages/matrix/src/read-model/assignment-defaults.ts`) takes `string | SkillTaxonomy`, because
`targetsOf` branches on `domainId` and `categoryId` alone — so a marketplace's skills REACH sub-agents.
`PRELOAD_DEFAULTS` (`packages/matrix/src/read-model/preload-defaults.ts`) is
`Partial<Record<SkillId, readonly RoleFlavor[]>>` with one hand-written row per catalogue skill and
nothing deriving it — so a marketplace's skills are **lazy by rule**, and `createLoadStateResolver`
refuses a namespaced id outright rather than consulting the table. Reach is taxonomy-aware and
eagerness is not, on purpose. A user's saved `SkillAssignment.preloaded` still overrides it per
`(skill, sub-agent)`, which is why the cheap direction is the safe one.

The two error-severity findings `checkMatrixHealth` produces divide the same way, in opposite
directions. `checkUnauditedSkills` warns only for ids the built-in catalogue names — otherwise a
custom marketplace draws one warning per skill on every `doctor` run and can never reach a clean bill
of health. `checkAuditVerdictContradictions` reads the same manifest and is therefore constructible
**only** for the catalogue's own checkout: a skill outside the manifest can contradict no verdict, and
the load-side collision guard refuses any other marketplace shipping an id the manifest names.

**Sub-agent ids are outside this rule entirely.** Marketplaces ship skills, never sub-agents — every
sub-agent comes from this application's own roster — so `resolveAssignment` reading the roster from the
vendored `SUB_AGENT_GROUPS` union is correct by design, not the same defect one axis over.
