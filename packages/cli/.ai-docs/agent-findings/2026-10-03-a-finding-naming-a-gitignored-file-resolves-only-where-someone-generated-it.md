## What Was Wrong

`2026-09-03-the-schema-validating-a-compiled-agent-refuses-two-keys-its-own-template-emits.md`
lists `e2e/helpers/handrun.gen.mjs` under `affected_files`. That file is generated by
`scripts/handrun.mjs` and is gitignored (`.gitignore`: `packages/cli/e2e/helpers/handrun.gen.mjs`).

The "this repository" spec in `scripts/check-findings-frontmatter.test.ts` resolves every
`affected_files` entry with `existsSync` and holds the unresolved ones to a fixed list. So the spec
passes only in a tree where somebody ran the hand-run bundler, and fails anywhere else:

```
bun run --cwd packages/cli test scripts/check-findings-frontmatter.test.ts
# in a copy without the bundle:
#   holds its dangling frontmatter references to the ones already reported
#   + { file: "2026-09-03-the-schema-validating-…", key: "affected_files", value: "e2e/helpers/handrun.gen.mjs" }
```

Nothing generates the bundle before the unit suite. `grep -rn handrun` over
`.github/workflows/*.yml`, `vitest.config.ts`, `vitest.global-setup.ts` and `package.json` finds
nothing, and `ci.yml`'s `check-cli` job runs `bun run test --filter=agents-inc` on a fresh checkout.

## Fix Applied

None — discovery only. Found while running the `scripts/` suites after a documentation edit. Both
files belong to other lanes.

## Proposed Standard

`TEMPLATE.md` rule 6 should say that `affected_files` names tracked files only. A generated or
gitignored artefact is named by the tracked file that produces it (here `scripts/handrun.mjs`). Two
alternatives for whoever owns the checker: drop the entry from the 2026-09-03 finding's
frontmatter, or have the checker count a gitignored path as resolved. The second keeps the verdict
the same on every machine without editing a dated finding.
