## Dispositions — category placement and exclusivity

**A. `desktop-framework` stays `exclusive: true`.** It is the anchor fence the 14 `requires`
bindings point at. The `{electron, tauri}` conflict group (default-rules.ts:83-86) is wholly
inside this exclusive category — redundant, dies free with decision 2, nothing lost. The
"Desktop Framework" `alternatives` group (default-rules.ts:725) is informational and untouched.

**B. `desktop-multiwindow` — radio redundant: CONFIRMED. Un-flag: YES.** Once
electron-multiwindow carries `requires [electron]` and tauri-multiwindow `requires [tauri]`,
their mutual exclusion follows from the framework radio via requires-reachability: whichever
framework is selected makes the other pair-member's requirement unsatisfiable. The radio then
restates a fact another mechanism already carries — exactly the redundancy decision 2 kills
conflict groups for. And the category has no intrinsic pick-one semantics: its members are
per-framework how-to guides, not competing tools. A future second Electron windowing skill
would _compose_ with the first; a kept radio would wrongly forbid that combination. Un-flag.

**C. `desktop-security` — radio redundant: CONFIRMED. Un-flag: YES.** Same mechanism, same
argument as B. Hardening guides compose; nothing about "desktop security" is pick-one. The
pairing is an artifact of per-framework naming, and the framework fence already carries it.

**D. `desktop-packaging` — radio redundant in effect: CONFIRMED. Un-flag: NO — keep exclusive.**
This is the partial refutation of the worksheet's "makes all the paired radios redundant too".
Observationally the radio is as redundant as B and C — today. But unlike B and C, the category
itself has real pick-one semantics independent of the framework divide: an app has exactly one
packaging pipeline. The Forge skill's own decision framework poses Forge vs electron-builder as
an either/or toolchain choice (SKILL.md §"Forge vs electron-builder"), and the electron-updater
finding makes an electron-builder skill a plausible future member of this category. The moment
one joins, the radio is the _only_ mechanism that can fence electron-forge ⊥ electron-builder:
both would carry `requires [electron]`, so requires-reachability cannot separate them, and
conflict groups no longer exist. Decision-2 consistency cuts the other way here — the principle
targets fences that duplicate another mechanism's statement of the same fact. B and C's radios
duplicate the framework fence. Packaging's radio states a different fact ("one packaging
toolchain per project") that merely coincides with the framework fence under current membership.
Zero behavioral cost either way today; the tie-breaker is future-correctness, and it favors
keeping the flag. (Acceptable alternative if the owner wants strict purism: un-flag all three
and re-flag packaging when an electron-builder skill lands — a one-line §2a-style flip. Keeping
it now just avoids relying on someone remembering.)

**E. The eight open single-vendor categories — no changes.** `desktop-backend`, `desktop-ipc`,
`desktop-mobile`, `desktop-plugins`, `desktop-storage`, `desktop-testing`, `desktop-ui`,
`desktop-updates` each hold one skill; the `requires` binding closes each completely, and
open + single-member needs no radio. Placement is coherent, not lopsided: the Electron-only
categories are not "missing" Tauri members — the vendors factor the same concerns differently.
Tauri's updater lives inside tauri-bundling (and the updater plugin inside tauri-plugins), its
IPC inside tauri-backend/tauri, its storage in plugins (store, stronghold, sql). No moves, no
merges, no new categories.

**F. Apply-phase ordering constraint.** Land the 14 `requires` bindings BEFORE or in the same
change as un-flagging `desktop-multiwindow`/`desktop-security` — never between, or those two
pairs are briefly fenceless. The `{electron, tauri}` group deletion is safe at any point, since
`desktop-framework` stays exclusive throughout.

## Contradicts the worksheet

1. **"…makes all the paired radios redundant too" (§B10) — confirmed as behavior, refuted as
   disposition.** All three radios do become observationally redundant once `requires` lands,
   but only `desktop-multiwindow` and `desktop-security` should be un-flagged.
   `desktop-packaging` should stay exclusive: it carries genuine pick-one category semantics
   (one packaging pipeline per app; Forge vs electron-builder is either/or per the Forge skill's
   own decision framework) that would become the only available fence if an electron-builder
   skill ever joins the category. See disposition D.
2. **"Cleanest batch… uniform fix" — one asterisk.** The uniform binding holds 14/14, but
   electron-updater carries a second, _conditional_ constraint the uniform fix cannot express:
   it defaults to the electron-builder packaging pipeline (reads `app-update.yml`, which only
   electron-builder writes) and is contra-indicated specifically beside electron-forge **with
   the Squirrel maker** — Forge-without-Squirrel and generic-provider setups are documented
   electron-updater paths in the skill's own decision tree. Cross-category, both
   electron-bound, so neither exclusivity nor `requires` can state the Squirrel case. Needs a
   `deferredToD306` record, not silence.
3. **Worksheet §B10 says "the six single-vendor open categories" then enumerates eight** —
   electron-ipc, electron-storage, electron-ui, electron-testing, electron-updater,
   tauri-backend, tauri-plugins, tauri-mobile. The matrix confirms eight open desktop
   categories (backend, ipc, mobile, plugins, storage, testing, ui, updates), one member each.
   Count typo only; the enumeration itself is correct.
