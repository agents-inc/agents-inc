# Editor v6 — bringing `apps/editor` onto the latest Claude Design files

**Tracker row:** EDITOR-09 in [`../../editor.md`](../../editor.md). This folder is that row's detail
and its live progress file. It is the session's memory: the programme spans many hours and several
compactions, and anything not written here is lost.

**Owner brief, 2026-08-26.** The design folder was refreshed (all of `.claude-design/` is dated
2026-08-25). Seven changes were named:

1. a grouping toggle in the agents sidebar — group by domain or by scope;
2. the add-skill button beside the search field restyles when the page is scrolled;
3. the stack-selection header becomes collapsible;
4. the agents header on the right adopts the section-header treatment used elsewhere;
5. agents lose the five-square effort meter and gain a cycling word, like every other toggle;
6. a new call to action that shows the actual compiled output, with real syntax highlighting;
7. a chat field docked to the bottom of the main column, which will eventually pre-select skills
   and sub-agents from a natural-language description.

The owner asked for a recommendation on (6)'s highlighter and on (7)'s AI provider, said (7) can
ship as UI only for now, and said to park anything genuinely undecidable and work the rest.

## The three architecture decisions

Each was researched against the live tree on 2026-08-26. The full option tables are in
[`decisions.md`](./decisions.md); the headline and the single strongest reason are here.

| #   | Question                            | Decision                                                                                  | Why, in one line                                                                                                                                                                  |
| --- | ----------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | How to highlight the preview        | **Shiki, client-side, fine-grained, lazy behind `import()`, via `codeToTokens`**          | The theme already exists in this repo — `inkRampSyntaxTheme` in `apps/www/astro.config.ts` is a Shiki TextMate theme built from this exact palette, and it is already owner-ruled |
| 2   | Where the preview's bytes come from | **Extract a shared pure renderer the CLI's write path also calls**                        | A server endpoint would have to import the same node-free renderer, so the extraction is a prerequisite for it rather than an alternative                                         |
| 3   | How the composer talks to a model   | **Anthropic direct from the existing Hono worker, behind a Cloudflare AI Gateway (BYOK)** | The composer's output is a mutation of a Zod-typed store, and this is the shortest path from that schema to a provider-enforced typed value                                       |

**Monaco was rejected** — measured at ~745 KB gzipped against Shiki's ~59 KB, and adopting VS Code's

**"Run a compile in a folder" has no subject.** `--ui` on `init` and `edit` shells out to the OS
browser opener against the deployed `https://agentsinc.sh`; there is no local-serve path, so the
local and deployed cases do not diverge and one renderer serves both.

The prototype is a prototype. Five of its strings name things the CLI does not emit, and one of its
scales contradicts a shipped contract. **The contract wins in every case below** — these are
implementation decisions, not open questions, and a reader who follows the design file instead will
ship a preview that diffs against reality on its first line.

### The effort hazard, written out because it fails silently and in the worst direction

`agentEffortSchema` is `z.enum(AGENT_EFFORTS)` and sits inside `persistedConfigSchema`. Narrowing the
scale to the design's four would make one stored `xhigh` fail the whole `safeParse` in
`config-store`'s `merge`, which returns `current` — **discarding the visitor's entire saved
configuration**, reporting only to Sentry. Renaming `medium` to `med` breaks the share-link wire
contract in both directions at once: links minted here would not decode on the CLI, and links
arriving from the CLI would not decode here.

The precedent for resolving it is already in the same file: `AGENT_MODELS`. Contract's scale,
contract's spelling.

**And nothing binds the four copies together.** `EFFORT_NAMES`, `seedEffortSchema`, `AGENT_EFFORTS`
and `AGENT_OPTIONS.efforts` (the editor's e2e constants) are four hand-written literals;
`check-enumeration-drift.ts` binds only the first to a documentation table, and `tsc` cannot see the
others because each is independently `as const`. Any change to the scale must touch all four, and no
gate will notice a miss.

## Owner rulings, 2026-08-26 (second round)

These supersede the Phase C spec wherever they differ. The spec was written before them.

1. **THERE ARE NO MODES. One field, one button.** Superseded the same day: modes were first cut from
   three to two (`ask` dropped), then removed entirely. The owner's reason is that `build` and
   `adjust` "essentially do the same thing", which the Phase D spec had already run into from the
   other end — the settled output schema has no field for the properties `adjust` was supposed to
   edit, and structured outputs cannot express one. A distinction neither the UI nor the schema
   could carry was not a distinction.
2. **Intent comes from the prompt text.** ~~and suggestion chips prefill it~~ — **the chips were
   REVERSED by the 2026-08-30 design refresh** and are gone. They shipped in Phase C exactly as this
   ruling described (a writing aid, not a mode, with nothing downstream branching on which was
   clicked); the refreshed `DECISIONS.md` cut them with a one-line reason — "the placeholder does
   that work" — and rewrote the placeholder to name all three capabilities in one sentence. Removed
   in Phase F. **The half that survives is the half that mattered**: intent still comes from the
   prompt text alone, and typing a sentence by hand still reaches the only place there is.
   2b. **What the feature actually does, settled 2026-08-26 and narrower than Phase D was specced
   against:** it has a back-and-forth with the user, proposes a set of skills, and on go-ahead
   selects them. It may also choose **preload vs lazy** per skill, and it may **save the stack**.
   That is the whole surface. It does not touch sub-agents, scope, install mode, or anything else.

   Two consequences the schema has to respect, both measured:

   - **The proposal emits the shape already stored. No translation format.** Owner ruling: "as long
     as it outputs the same shape as what we currently store when selecting skills its fine but lets
     keep it the same if we can." An earlier plan invented a per-entry format with an optional agent
     scope; that is dropped. The model emits `skillEntrySchema` as it stands — `install`, `scope`,
     and `assignments` keyed by agent id with `{ load, enabled }` — so a proposal is indistinguishable
     from a hand-made selection and there is no second format to drift.

     This also settles the owner's own example without a special case: "always have React in context
     when developing for web" is preloaded on the web agents' edges and untouched on the rest, which
     the stored shape expresses directly and a per-skill `load` could not.

     **Two forced deviations, not one** — corrected 2026-08-26. `assignments` is `Record<agentId, …>`, and a structured
     output cannot express an open record: every object in the schema must carry
     `additionalProperties: false`, which admits no dynamic keys. So the wire form promotes each key
     to a field — `assignments: [{ agent, load, enabled }]` — and the client does one
     `Object.fromEntries` on arrival. Field for field it is the stored shape; only the record becomes
     an array, and only because the API cannot carry a record. **`PersistedConfig["skills"]` is
     `Record<skillId, SkillEntry>` and takes the same promotion for the same reason** — this file said
     "one forced deviation, and only one" and was wrong; the argument that moved `assignments` applies
     one level up and nobody noticed. Measured against the published SDK's own type declarations
     rather than recalled — re-verify both before implementing.

   - **There is exactly ONE saved-stack slot, with a fixed name** — `SAVED_STACK_NAME = "Saved stack"`
     in `stores/saved-stack-store.ts`. So "it can save the stack" has a subject, but a model-chosen
     stack NAME has nowhere to go today. Either saving overwrites the one slot, or named stacks are
     a prerequisite. Do not invent a naming surface.

3. **A proposal is ALWAYS shown before anything is applied.** This settles what
   `.claude-design/README.md` called the biggest open item in the whole design. Never a silent
   mutation, in either mode. `judgeSelection`'s verdict now has somewhere to go, and no repair loop
   is needed.
4. **The concept of "recommended" is removed completely from the editor and the CLI.** Measured the
   same day: **it has no code subject.** `grep -rniI "recommend" apps/editor/src apps/editor/e2e`
   returns 0; the only hits under `packages/matrix` and `packages/cli/src/types` are the word inside
   one skill's description (Qdrant's "recommendation API"), and the `apps/www` hits are ordinary
   English ("the recommended default"). So the ruling is not a removal but a **prohibition**: the
   design source still draws a `recommended` filter chip beside the domain chips, and that chip is
   now dead. Do not build it from the design file.
5. **The marketplace button floats.** It keeps its sticky-inside-the-column mechanism —
   `position: fixed` was tried there and rejected (EDITOR-35).
6. **`MenuTrigger` carries the focus ring.** No carve-out in `packages/ui/CLAUDE.md`'s rule.
7. **The proposal shows what changes by reusing the info panel's diagram** — _"How are you showing
   users what will change when they accept the plan? We should reuse the info panel diagram imo.
   That way it's clear what is being added and removed."_ The diagram is `MatrixGrid`
   (`packages/ui/src/components/matrix-grid.tsx`), the domain × role field inside the skill options
   panel, whose only call site today is `skill-options-panel.tsx`. The ruling turns that grid into a
   **diff**, and in doing so closes the removal-row question this file records as open under Phase C
   — a proposal needs no mode to know which it is doing, because it shows what changed.

   **This ruling was recorded only inside `phase-c-spec.md` (§11, `:1947`, `:2531`) and nowhere
   else, while the phase that owns that spec was marked LANDED AND RETIRED.** It reached no tracker,
   no roadmap and, until now, not this section — which is exactly the disappearance the
   delete-on-land rule exists to prevent, running in the opposite direction. Filed as **EDITOR-56**
   on 2026-08-26; the design is in the spec's §11.1, §11.9 and §11.10 and is not restated here.

### Phase C — the docked composer, UI only (owner item 7) — **LANDED 2026-08-26**

One field, one button, two suggestion openers above it, and a proposal that always precedes any
change. No modes: the design draws three, and they were cut to two and then to none. Spec:
[`phase-c-spec.md`](./phase-c-spec.md).

**Nothing is persisted** — draft and proposal are local `useState`, so `ui-store.ts` was never
touched and the migration hazard has no subject here.

**`Segmented` gained nothing.** The reuse-with-a-`cva` decision existed only for the mode track;
with the track gone it is moot, and the whole `packages/ui` diff is one type-scale step.

**The chips are a writing aid, not a mode** — nothing records which was clicked, and a hand-typed
sentence reaches the same place. Pinned in both directions, by grep and by behaviour, because that is
the thing most likely to drift back into a mode.

**Openers sit ABOVE the field**, and the reason is structural rather than aesthetic: the band's bottom
hairline is flush with the viewport edge because the band is the dock's last child, so a strip below
it reads as a second band. The dock never draws three things because openers and a proposal are
mutually exclusive by construction — openers need a blank draft, a proposal needs a submitted one.

**The removal-row gap is CLOSED as a design and OPEN as work.** `build`'s old "cannot remove a
skill, by construction" guarantee went with the mode, and one field invites _"drop the ORM"_. This
file used to record the removal ROW as undrawn and Phase D's stage 7 as partly blocked on that
design; **ruling 7 answered it the same day** and `phase-c-spec.md` §11.1 carries the answer. What is
undrawn is no longer the design but the code — `MatrixGrid` has no `removed` state and no read-only
mode, and `ProposalGroup.verb` is the closed union `"added" | "changed"`, so `tsc` refuses a removal
rather than mis-rendering one. That is EDITOR-56, not a Phase C defect.

**Three decisions this phase made that the design does not state**, each recorded where it was made:

  palette does not exist; this repository's does — every core token carries a dark value — so the

  derived, which is unchanged by this.
- **The strip is the half that gives.** Nine domains plus a wide clear control is wider than the
  main column at 1600px, and letting the filters move put a `z-60` sticky row over the roster panel —
  observed, not hypothesised. So the tabs scroll inside their own group and the filters hold the
