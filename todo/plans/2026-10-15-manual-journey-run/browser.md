## Defects

**D1. Typing in the docked composer scrolls the page down 66px per keystroke.**
Repro: `repro/browser-repro-50.sh`. It opens the editor, clicks into `Composer prompt` with the page at the top and types
"Add Prisma". The wrong output is `scrollY after each keystroke: 66,132,198,264,330,396,462,528,594,660`, where it
should be all 0. `html scroll-padding-bottom: 130px` is printed alongside. It reproduces in full Chromium 141 (`channel: "chromium"`),
at 1280x800 as well, and with no stack chosen.
Suspected cause: `useScrollClearance` (`apps/editor/src/features/configure/lib/use-scroll-clearance.ts`, first
landed in `fe1761cf` on 2026-10-04, after the last run) sets the document's `scroll-padding-bottom` to the dock's own height.
The textarea sits inside that sticky dock, so each caret reveal lands in the padded strip and scrolls the document,
and the dock rides along, so every keystroke repeats it.

**D2. Inside the stuck filter bar, typing, moving the caret or Tabbing scrolls the page back up.**
Repro: `repro/browser-repro-51.sh`. Wrong output: with the bar stuck at y 2500, `e`/ArrowLeft/ArrowRight/Home/End give
`y=2397 … 2294 … 2191 … 2088 … 1985 stuck=true`. With the bar stuck at y 3000, four Tabs give `2538 (ADD SKILL),
2140 (WEB 84), 1742 (API 56), 1344 stuck=false (AI 20)`. The y should be unchanged throughout. `html scroll-padding-top: 123px`.
Suspected cause: the same hook's `scroll-padding-top`, set to the stuck bar's height. Every control inside the bar
lies within that padded strip, so a caret reveal or a focus scroll moves the document. This is D1's mechanism on
the top edge. 2026-10-01 missed it because a filtering query shortens the page until the bar unsticks. Only an
input that keeps the catalogue long (`e`, or a caret move) shows it.

- **O3.** Under `?q=query` the domain strip highlights AI while API's Knex.js is the top result, and emptied
