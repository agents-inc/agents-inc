## Defects

**D1. A round trip over an installed external skill rewrites its `metadata.yaml` in a different key order, even when the run reports "No changes made."** (journey 24; bears on journey 11's "an edit the user changes nothing in must write nothing")
Repro: `$S/repro-24.sh`. It needs the worker on :8787 holding `yygY4oK_` (it re-POSTs `payloads/yygY4oK_.raw.json`, content-addressed) and tmux. It runs `init --from yygY4oK_` in a fresh HOME/project under `/tmp/c924/gap-authoring/repro24.XXXX`, then a bare `edit` (mints `wHt_gYtr`), then `edit --from=wHt_gYtr` answering `y`. Output:

```
Wrote 1 skill(s) this configuration carries: external-web-testing-test-driven-development
No changes made.
EXIT=0
--- metadata.yaml diff (before < > after), skill unchanged:
1a2,7
> forkedFrom:
>   skillId: external-web-testing-test-driven-development
…
10,15d15
< forkedFrom:
…
diff exit=1
```

The same reorder happened in the journey run (`$S/24-after-init/proj/.claude/skills/…/metadata.yaml` vs the live file). `SKILL.md` and `writing-good-tests.md` keep their bytes but get new mtimes, and `config-types.ts` is rewritten byte-identical with a new mtime.
Suspected cause: two writers serialise the carried skill's metadata with different key orders. The install-time generator puts `forkedFrom` last. The re-apply path, which writes the external entry's carried `metadata.yaml` back through the metadata writer, puts `forkedFrom` first. And the "carries" write is unconditional even when the carried bytes match what is on disk.
