## Defects

### D2' — load warnings repeated ×3 by global runs over a registered project: also `metadata.yaml`, also `compile` (journey 39; extends entry D2)

Repro: `repro/gap-cli-repro-39.sh`.
It is self-contained: it copies the public catalogue checkout, breaks one metadata.yaml and one SKILL.md, and uses
the editor-minted ids, re-minting them from the saved payloads if the worker lost them. Last run: `init --from x1`,
`edit --from x3`, `compile (HOME) x3`. With no registered project the edit and compile print each warning once.

Suspected cause: the global run's fan-out to registered projects reloads the marketplace (twice per project here), and
each load prints its own warnings, with no per-run dedupe. `doctor` has the same lack of dedupe: it loads twice and
prints the raw warnings between its table rows, on top of its own Marketplaces row.

### D3 — a skill skipped at load silently takes the sub-agents that existed only to carry it (journey 39)

Repro: the same `repro-39.sh`, section D3. Editor id `wej0WC-q` puts `agents: {web-developer: on}` beside React's
assignments to 4 more agents, and the Install dialog says "5 sub-agents". If React's metadata.yaml does not parse, the
run prints `Skipped 1 skill(s) this catalog does not know: web-framework-react`, lists `Sub-agents: web-developer`, and
compiles 1 agent. No line names web-researcher, web-tester, pm or reviewer as dropped, or says why.

Suspected cause: the seed's agent roster is derived as `on` agents plus the agents in surviving skills' assignments.
Once the skill is filtered out at load, its assignment-only agents fall out of the roster, and only the skill skip is
reported.

### D4 — `build marketplace` over a marketplace repo's unparseable `.agents-inc/config.ts`: partial write, then exit 1 with an installation remedy (journey 38's build leg)

Repro: `repro/gap-cli-repro-38-build.sh`.
It is self-contained (CLI only). `marketplace.json` is rewritten (`0.1.0` → `0.2.0`) and `catalog.json` is left stale,
with `EXIT=1`. The remedy names `uninstall` and `init`, which do not apply to a marketplace repo. `doctor` there prints
`Check threw` and then dies in the Operational section with the raw error chain, so it never reaches a Summary. That
contradicts the refusal's own "'npx agents-inc doctor' reports the same file". An empty or export-less file is read as
absent with no line.

Suspected cause: `commands/build/marketplace.ts` calls `writeMarketplace` before `loadMarketplaceMatrix`, which is the
first read of `loadSourceRepoConfig`, and nothing reads that config up front. `unreadableSourceRepoConfig` reuses
`configUnreadableError`, whose remedy is the installation's. Doctor's operational checks do not catch that reader's
throw. `loadConfig`'s `exportsNothing → null` is what makes an empty or export-less file read as absent.

- O1 (journey 37, eject): the ending's remedy `Run 'npx agents-inc doctor' to see what this installation is left
holding` leads to a doctor that reports 14/14 green under a live global install. The 237 skills the run left in a
  config-less project are not named. Same cause as entry D1 (`checkNoOrphans` lists agent `.md` files only).
- O2 (journey 38 c): a global `compile` / `edit --from` that skips an unreadable registered project ends `✓` with exit 0. The skipped project's inlined global section is now stale (it lacks the added Zustand). No row says whether this
  is `COMPLETED_WITH_FAILURES`.
- O3 (journey 39): when a public-catalogue skill is skipped, every built-in stack naming it warns (11 lines), although
  the configuration uses no stack.
- O4 (build): `build plugins` never reads the marketplace's `.agents-inc/config.ts`. With `skillsDir: 'skills'` declared
  and the skills moved there, it prints `Compiled 0 skill plugins` and then `✓ Plugin compilation complete!`, exit 0.
- O5: the eject ending prints its failure twice: once as `Warning: Could not create …` and again in the account, with
  three blank lines between them.
- Not driven by hand, read from source: `lifecycle/project-config-unreadable-under-install` and
  `config-unreadable-under-install` build their installation with `init --from` (`createDualScopeEnvFromSeed`). Row 38's
  status cell says "every spec named below opens from a hand-written config".
