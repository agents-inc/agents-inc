## Defects

**D1 — `list` reports `Agents: 0` for every Codex installation.**
`source $J/env.sh codex; export HOME=$L/h1 CODEX_HOME=$HOME/.codex; cd $HOME/code/proj1`, after
`agents-inc init --from im2vXBWi --provider codex`; then run `agents-inc list`. It prints `Agents:  0` and no `Agents:`
directory line, while `ls .codex/agents | wc -l` gives 16. The same happens for the global installs (h5, h6), and for `list --provider codex`
in a dual scope. A Claude install of the same id prints `Agents:  18` and `Agents:  …/.claude/agents`. Read from code:
`AGENT_FILE_EXTENSION = ".md"` in `packages/cli/src/cli/lib/plugins/plugin-info.ts`, which `isCompiledAgentFile` uses.
This is the CLI-896 class: an agent lister that only knows `.md`.

**D2 — a GLOBAL Codex install run from HOME writes a trust entry for HOME itself.**
Fresh `HOME=$L/h5`, `cd $HOME`, then `agents-inc init --from vhKU1nNy --provider codex` (plugin+global, every sub-agent global).
The output says "Trusted this project in your Codex configuration, so Codex reads its sub-agents: added
[projects."$HOME"] with trust_level = "trusted" to $HOME/.codex/config.toml", and config.toml then has that table.
The same happens for eject+global (h6). The entry is not needed: in a copy with the entry deleted (`h5b`), a turn from
`$HOME/code/other` still sends all 16 roles in `agent_type`. The code says the opposite should happen.
`codex-compile-notices.ts` (`trustNotice`) states that "a global-only installation has no project roles for a trust
entry to unlock, and writing one would grant trust to a directory with nothing in it". But `holdsProjectRoles(HOME)` globs
`agentsDir("codex","project",HOME)`, which is `~/.codex/agents`, the same directory as the global roles. So the
check is true and the user's whole home directory is marked trusted. Same class as CLI-901 and CLI-895: a
project-scope path resolved at HOME.

**D3 — the global eject install from HOME names a directory it never wrote.**
Fresh `HOME=$L/h6`, `cd $HOME`, then `agents-inc init --from JJV4zKKJ --provider codex`. The output says "Copied 10 skills to
.codex/skills/", which is correct, then "Skills copied to:\n $HOME/.agents/skills\n    cli-framework-oclif-ink/ …".
`ls $HOME/.agents`→ "No such file or directory", and the skills are in`$HOME/.codex/skills`. Read from code:
`reportSkillsCopied`in`packages/cli/src/cli/commands/init.tsx`collapses both scopes into`resolveInstallPaths(cwd, "project").skillsDir`when`isHomeDirectory(cwd)`. That is right for Claude, where both answers
are `~/.claude/skills`, and wrong for Codex.

**D4 — a Codex uninstall deletes or judges Claude's `.claude/`.**
`HOME=$L/h1; cd $HOME/code/proj1` holds only a Codex project installation. Run `mkdir .claude`, then `agents-inc uninstall --yes`.
The output includes "✓ Removed .claude/", and `.claude` is gone. In the dual scope
(`h2/code/proj2`, `uninstall --provider codex --yes`) it prints "Kept .claude/ (contains user content)", which calls the
Claude installation user content. The Codex run's own emptied `.codex/` and `.agents/` are left behind with no line.
Read from code: in `packages/cli/src/cli/commands/uninstall.tsx`, `removeDirIfEmpty(target.claudeDir)` runs, and
`claudeDirKept` is computed, with no provider condition.

**D5 — `doctor` in a scope holding both installations reports only the Claude one, with no way to ask for the other.**
`HOME=$L/h8a; cd $HOME/code/p` has a Claude install of `im2vXBWi` plus `init --from im2vXBWi --provider codex`. Remove
`.codex/agents/pm.toml`, `.codex/agents/reviewer.toml` and `.agents/skills/web-framework-react`, then run `agents-inc doctor`.
The operational rows are all Claude's: "Config Valid ✓ .agents-inc/claude/config.ts", "Layout ✓ This project is on
.agents-inc/claude/", "Agents Compiled ✓ 18/18", "Skills Installed ✓ 10/10". The two missing roles and the missing Codex skill
are reported nowhere. The only Codex trace is the two-installations finding, filed under the row label
"Placements Offered ✗". `agents-inc doctor --provider codex` → "Nonexistent flag: --provider". Row 64 justifies the missing flag
by saying doctor "reports on every installation in the scope".

**CLI-901 — CONFIRMED, not fixed.** Fresh `HOME=$L/h6`, `cd $HOME`, then `agents-inc init --from JJV4zKKJ --provider codex`. That puts 10

## Observations (not verdict-bearing)

- **Editor copy.** For an eject+global Codex selection, step 02 reads "ejects 10 skills into `.agents/skills/` … Global
  skills land in ~/.codex", but they land in `~/.codex/skills` (`browser/11-eject-global-c-install-dialog.png`).
  Claude's sentence has the same shape. The Codex notice reads "agent summoner **or** skill summoner are not installed".
- **`share --provider codex`** prints "Install it: npx agents-inc init --from -AMfjSoj" with no `--provider codex`.
  Following it installs onto Claude.
- **`edit --from 7Tpgj5aX --provider codex` with no TTY** refuses and suggests "Run 'npx agents-inc edit --from 7Tpgj5aX'",
  dropping `--provider`. In the dual scope it ran in, that suggested command is itself refused.
- **What a Codex uninstall leaves behind, unreported.** The `[projects."…"] trust_level = "trusted"` entry it wrote stays,
  and so does `[marketplaces.agents-inc]` after the global plugin uninstall.
- **Content check on Codex.** `doctor`'s content check prints "Agents ✓ No agents to validate" on every Codex install, which
  holds 16 role files. Claude prints "18 agents validated".
- **Edit wizard on Codex.** The Agents step offers Agent Summoner and Skill Summoner with no note, and `edit` never prints
  the 16-of-18 notice. The editor disables both with the reason.
- **Read-path wording.** The refusals on `share` and `compile` say "Refusing to **install** …".
- **Role prompt content.** The developer_instructions of pm, web-developer, api-developer, cli-developer and
  ai-developer tell the agent to read or write `.claude/decisions.md`, `.claude/patterns.md` and `.claude/progress.md`.
  So a Codex sub-agent following them would create `.claude/` in a Codex project. This comes from the marketplace
  content, not from the CLI.
- **Provider control.** The editor's provider control resets to Claude on reload. This is by design: `ui-store.ts`
  marks it transient.
