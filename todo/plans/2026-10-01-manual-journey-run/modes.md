# Lane `modes`: results (2026-10-01)

Built CLI `agents-inc/0.165.0`, real `claude` 2.1.287. Every run used a fake HOME under
`$J/lanes/modes/` (`$LANE` below). Wizards were driven in tmux one key at a time, and the screen was
read after every step. I ran no test suites. The marketplace for journey 21 was built from an rsync copy
of `~/dev/skills` (without `.git` or `node_modules`) at `$LANE/mkt/skills`. Before building, I
moved its checked-in `dist/` and `.claude-plugin/` aside, so the build started from nothing.

Helpers, all in `$LANE`:

- `run.sh <home> <cwd> <cmd>` runs a command under that HOME.
- `keys.sh` sends keys 150 ms apart. Ink drops keys that arrive faster.
- `srcrows.sh` reads the Sources rows with the selected option marked `[SEL]`, taken from the bold-cyan
  escape code.
- `tc.sh` runs `tsc --strict` on `config.ts`, plus a probe that assigns a bogus literal to
  `SkillId`, `AgentName` and `Category`.
- `shim/claude` is a logging wrapper that `exec`s the real binary.

## Defects

**1. `edit` (and `init` run in a project under an existing global install, which routes to `edit`
through the dashboard) installs writing sub-agents into an untrusted Claude project without the
folder-trust line.** Journey 79 says the user "installs writing sub-agents … into a Claude project
Claude Code has not been told to trust, and is told the folder must be trusted". That holds on
`init`'s own install path and on `compile`, and nowhere else. In source, `hostCompileNotices` is
called only from `src/cli/commands/compile.ts` and `src/cli/commands/init.tsx`
(`reportWhatThisHostCannotCarry`); `edit.tsx` has no call. Reproduction:

```
source $J/env.sh modes; export HOME=$LANE/h79 CODEX_HOME=$HOME/.codex   # project install at $LANE/p79, no ~/.claude.json
cd $LANE/p79; agents-inc edit          # in tmux
  Enter (Skills → Sources) · Enter (→ Agents) · Down×3 (API Developer) · Space · s  → "[✓] [P] API Developer"
  Enter (→ Confirm) · Enter
# screen: "Changes: + api-developer (agent) / 1 agents rewritten, 5 unchanged / ✓ Done", EXIT=0,
#         0 lines mentioning trust
grep -c '^hooks: {"Stop"' .claude/agents/api-developer.md      # → 1
agents-inc compile | grep 'trust the folder'                     # → "... Until then, 4 sub-agents' completion gates will not run ..."
```

The same silence came from `init` in `$LANE/h17/proj/p17` (HOME `h17` already held a global
install). `init` showed the dashboard (`Skills: 1 installed … ❯ Edit`). Edit → add Zustand [P] → Web
Developer `s` → `[P][G]` → confirm printed `+ web-developer [P] (agent)`, `✓ Done`, with no trust
line. `p17/.claude/agents/web-developer.md` carries the Stop hook, and a `compile` right after printed
`… Until then, 1 sub-agent's completion gate will not run …`. A user who types `init` in a second
project is therefore never told. This needs the owner to rule whether `edit` owes the notice.

## Observations (not verdict-changing; recorded for the owner)

- **A project-scope edit rewrote the global `config.ts`.** This was J17 run 2: a project `edit` that
  switched only the project-scoped Zustand to Plugin. Snapshot `$LANE/snap/17/g-cfg-0` was taken
  just before the run. Afterwards `diff -r $LANE/snap/17/g-cfg-0 $LANE/h17/.agents-inc` shows one added
  line in the global `config.ts`, `>   marketplaceName: 'agents-inc',`, with mtime inside the run.
  The global skills, agents and `config-types.ts` did not change. This comes from
  `writeFromProjectContext` → `writeGlobalPairWhenChanged` in `src/cli/lib/config-gate/index.ts`
  treating the newly resolved metadata as a global change. It is benign in content, but it is a
  write to a scope the run did not target. The same field also stays behind after a full switch back
  to eject (h5, J5).
- The swap edit (J5) printed `Installing skill plugins...` before `Copied 1 local skill(s)`, and
  then `Installed web-state-zustand@agents-inc`: the two halves' progress lines interleave. This is
  cosmetic.
- After a plugin→eject switch, `claude plugin uninstall` leaves
  `~/.claude/plugins/cache/agents-inc/<id>/` on disk. That is Claude Code's own cache, not this
  CLI's.
- Timings for real `claude plugin` work: directory-marketplace register + 2 installs, 2 s;
  GitHub-marketplace clone + 2 installs, 5 s; per-skill 4 s; first project-scope install in a fresh
  HOME, 17 s; `update`, about 2 s. Nothing was slow.
- "Once per distinct marketplace" was exercised only with one marketplace backing 2 skills (one
  call, deduplicated). No install here held two distinct marketplaces.

## Corrections

- **Row 5** ("PARTIAL, and blocked … needs a real `claude plugin install`") and **row 10**
  ("refresh success branch … TO TEST (blocked)") are blocked only on CI. With the real `claude`
  2.1.287 under a fake HOME both drive fine, in seconds, against both the real GitHub marketplace
  and a local directory marketplace.
- **Row 17**'s "two runs **or a global edit that owns both scopes**" is half true. A global `edit`
  run from HOME lists only the global skill; the project-scoped one does not appear. A project
  `edit` renders the global skill as `🔒`, and it cannot be focused. So two runs is the only route,
  and no edit owns both scopes.
- The **brief's** "`init`/`compile` print one line naming the folder" holds only for `init`'s fresh
  install path. `init` in a project whose HOME already holds a global install goes through the
  dashboard to `edit`, which prints nothing (Defect 1).
- **Row 21 / the brief's "a marketplace you build yourself"**: a copy of the skills repo can only be
  published as `agents-inc`. `build marketplace --name <other>` refuses because the 238 skill ids
  lack the `<other>-` prefix. `agents-inc` is accepted only because the copy keeps the catalogue's
  own `package.json` name (`@agents-inc/skills`), and the bare `build marketplace` refuses that
  scoped name.
