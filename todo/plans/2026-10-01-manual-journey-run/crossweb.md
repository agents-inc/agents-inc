## Defects

**D1. The output preview's skill descriptions do not match the install (CLI-898 is not live yet).**
Repro: in the editor, pick stack **CLI Tool** → Preview → `~/.claude/agents/cli-developer.md`. Then install the minted id (`0x5rKwRJ`) with `agents-inc init --from 0x5rKwRJ` and `diff` against `~/.claude/agents/cli-developer.md`:

```
< - Description: React component patterns
> - Description: Component architecture, hooks and React 19 patterns. Load when building or refactoring React components, custom hooks, forms, or async UI.
< - Description: Lightweight client state
> - Description: Zustand stores, client state patterns. Use when deciding between Zustand vs useState, …
```

It is the same in all 9 agents (13), and in `reviewer.md` and `web-tester.md` (27). Root cause: the editor fetches `.claude-plugin/catalog.json` live from GitHub (`apps/editor/src/lib/api/catalog.ts`). The published one (`agents-inc/skills` commit `3a51ef57`, 2026-09-06) carries no `activationDescription` (`grep -c activationDescription` = 0), so `resolveSkill` falls back to the label. The CLI-898 archive entry names this as an owner action: "rebuild the public marketplace's catalog.json with this CLI". Until then the preview and the install differ on every activation-table description.

**D2. The output preview orders an agent's skills differently from the install.**
Repro: as D1 (CLI Tool stack, id `0x5rKwRJ`). In `cli-developer.md` the preview's front-matter `skills:` is `[cli-framework-oclif-ink, meta-design-expressive-typescript]`; the disk has `[meta-design-expressive-typescript, cli-framework-oclif-ink]`. The activation table also differs:
preview `react, zod, zustand, vitest, reviewing, ts-config, git-hooks, eslint-prettier` (the payload/config order) against disk `react, zustand, zod, vitest, eslint-prettier, ts-config, git-hooks, reviewing`.
All 9 agents differ only by order and descriptions: as a multiset, every non-description line is equal. Both sides hold the same `stack` in `config.ts`.

**D3. The output preview leaves out files the install writes, and draws two files differently.**

- (a) For an all-global install run from a project directory, the CLI writes `<project>/.agents-inc/claude/config.ts` + `config-types.ts`. The preview's tree has only the `~/` root (`11 files` for 13, where the install wrote 13). See `holdsSomething(projectSplit)` in `apps/editor/src/features/configure/lib/output-preview.ts`.
- (b) For the external skill (25), the install writes `~/.claude/skills/external-meta-methodology-brainstorming/metadata.yaml`, which the preview's tree does not list.
- (c) That skill's `SKILL.md` in the preview reads `name: brainstorming`; on disk it is `name: external-meta-methodology-brainstorming`. The preview's subtitle names the disk path, `~/.claude/skills/external-meta-methodology-brainstorming/SKILL.md · new`.
- (d) In `config-types.ts` (25) the preview has `export type SkillId = 'external-meta-methodology-brainstorming' | 'web-framework-react'`, while the disk splits it as `// Custom | 'external-…' // Marketplace | 'web-framework-react'`.

**D4. The output preview's global `config.ts` disagrees with the install on non-machine fields.**
Repro: id `0x5rKwRJ` (13). The preview's global `export default` has `description: 'oclif, Ink, Zustand, Vitest'` and no marketplace fields. The disk's global config has no `description` (it went to the project config), and has `marketplace: 'github:agents-inc/skills'`, `marketplaceName: 'agents-inc'` and `projects: [...]`.
With an explicit marketplace (27) the preview draws `marketplace:` but not `marketplaceName:`. (`projects:` is machine-specific and arguably out of scope; the other fields are not.)

**D5. `edit --ui` (and `share`) run from a project directory over a global installation mint a payload with no per-agent assignments, so the round trip silently de-assigns skills.**
Repro (fresh HOME, an empty project with `package.json`):

```
agents-inc init --from i0LDegbw          # React+Zustand, 5 global agents; ~/.agents-inc/claude/config.ts stack: React preloaded on all 5
agents-inc edit --ui                     # from the project dir → "Shared as D2N8cn4f"
curl -s localhost:8787/configs/D2N8cn4f  # "web-framework-react":{"install":"plugin","scope":"global","assignments":{}}, same for zustand
cd ~ && agents-inc edit --ui             # from HOME → tYQ5KK9W: assignments present ("pm":"preloaded",…)
cd <project> && agents-inc share         # → D2N8cn4f again, assignments {} (same function)
```

In the editor, `?fromId=D2N8cn4f` shows every agent as `no skills — base agent`, and its preview of `web-developer.md` has no `skills:`. If the user then changes anything there, mints, and runs `edit --from <new id>`, the apply rewrites all 5 agents without React. React is still installed as a plugin but loaded by nothing (`Warning: Skill 'web-framework-react' is assigned to no sub-agent`). The pre-apply disclosure lists only the removed Zustand, not the loss of React from five agents.
This is the default editor flow: the Install dialog says `cd ~/code/your-project` → `init --from`, so the project dir is exactly where a user then runs `edit --ui`. The project's own `config.ts` has no `stack` (only the global one does), which is the likely source.

**D6. `edit --ui --from <id>` in a directory with no installation suggests an apply command that refuses there.**
Repro: fresh HOME, empty dir: `agents-inc edit --ui --from ddob8Bzk` prints `To apply it here instead, run 'npx agents-inc edit --from ddob8Bzk'.` Running exactly that prints `Fetching configuration ddob8Bzk...` then `Error: No installation found. Run 'npx agents-inc init' first…` and exits 1.
`init --ui --from` in the same state correctly says `init --from`. (Minor: `edit --from` also fetches before it checks for an installation.)

## Corrections

- **The brief's step "open that link in the browser" cannot be done literally in this rig.** `edit --ui`, `edit --ui --from` and `init --ui` print `https://agentsinc.sh/editor/?fromId=<id>`, which is `EDITOR_URL`, hard-coded in `packages/cli/src/cli/consts.ts`. `AGENTS_INC_API_URL` moves only the API, so a locally minted id opened at that link shows `this share link points to nothing — showing your own configuration instead.` (shot `49`; `curl https://api.agentsinc.sh/configs/D2N8cn4f` → 404). I opened the same `?fromId=` query on the local editor instead.
- **The add-skill flow (25 and the editor half of 24) cannot run against the local worker as rigged.** `GET :8787/skills` → `503 The skill index is not available yet`, because KV key `skill-index:v2` is filled only by the daily GitHub workflow. Seeding it would mean writing under `apps/server/.wrangler`, which the brief forbids. I substituted production's published index for that one browser route; everything else hit the local worker.
- **Journey 48's row says COVERED.** Its spec re-renders the CLI's own config through `@workspace/compile`, so it never runs the editor's `output-preview.ts` input building, which is where D1–D4 sit. The row's headline, "the preview a visitor is shown is the install a user gets", is false for the editor's preview today.
- **Journey 23/30's row says the hand-off is "the unproved thing, not a second payload build".** The defect is in fact in the payload build: `seedPayloadForInstallation` from a project directory (D5).
- **Journey 27's row says the dialog takes a "dialog + token".** For a public repo the dialog shows no token field. The field appears only after a failed read.
