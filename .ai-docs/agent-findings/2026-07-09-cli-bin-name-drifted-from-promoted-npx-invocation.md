## What Was Wrong

`CLI_BIN_NAME = "agentsinc"` in `src/cli/consts.ts` was interpolated into ~20 user-facing
strings (`Run '${CLI_BIN_NAME} init' first`, etc.) across commands, `utils/messages.ts`,
`installation.ts`, `skill-fetcher.ts`, and `config-types-writer.ts`. This produced runtime
warnings like `Warning: No local skills found. Run \`agentsinc init\` or \`agentsinc edit\`
first.`— but the project's promoted/documented invocation (per README "Getting Started")
is`npx @agents-inc/cli init`, not the bare `agentsinc` global-bin form. The two conventions
(registered bin name vs. promoted npx invocation) were conflated under one constant name that
implied it held a literal binary name, when in practice every call site used it purely as a
"how do I invoke this tool" instructional string.

Additionally, `src/cli/lib/configuration/source-manager.ts` (`writeConfigFromPartial`) had a
hardcoded literal ``Run \`agentsinc init\` first.`` that never went through `CLI_BIN_NAME` at
all — a second, undetected copy of the same drift, found only by grepping for the bare word
`agentsinc` rather than trusting the constant's call sites to be exhaustive.

## Fix Applied

- Renamed `CLI_BIN_NAME` -> `CLI_INVOKE_COMMAND` in `src/cli/consts.ts`, value changed to
  `"npx @agents-inc/cli"`, with a JSDoc comment clarifying this is the promoted invocation
  prefix for user-facing messages, distinct from the registered global bin name (`agentsinc`,
  still correct in `package.json`'s `bin`/`oclif.bin` — intentionally left unchanged).
- Updated all ~21 call sites (commands, `utils/messages.ts`, `installation.ts`,
  `skill-fetcher.ts`, `config-types-writer.ts`, the multi-line generated-README snippet in
  `new/marketplace.ts`) to import/use `CLI_INVOKE_COMMAND`.
- Fixed the orphaned hardcoded literal in `source-manager.ts` to use the constant instead.
- Updated unit tests that asserted the stale literal `"agentsinc init"` (some via the
  constant already, some hardcoded) in `installation.test.ts` (both copies),
  `config-types-writer.test.ts`, and one e2e test (`edit-wizard-launch.e2e.test.ts`).
  Left `smoke.e2e.test.ts`'s assertion on oclif's own `--help` output banner unchanged — that
  string comes from `package.json`'s `oclif.bin` config, not `CLI_INVOKE_COMMAND`, and is
  correctly still `agentsinc`.
- Left internal code comments/JSDoc that reference `agentsinc` as prose (not runtime output)
  and the `// AUTO-GENERATED by agentsinc` file-header attribution in generated `config.ts`
  files untouched — out of scope (not "run this command" instructions, and not printed as
  CLI warnings).
- Updated the two direct `.ai-docs` mentions of the old constant
  (`reference/utilities.md` Branding table, `reference/architecture-overview.md` Project
  Identity table) to prevent immediate drift.

## Proposed Standard

Add a short rule to `.ai-docs/standards/clean-code-standards.md` (or a new
"CLI Self-Reference" note in `reference/utilities.md`): whenever the CLI needs to tell the
user "run this command", it MUST use `CLI_INVOKE_COMMAND` from `consts.ts`, never a raw
literal. Additionally: this project has two legitimately different "what is this tool called"
answers — (1) `CLI_INVOKE_COMMAND` (`npx @agents-inc/cli`) for anything instructing a user to
run a command, and (2) the registered bin name `agentsinc` (`package.json` `bin`/`oclif.bin`)
for anything about the actual global-install executable (oclif's own `--help`/`USAGE` output,
global-install docs). Document this split explicitly near `CLI_INVOKE_COMMAND`'s definition so
future contributors don't recreate the same drift by hardcoding either form.
