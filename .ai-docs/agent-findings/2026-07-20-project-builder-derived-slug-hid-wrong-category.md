## What Was Wrong

`e2e/fixtures/project-builder.ts` computed each test skill's `category` and `slug` by
splitting the skill ID on `-`:

```ts
function derivedCategorySlug(skillId: string): { category: string; slug: string } {
  const parts = skillId.split("-");
  return {
    category: parts.slice(0, 2).join("-"),
    slug: parts.slice(2).join("-") || skillId,
  };
}
```

Its result was spread into `renderMetadataYaml()` in three builder methods (`editable`,
`pluginProject`, `localProjectWithMarketplace`), which together back 91 call sites across
the e2e spec tree.

This is the exact pattern CLAUDE.md bans: "NEVER derive `slug` from skill ID or directory
path — `slug` is a required field in metadata, always pass it explicitly."

The concrete harm is not hypothetical. The derivation silently produced a **category that
does not exist**:

| skill ID            | derived category | canonical category (`CATEGORIES` in `src/cli/types/generated/source-types.ts`) |
| ------------------- | ---------------- | ------------------------------------------------------------------------------ |
| `web-state-zustand` | `web-state`      | `web-client-state`                                                             |

Every other ID happened to land on a real category, so the bug was invisible. That is the
failure mode of derive-from-ID: a wrong value looks exactly as plausible as a right one,
because it is generated by the same rule that generates the right ones. Nothing rejects it,
so the fixture writes a metadata.yaml describing a category the product does not have.

An unmapped ID was equally silent — it would emit a plausible-looking guess rather than
failing, so a typo in a spec's `skills: [...]` array could never surface here.

## Fix Applied

Replaced the derivation with an explicit, asserting lookup table:

```ts
const SKILL_CATEGORY_SLUGS: Partial<Record<SkillId, { category: string; slug: string }>> = {
  "api-framework-hono": { category: "api-framework", slug: "hono" },
  /* ... */
};

function categorySlugFor(skillId: SkillId): { category: string; slug: string } {
  const entry = SKILL_CATEGORY_SLUGS[skillId];
  if (!entry) {
    throw new Error(
      `No category/slug mapping for skill "${skillId}". ` +
        `Add it to SKILL_CATEGORY_SLUGS in e2e/fixtures/project-builder.ts.`,
    );
  }
  return entry;
}
```

All 91 builder call sites were enumerated by brace-matching the call arguments; exactly six
distinct skill IDs reach this code path, and each table entry reproduces the old derivation
byte-for-byte, so no fixture output changed. The table has no unreachable entries.

The `web-state-zustand` → `web-state` mismatch was **deliberately preserved** rather than
corrected, because this refactor pass is strictly behavior-preserving. The wrong value is
now visible as a literal in the table with a comment naming it, instead of being an
invisible consequence of a formula. Correcting it to `web-client-state` is a separate,
assertion-affecting change: the only site that reaches it is the `it.fails` test
`"should show all skill IDs in output"` in `e2e/commands/list.e2e.test.ts`, so the value
must not be changed without re-evaluating that test.

## Proposed Standard

Two additions, both narrow:

1. **`.ai-docs/standards/e2e/anti-patterns.md`** — add a "Derived fixture metadata" entry.
   The existing CLAUDE.md rule is phrased for product code ("`slug` is a required field in
   metadata"), which is why it was not read as applying to a test fixture. State it for
   fixtures explicitly: _a fixture may not compute a skill's `category`, `slug`, `domain`,
   or `displayName` from its ID or directory name. Map them explicitly and throw on an
   unmapped ID._ Give the reason in one line: a derived value that is wrong is
   indistinguishable from one that is right, so nothing ever catches it.

2. **Same doc, adjacent** — when a fixture needs a value that also exists as a product
   constant, the fixture's literal should be checked against that constant at review time.
   `web-state` would have been caught in seconds by grepping `CATEGORIES` in
   `src/cli/types/generated/source-types.ts`. A generated union already encodes the truth;
   fixtures should be diffed against it rather than re-deriving it.
